# OpenSpec workflow для разработки с агентами

Этот гайд предназначен для участников команды, которые планируют и реализуют изменения с помощью Codex, Claude Code, Cursor или OpenCode. OpenSpec хранит согласованный план рядом с кодом, а человек остаётся ответственным за scope, решения, review и merge.

## Когда нужен OpenSpec change

Создавайте change для:

- продуктовых возможностей и исправлений, меняющих наблюдаемое поведение;
- инфраструктуры, зависимостей, tooling и архитектурных решений;
- командных процессов и значимых изменений документации.

Опечатки, исправления ссылок и небольшие уточнения документации можно вносить напрямую через Pull Request. По умолчанию один логический change соответствует одной короткоживущей ветке и одному PR.

## Подготовка

Проект использует OpenSpec CLI 1.7.0 — эту же версию использовали для генерации agent integrations в репозитории.

```bash
npm install -g @fission-ai/openspec@1.7.0
openspec --version
```

Ожидаемая версия:

```text
1.7.0
```

Другие варианты установки описаны в [официальной документации OpenSpec](https://openspec.dev/docs/installation). Репозиторий уже инициализирован: не запускайте `openspec init` повторно. Не запускайте `openspec update` в рамках обычной разработки — обновление CLI и generated agent integrations оформляется отдельным tooling change.

Перед началом работы создайте короткоживущую ветку от актуальной `main` согласно принятому в команде шаблону именования. Все команды OpenSpec и проверки проекта выполняйте из корня репозитория.

## Команды агентов

Этапы workflow одинаковы для всех клиентов; отличается только синтаксис вызова.

| Действие | Codex | Claude Code | Cursor | OpenCode |
| --- | --- | --- | --- | --- |
| Исследовать идею без реализации | `$openspec-explore` | `/opsx:explore` | `/opsx-explore` | `/opsx-explore` |
| Создать change и planning artifacts | `$openspec-propose` | `/opsx:propose` | `/opsx-propose` | `/opsx-propose` |
| Обновить согласованный план | `$openspec-update-change` | `/opsx:update` | `/opsx-update` | `/opsx-update` |
| Реализовать задачи change | `$openspec-apply-change` | `/opsx:apply` | `/opsx-apply` | `/opsx-apply` |
| Синхронизировать delta specs | `$openspec-sync-specs` | `/opsx:sync` | `/opsx-sync` | `/opsx-sync` |
| Архивировать завершённый change | `$openspec-archive-change` | `/opsx:archive` | `/opsx-archive` | `/opsx-archive` |

После команды можно указать имя change или описание задачи. Например:

```text
$openspec-propose add-user-authentication
```

Для прозрачной проверки состояния доступны обычные CLI-команды:

```bash
openspec list
openspec status --change <change-name>
openspec validate <change-name> --strict
```

## Полный lifecycle

```text
Идея → Explore (опционально) → Propose → Human review плана
     → Apply → Проверки и PR → Human review реализации
     → Archive / sync specs → Финальное approval → Merge
```

### 1. Исследуйте сложную или неясную задачу

Используйте `explore`, когда нужно изучить код, сравнить подходы или уточнить границы задачи. На этом этапе агент может анализировать репозиторий и обсуждать решения, но не должен реализовывать изменение.

Для небольшой и хорошо определённой задачи этап можно пропустить.

### 2. Создайте change через propose

Передайте агенту:

- проблему и ожидаемый результат;
- что входит и не входит в scope;
- важные ограничения и совместимость;
- проверяемые критерии готовности.

Агент создаст каталог `openspec/changes/<change-name>` и артефакты, предусмотренные текущей schema:

- `proposal.md` — зачем и что меняется;
- `specs/**/spec.md` — изменения наблюдаемых требований, если они есть;
- `design.md` — выбранный подход и компромиссы;
- `tasks.md` — упорядоченные проверяемые задачи.

Для чистого refactor, tooling или docs change delta specs могут быть явно пропущены. Не создавайте искусственные продуктовые требования только ради наличия spec-файла.

### 3. Проведите human review плана

До реализации человек проверяет:

- соответствует ли proposal реальной проблеме;
- явно ли определены scope и non-goals;
- описывают ли specs наблюдаемое поведение и важные сценарии;
- согласованы ли архитектурные решения и новые зависимости;
- можно ли независимо проверить каждую задачу.

Если решение изменилось, используйте `update`. Агент должен согласовать proposal, specs, design и tasks между собой. Реализацию продолжают только после повторного human review обновлённого плана.

### 4. Реализуйте change через apply

Команда `apply` заставляет агента загрузить актуальный контекст change и выполнять незакрытые задачи по порядку. Агент должен:

- соблюдать утверждённый design и не расширять scope молча;
- вносить минимальные изменения в нужной области;
- добавлять или обновлять релевантные тесты;
- отмечать задачу выполненной только после проверки результата;
- остановиться и предложить `update`, если реализация требует другого решения.

Если одновременно активно несколько changes, всегда указывайте имя явно.

### 5. Выполните проверки и подготовьте PR

Минимальная проверка OpenSpec:

```bash
openspec validate <change-name> --strict
```

Также выполните проверки, соответствующие затронутой области. Для cross-cutting, dependency и configuration changes используется полный набор:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

В PR должны находиться planning artifacts и их реализация. Human reviewer проверяет соответствие результата proposal, specs, design и tasks, а также тесты и отсутствие незаявленного scope.

### 6. Синхронизируйте specs и архивируйте change

Архивируйте change только когда:

- все задачи выполнены;
- OpenSpec и релевантные проверки проходят;
- реализация прошла human review.

Используйте `archive` в той же ветке и PR. Команда проверит готовность артефактов и задач. Если change содержит delta specs, она сравнит их с основными specs и предложит синхронизацию перед архивированием. Отдельный `sync` нужен только когда основные specs требуется обновить без архивирования.

После архивирования проверьте итоговый diff, получите финальное approval и только затем выполняйте merge. Архивный diff является частью того же PR и тоже требует review.

## Ответственность человека и агента

| Человек | Агент |
| --- | --- |
| Формулирует проблему и принимает scope | Исследует репозиторий и выявляет затронутые области |
| Утверждает planning artifacts и архитектурные решения | Создаёт и согласует proposal, specs, design и tasks |
| Разрешает новые зависимости и значимые компромиссы | Реализует только утверждённые задачи |
| Проверяет код, тесты и пользовательское поведение | Запускает проверки и сообщает фактический результат |
| Даёт финальное approval и выполняет merge | Синхронизирует specs и архивирует change по запросу |

Агент не заменяет human review и не может самостоятельно утвердить собственные решения или реализацию.

## Если workflow отклонился от плана

- **Изменился scope или design:** остановите apply, вызовите `update`, проверьте артефакты и только затем продолжайте.
- **Задача или проверка не завершена:** не отмечайте её выполненной и не архивируйте change.
- **Команда выбрала не тот change:** укажите имя change явно при следующем вызове.
- **Версия CLI отличается:** установите 1.7.0; не регенерируйте integrations без отдельного change и review.
- **Нужно сохранить активный change:** используйте `sync` отдельно и не вызывайте `archive`.
