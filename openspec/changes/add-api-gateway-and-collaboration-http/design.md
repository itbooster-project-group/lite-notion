## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь только состояние кода и внешние ограничения, которые определяют подход.

На `main` три процесса слушают три порта (`web:3000`, `api:3001`, `collaboration:3002`), браузер ходит в каждый напрямую. Разграничение — CORS в API и точное сравнение `Origin` в `apps/collaboration/src/auth/origin.ts`.

`apps/collaboration` держит собственный `PrismaClient` (`src/main.ts`), собственную копию `JWT_SECRET` и верифицирует токены через `packages/auth-token`. API ту же проверку делает независимо, через `passport-jwt` в `src/auth/jwt.strategy.ts`; из `auth-token` он импортирует только тип `AccessTokenPayload`, оба раза как `import type`. То есть общий пакет сегодня разделяет форму payload, но не саму проверку.

`PageDocument.yjsState` имеет двух писателей: `PrismaPageDocumentRepository.replace` и `PageDocumentPersistence.store`. Оба делают слепую перезапись; `storageRevision` инкрементируется обоими и не читается в `where` нигде в репозитории. Редактор уже мигрировал на Hocuspocus, но `PageDocumentModule` остаётся подключённым в `app.module.ts`, а `PUT /api/v1/pages/{pageId}/document` — опубликованным.

Внешние ограничения, проверенные по установленным версиям:

- `@hocuspocus/server@4.6.0` содержит хук `onTokenSync` и полный round-trip обновления токена по живому сокету: `connection.requestToken()` шлёт `Auth`/`AuthMessageType.Token`, `@hocuspocus/provider@4.6.0` отвечает через `readAuthMessage` → `provider.sendToken()`, повторно вызывая сконфигурированную `token`-функцию. Бросок из хука закрывает соединение с `Unauthorized`.
- `connection.readOnly` — публичное мутируемое поле, и оно проверяется на каждое входящее sync-сообщение, а не только на хендшейке. Понижение роли применимо к живому соединению.
- `shouldSkipStoreHooks(origin)` в ядре сервера хардкодит `case "redis": return true` — это механизм, не дающий каждой реплике персистить update, пришедший по брокеру.
- `@hocuspocus/extension-redis@4.7.0` зависит от `ioredis` и `@sesamecare-oss/redlock` и требует `@hocuspocus/server@^4.7.0`.
- Браузерный `WebSocket` не умеет задавать заголовки: токен приходит первым кадром внутри протокола, и в HTTP-запросе на upgrade его нет.
- Лимит тела запроса в API уже задан явно: `JSON_BODY_LIMIT = '2mb'` применяется через `app.useBodyParser('json', ...)` в `src/application.ts`. При `DOCUMENT_MAX_BYTES = 1 MiB` (в base64 ≈ 1.33 MiB) запас есть, и переносить документы по HTTP он уже позволяет — менять здесь нечего, требование только фиксируется в спеке.

## Goals / Non-Goals

**Goals:**

- Один сетевой вход, одна реализация проверки подписи, один процесс, знающий `JWT_SECRET`.
- Collaboration без собственного состояния: ни соединения к базе, ни секретов, ни доменной логики прав.
- Снятие обеих границ переавторизации одним механизмом, без событийного канала.
- Возможность запустить collaboration в нескольких репликах.
- Один writer у `PageDocument.yjsState`.

**Non-Goals:**

- Перформанс-оптимизация горячего пути аутентификации: `ext_authz` осознанно добавляет хоп.
- Кеширование вердиктов авторизации в collaboration. Вводить его вместе с самим переходом — значит отлаживать две вещи сразу; оно остаётся возможным потом, с TTL в секунды.
- Замена `Origin`-проверки и CORS. Они становятся избыточными за единым origin, но остаются как эшелон защиты.
- Собственный gateway-сервис. Шлюз — конфигурация прокси; бизнес-логики в нём нет по определению capability.

## Decisions

### Envoy с `ext_authz`, а не с `jwt_authn`

Envoy умеет проверять JWT нативно фильтром `jwt_authn`, и это дешевле — локальная криптография вместо HTTP-хопа. Выбран `ext_authz` по одной причине: API остаётся эмитентом токенов и подписывает их в `TokenService.signAccessToken`, поэтому `JWT_SECRET` из него не уходит никогда. `jwt_authn` означал бы **вторую** копию секрета, а не перенос одной.

Второй довод — WS-путь. Envoy структурно не может аутентифицировать collaboration-соединение, значит вердикт по такому токену всё равно выносит API. При `jwt_authn` в системе жили бы две независимые реализации проверки — фильтр Envoy и код API, — с риском разойтись в списке допустимых алгоритмов и в трактовке `exp`. Ровно это расхождение уже существует сегодня между `auth-token` и `passport-jwt`, и лечить его удвоением не хочется.

**Альтернативы:** Traefik с `ForwardAuth` — эквивалентен по смыслу, выбор Envoy сделан явно. OpenResty с проверкой на Lua — возвращает вторую копию секрета и выносит проверку за пределы TypeScript-кодовой базы. Node/Nest-приложение как шлюз — добавляет процесс и хоп, а прокси-задачи (upgrade, таймауты, буферизация) пришлось бы решать руками.

**Цена, принятая сознательно:** API становится обязательным звеном для любого запроса, включая раздачу frontend. Это ухудшает blast radius его падения и учтено в рисках.

### Периметр включает web

Шлюз выставляет наружу всё: `/` → web, `/api/v1/*` → API, `/collaboration` → collaboration. Один origin убирает CORS как класс, схлопывает `NEXT_PUBLIC_API_BASE_URL` и `NEXT_PUBLIC_COLLABORATION_URL` в один адрес и упрощает CSP до одного источника.

Главное — он делает возможной сетевую изоляцию: внутренние маршруты просто не имеют публичного пути. Альтернатива (web отдельно, за шлюзом только API и collaboration) оставляла бы два origin и всю CORS-конфигурацию при тех же издержках на шлюз.

### Граница аутентификации — префикс API, а не «всё кроме списка»

Соблазнительная формулировка «шлюз аутентифицирует всё, кроме явного перечня» приводит к дедлоку: страница входа тоже маршрут, и потребовав для неё токен, мы делаем недостижимым способ этот токен получить. Поэтому граница проводится по префиксу публичного API, а не по всему трафику.

Раскладка получается такая:

| Маршрут | `ext_authz` | Почему |
|---|---|---|
| `/` и статика приложения | нет | публично раздаваемый бандл; ни данных, ни секретов |
| `/api/v1/auth/{register,login,refresh}`, `/api/v1/health` | нет | вызываются заведомо неаутентифицированным клиентом |
| остальной `/api/v1/*` | да | защищено по умолчанию |
| `/collaboration` | нет | токен недоступен на этапе upgrade — см. спеку |

Приватность экранов SPA остаётся клиентской, как и сегодня в `app/routing/private-route.tsx`: шлюз маршруты приложения не разграничивает. Это не ослабление — данные всё равно отдаёт только API, а он защищён.

Поток входа после этого замыкается: браузер загружает приложение с `/` без токена → приложение показывает экран входа → `POST /api/v1/auth/login` проходит мимо `ext_authz` → API ставит refresh-куку и возвращает access-токен в теле → дальнейшие запросы идут с `Bearer`, и их уже проверяет `ext_authz`.

**Побочное упрощение.** Сегодня refresh-кука ходит cross-origin (web на `:3000`, API на `:3001`) и требует `credentials: include` на каждом запросе. За единым origin она становится same-origin: `SameSite=Lax` достаточно, cross-origin-специфика уходит. Требования `user-authentication` это не меняет — там зафиксированы `HttpOnly` и `SameSite` без привязки к значению, — но реализация упрощается.

**Проверено:** серверных обращений к API из Next.js нет — `workspace-page.tsx` и вся `app/` помечены `'use client'`, данные тянет браузер. Поэтому случая «запрос от Next.js-сервера к API без пользовательского токена» не возникает и отдельной модели аутентификации для него не нужно.

### Две модели аутентификации на внутренних маршрутах

Разделение продиктовано тем, есть ли у операции пользователь в скоупе:

| Маршрут | Аутентификация | Почему |
|---|---|---|
| Проверка токена (для шлюза) | сам проверяемый токен в теле/заголовке | операция и есть проверка |
| Проверка доступа к странице | **токен клиента**, переданный collaboration без изменений | нет режима «от имени пользователя» — нет и привилегии, которой можно злоупотребить |
| Чтение/запись содержимого документа | **сервисный креденшл** | `onStoreDocument` — отложенный flush, он может случиться после ухода последнего клиента комнаты |

Проброс клиентского токена для авторизации заодно даёт бесплатную проверку срока: истёкший токен отвергнет сам API.

### Переавторизация: `onTokenSync` + дедлайн, без брокера

В `onAuthenticate` в контекст соединения кладётся `exp` (его отдаёт ответ эндпоинта проверки — collaboration сам токен не разбирает). По таймеру на `exp - lead` с джиттером вызывается `connection.requestToken()`. Джиттер обязателен: без него после деплоя все клиенты пойдут переавторизовываться синхронно.

В `onTokenSync` выполняется та же процедура, что при подключении: проверить токен, спросить роль, затем либо `connection.readOnly = !canWrite` и перевзвод таймера по новому `exp`, либо бросок — и Hocuspocus закроет соединение сам.

Отдельный таймер закрывает соединение, если клиент на `requestToken` не ответил; он гасится в `onTokenSync`.

Почему не событийный канал отзыва через брокер: он даёт меньшую задержку, но требует правильно ответить на вопрос про наследование — отзыв на предке меняет ответ для заранее неизвестного множества потомков. Механизм по сроку токена от этого вопроса не зависит вовсе и даёт жёсткую верхнюю границу. Событийный канал остаётся возможным поверх, как быстрый путь, — тогда эта же процедура станет его обработчиком.

### Отказ и недоступность различаются

`401`/`403`/`404` от API — авторитетный отказ, соединение закрывается сразу. Таймаут, сетевая ошибка и `5xx` — не отказ: соединение сохраняется, попытка повторяется с backoff в пределах грейс-окна, и только по его исчерпании закрывается.

Без этого разделения падение API начинает **сливать** живые сессии: каждое соединение доходит до дедлайна, переавторизация не удаётся, всех выкидывает. Раньше падение API редактирование не трогало вовсе, и терять это свойство целиком не стоит.

### Redis-расширение, а не свой транспорт

Берётся готовый `@hocuspocus/extension-redis`; `@hocuspocus/server` и `@hocuspocus/provider` поднимаются 4.6 → 4.7. Расширение закрывает и фанаут updates, и awareness, и — через `redlock` — взаимное исключение вокруг сохранения, которого у брокера сообщений нет в принципе.

Sticky-роутинг по комнате на балансере рассматривался и отброшен: имя комнаты в URL не передаётся (`messageAddress` = `documentName\0sessionId`), а `HocuspocusProviderWebsocket` мультиплексирует несколько документов в один сокет — одно соединение может нести комнаты, которым полагались бы разные бэкенды. Redis здесь не предпочтение, а единственный связный вариант.

### Пакеты сворачиваются в `apps/api`

Все три workspace-пакета существовали ради одного: чтобы `apps/api` и `apps/collaboration` пользовались общим кодом внутри своих процессов. Change убирает второго потребителя у каждого — collaboration больше не подключается к базе, не вычисляет права и не проверяет подписи. Проверено по манифестам: после рефакторинга `@lite-notion/database` и `@lite-notion/page-permissions` импортирует только `apps/api`, а `apps/web` не импортирует ни один из них. Граница пакета, разделяющая одного потребителя с самим собой, — накладной расход без выигрыша: три `tsc`-сборки, четыре `pre*`-хука в `apps/api/package.json` и корневой `dev:prepare` перед каждой командой.

Переезд выходит на удивление дешёвым, потому что резолюция никуда не завязана:

- `tsconfig.base.json` не содержит `paths` — модули резолвятся через `exports` workspace-пакетов, поэтому после сворачивания импорты становятся обычными относительными путями и правки резолюции не требуется;
- генератор Prisma пишет в `../src/generated/prisma` относительно схемы, так что после переезда `prisma/` в `apps/api` вывод попадает в `apps/api/src/generated/prisma` — ровно тот каталог, который уже числится в `.gitignore` и сейчас лежит осиротевшим. Блок `generator` не меняется;
- `prisma.config.ts` адресует `prisma/schema.prisma` и `prisma/migrations` относительно рабочего каталога, поэтому работает без правок, будучи положенным в `apps/api`.

После удаления всех трёх каталог `packages/` пустеет, и глоб `packages/*` уходит из `pnpm-workspace.yaml`.

**Альтернатива** — оставить пакеты как есть. Отброшена: единственное, что они теперь дают, — это возможность будущего второго потребителя базы, а change существует именно для того, чтобы такого потребителя не было. Если он когда-нибудь понадобится, выделить пакет обратно из `apps/api` дешевле, чем всё это время платить за границу.

**Побочное следствие:** `apps/api` становится единоличным владельцем миграций. Это корректно ровно потому, что других процессов, ходящих в базу, не остаётся.

### Модель прав меняет способ вызова, но не единственность

Действующее требование `page-permissions` «Одна реализация модели на всех потребителей» прямо запрещает то, что делает этот change: «Обращение одного сервиса к другому по сети ради проверки прав MUST NOT становиться условием работы модели», со сценарием, в котором процесс вне HTTP-слоя получает роль, не обращаясь к API.

Запрет был следствием того, что модель жила в разделяемом пакете и вызывалась внутри процесса. Со сворачиванием пакета и переходом collaboration на HTTP он теряет смысл: сетевой вызов перестаёт быть обходным путём и становится единственным предусмотренным способом. Требование заменяется на «Единственная реализация модели принадлежит API» — все гарантии, не связанные со способом вызова, сохранены дословно, и добавлена одна новая: недоступность API MUST NOT трактоваться как отсутствие доступа.

Стоит отметить, что по сути гарантия становится **сильнее**. Раньше невозможность расхождения REST и collaboration держалась на дисциплине «оба зовут один пакет»; теперь решение физически выносит один процесс, и разойтись нечему.

### Удаление `@lite-notion/auth-token`

После того как collaboration перестаёт верифицировать токены, рантайм пакета теряет единственного потребителя; API берёт оттуда только тип. Пакет удаляется, `AccessTokenPayload` возвращается в API. Это снимает и три `prebuild`/`pretest`/`pretypecheck` хука у обоих приложений.

## Risks / Trade-offs

- **API на критическом пути всего трафика** → падение API теперь роняет и раздачу frontend. Смягчение: health-проверка шлюза, и — отдельно — грейс-окно в collaboration, чтобы живые сессии переживали короткий перебой.
- **Подделка заголовков личности при обходе шлюза** → любой, кто дотянется до порта API, представится кем угодно. Смягчение: порты API и collaboration не публикуются из compose; шлюз безусловно затирает клиентские копии заголовков на **всех** маршрутах, включая публичные. Это несущий контроль, а не удобство — отмечено в спеке явно.
- **Бинарные блобы документов ходят по HTTP** → на каждый debounce-flush уходит до 1 MiB. Смягчение: действующий лимит `2mb` это покрывает; при росте `DOCUMENT_MAX_BYTES` поднимать придётся оба, а частоту flush пересматривать раньше лимита.
- **Бамп Hocuspocus 4.6 → 4.7** → возможны изменения в поведении хуков. Смягчение: бампить и сервер, и провайдер одной задачей, до включения расширения, и прогнать существующие интеграционные тесты комнаты.
- **Переавторизация создаёт периодическую нагрузку на API** → на каждое открытое соединение раз в TTL идёт пара внутренних вызовов. При коротком TTL это заметно. Смягчение: джиттер; при необходимости — кеш вердиктов с TTL в секунды (вынесено в Non-Goals этого change).
- **Совместимость версий сервера и провайдера** → протокол token-sync требует согласованных версий на обоих концах. Смягчение: держать `@hocuspocus/*` в одном catalog-пине.
- **Переписывание импортов при сворачивании пакетов** → около 25 мест, и ошибка здесь ломает сборку, а не поведение. Смягчение: сворачивание выполняется отдельным шагом после того, как collaboration перестал зависеть от пакетов, и проверяется `typecheck` по всему workspace.
- **Порядок выкатки** → между удалением прямого доступа к базе и появлением внутренних маршрутов система нерабочая. Смягчение: порядок ниже.

## Migration Plan

Порядок выбран так, чтобы каждый шаг оставлял систему работоспособной.

1. **Внутренние маршруты в API** — проверка токена, проверка доступа, чтение/запись документа; сервисный креденшл в конфигурации; явный лимит тела. Ничего не ломается: публичные маршруты и прямой доступ collaboration ещё на месте.
2. **Шлюз** — Envoy в compose, маршруты, `ext_authz`, затирание заголовков, WS-маршрут. API временно принимает и заголовки личности, и собственную проверку токена, чтобы шаг был обратимым.
3. **Переключение API на заголовки** — `JwtStrategy` убирается, порты сервисов перестают публиковаться. С этого момента обход шлюза невозможен.
4. **Collaboration на HTTP** — `PageAccessService` и `PageDocumentPersistence` переводятся на HTTP-клиент; из `package.json` уходят `@lite-notion/database`, `@lite-notion/page-permissions`, `@lite-notion/auth-token`, `jsonwebtoken`; из конфигурации — `DATABASE_URL`, `DATABASE_CONNECTION_TIMEOUT_MS`, `JWT_SECRET`.
5. **Бамп Hocuspocus и Redis-расширение** — сначала версии, потом расширение и Redis в compose.
6. **`onTokenSync`** — серверный дедлайн и обновление `token()` на вебе. Веб-часть должна выехать не позже серверной: иначе сервер запросит токен, а клиент вернёт тот же протухающий.
7. **Удаления публичного контракта** — `PageDocumentController` и его модуль, операции документа из OpenAPI snapshot и сгенерированного клиента, msw-хендлеры.
8. **Сворачивание пакетов** — последним, когда у каждого остался один потребитель: `database` и `page-permissions` переезжают в `apps/api`, `auth-token` удаляется, `packages/` исчезает. Шаг чисто механический и не меняет поведения, поэтому стоит после всех функциональных.

**Откат.** Шаги 1–2 откатываются независимо. С шага 3 откат означает возврат `JwtStrategy` и публикацию портов. Шаг 8 откатывается независимо от остальных: он не меняет поведения. Шаг 7 — точка невозврата для публичного контракта: после него клиент, использующий REST-документ, сломается, поэтому он выполняется последним и отдельным коммитом.

## Open Questions

- Конкретные значения `lead` до `exp`, джиттера, грейс-периода ответа клиента и грейс-окна недоступности API. Это настройки, а не архитектура: они не меняют ни спеки, ни разбивку задач, и подбираются при реализации по наблюдаемому поведению.
- Формат сервисного креденшла — общий секрет в заголовке либо mTLS между шлюзом и сервисами. На требования не влияет; для локального и LAN-окружения достаточно общего секрета, выбор для production можно отложить до появления production-конфигурации Envoy.
