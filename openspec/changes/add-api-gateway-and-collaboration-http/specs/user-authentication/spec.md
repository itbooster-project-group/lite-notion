## MODIFIED Requirements

### Requirement: Защита маршрутов по умолчанию
Каждый прикладной HTTP-маршрут API MUST требовать действительный access-токен, если он не помечен явно как публичный. Отсутствующий, синтаксически некорректный, просроченный либо подписанный другим ключом токен MUST приводить к ответу `401` в едином формате HTTP-ошибок. Ответ `401` MUST NOT раскрывать причину отклонения токена.

Проверку токена MUST выполнять шлюз до передачи запроса API, обращаясь за ней к внутреннему маршруту проверки. Перечень публичных маршрутов MUST быть известен шлюзу, и маршрут, в него не попавший, MUST считаться защищённым. Отказ MUST возвращаться шлюзом, а запрос MUST NOT доходить до обработчика.

API MUST отклонять статусом `401` прикладной запрос, дошедший без заголовков личности: такой запрос пришёл мимо шлюза.

`GET /api/v1/health` MUST оставаться публичным и сохранять существующий контракт ответов.

#### Scenario: Приватный маршрут без токена
- **WHEN** клиент обращается к маршруту, не помеченному публичным, без заголовка `Authorization`
- **THEN** ответ имеет статус `401` в едином формате ошибок, и обработчик маршрута не выполняется

#### Scenario: Приватный маршрут с просроченным токеном
- **WHEN** клиент обращается к приватному маршруту с access-токеном, срок действия которого истёк
- **THEN** ответ имеет статус `401`, и обработчик маршрута не выполняется

#### Scenario: Приватный маршрут с подделанной подписью
- **WHEN** клиент обращается к приватному маршруту с токеном, подписанным другим ключом либо с изменённой полезной нагрузкой
- **THEN** ответ имеет статус `401`, и обработчик маршрута не выполняется

#### Scenario: Отказ выдаётся до обработчика
- **WHEN** запрос к приватному маршруту не проходит проверку токена
- **THEN** запрос не доходит до API

#### Scenario: Публичный маршрут без токена
- **WHEN** клиент обращается к `GET /api/v1/health` без токена
- **THEN** запрос обрабатывается по существующему контракту health-проверки

## ADDED Requirements

### Requirement: Внутренний маршрут проверки access-токена

API MUST публиковать внутренний маршрут, принимающий предъявленный клиентом access-токен и отвечающий вердиктом о его действительности. Маршрут MUST проверять подпись и срок действия и MUST возвращать идентификатор пользователя и идентификатор сессии при успехе.

Этот маршрут MUST быть единственной реализацией проверки access-токена в системе: и шлюз для HTTP-трафика, и collaboration runtime для WebSocket-соединений MUST получать вердикт от него. Собственных реализаций проверки MUST NOT существовать ни в шлюзе, ни в collaboration runtime.

Ответ MUST NOT содержать сам токен. Отказ MUST NOT раскрывать причину: просроченный, malformed и подписанный другим ключом токен MUST быть неразличимы в ответе.

Маршрут MUST NOT читать состояние сессии из базы данных на каждом обращении: устаревание токена относительно состояния учётной записи остаётся ограниченным сверху `ACCESS_TOKEN_TTL_S`, как и прежде.

#### Scenario: Действительный токен подтверждается
- **WHEN** вызывающий сервис передаёт действительный непросроченный access-токен
- **THEN** ответ содержит идентификатор пользователя и идентификатор сессии из полезной нагрузки токена

#### Scenario: Недействительный токен отклоняется
- **WHEN** вызывающий сервис передаёт просроченный, malformed или подписанный другим ключом токен
- **THEN** ответ сообщает об отказе

#### Scenario: Причина отказа не раскрывается
- **WHEN** проверка отклоняет просроченный токен и затем токен с неверной подписью
- **THEN** оба ответа одинаковы и не указывают конкретную причину

#### Scenario: Вердикт одинаков для обоих потребителей
- **WHEN** один и тот же access-токен проверяется по запросу шлюза и по запросу collaboration runtime
- **THEN** оба получают одинаковый вердикт и одинаковую личность

#### Scenario: Ответ не содержит токен
- **WHEN** проверка завершается успешно
- **THEN** ответ не содержит предъявленный access-токен
