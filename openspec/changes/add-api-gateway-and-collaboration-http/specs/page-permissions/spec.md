## ADDED Requirements

### Requirement: Единственная реализация модели принадлежит API

Вычисление эффективного разрешения MUST существовать в системе в единственной реализации, и владеть ею MUST API — единственный процесс, обращающийся к базе данных. Ни один другой сервис MUST NOT содержать собственного правила доступа к странице и MUST NOT вычислять роль самостоятельно.

Потребители вне API MUST получать роль вызовом API. Такой вызов MUST быть единственным способом узнать роль для процесса, не владеющего моделью: собственная реализация, копия запроса к базе и любое локальное правило MUST NOT появляться взамен.

Реализация MUST возвращать по паре «пользователь — страница» роль либо её отсутствие. Отсутствие доступа MUST означать запрет соединения, `viewer` — соединение только на чтение, `editor` и `owner` — соединение с правом записи.

Расхождение между решением REST API и решением collaboration runtime для одной пары MUST NOT быть возможным — ни при какой комбинации прямых разрешений, наследования и границ `restricted`. Поскольку решение выносит один и тот же код, расхождение MUST быть невозможно конструктивно, а не за счёт синхронизации двух реализаций.

Выдача доступных пользователю страниц и вычисление роли MUST оставаться согласованными: для каждой страницы, попавшей в выдачу, вычисление роли MUST давать ту же роль, с которой страница показана, и MUST NOT давать отсутствие доступа.

Недоступность API MUST означать невозможность узнать роль, а не отсутствие доступа: потребитель MUST различать авторитетный отказ и невозможность его получить.

#### Scenario: Потребитель вне API получает роль вызовом API
- **WHEN** процесс, не владеющий моделью, спрашивает роль пользователя на странице
- **THEN** он получает её ответом API
- **AND** он не вычисляет роль сам и не обращается к базе данных

#### Scenario: Роль для соединения редактора
- **WHEN** collaboration runtime спрашивает роль пользователя, которому выдан `editor` на странице
- **THEN** он получает `editor`, чего достаточно, чтобы открыть соединение с правом записи

#### Scenario: Роль для соединения читателя
- **WHEN** collaboration runtime спрашивает роль пользователя, которому выдан `viewer`
- **THEN** он получает `viewer`, чего достаточно, чтобы открыть соединение только на чтение

#### Scenario: Запрет соединения
- **WHEN** collaboration runtime спрашивает роль пользователя, у которого доступа к странице нет
- **THEN** он получает отсутствие доступа, чего достаточно, чтобы запретить соединение

#### Scenario: REST и collaboration отвечают одинаково
- **WHEN** для одной и той же пары «пользователь — страница» роль запрашивают REST API и collaboration runtime
- **THEN** оба получают одну и ту же роль

#### Scenario: Выдача доступных страниц согласована с вычислением роли
- **WHEN** для каждой страницы из выдачи доступных страниц отдельно вычисляется роль текущего пользователя
- **THEN** она совпадает с ролью, с которой страница показана в выдаче
- **AND** ни для одной страницы выдачи вычисление не даёт отсутствия доступа

#### Scenario: Недоступность API не подменяется отказом в доступе
- **WHEN** потребитель не может получить роль из-за недоступности API
- **THEN** он не трактует это как отсутствие доступа

## REMOVED Requirements

### Requirement: Одна реализация модели на всех потребителей
**Reason**: Требование запрещало сетевой вызов как условие работы модели: «Обращение одного сервиса к другому по сети ради проверки прав MUST NOT становиться условием работы модели», со сценарием, в котором процесс вне HTTP-слоя получает роль, не обращаясь к API. Это было следствием того, что модель жила в разделяемом пакете и вызывалась обоими сервисами внутри процесса. Change переносит владение данными в API целиком: collaboration runtime больше не подключается к базе, поэтому вызов по сети становится не запрещённым обходным путём, а единственным предусмотренным способом. Сохранять требование, чей центральный запрет намеренно снят, нельзя.

**Migration**: Заменено требованием «Единственная реализация модели принадлежит API». Все гарантии, не связанные со способом вызова, сохранены дословно: единственность реализации, отсутствие собственных правил у потребителей, невозможность расхождения REST и collaboration, трактовка ролей и согласованность с выдачей доступных страниц. Добавлено требование различать авторитетный отказ и недоступность API — раньше такого случая не существовало, потому что вызов был внутрипроцессным.
