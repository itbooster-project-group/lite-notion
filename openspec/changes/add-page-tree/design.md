## Context

Мотивация — см. `proposal.md` → «Why». Требуемое поведение — см. `specs/page-tree/spec.md`.

Существующие ограничения, формирующие подход:

- Prisma schema содержит `User` и `Session`. Именование в ней — Prisma-дефолтное: PascalCase-модели и camelCase-поля без `@@map`, то есть таблицы физически называются `User` и `Session`.
- `apps/api` уже настраивает глобальный `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`) и глобальный `HttpExceptionFilter` в едином формате ошибок. Новый модуль ими пользуется и ничего в них не меняет.
- `JwtAuthGuard` зарегистрирован как `APP_GUARD`, маршруты закрыты по умолчанию. Идентификатор пользователя берётся из `@CurrentUser()` и claims токена, без обращения к базе.
- `PrismaService` намеренно ленивый: процесс API поднимается при недоступной базе. Новый модуль не должен требовать соединения на этапе инициализации.
- Юнит-тесты не поднимают базу (`apps/api/AGENTS.md`). Существующий образец — `auth.repository.in-memory.ts`: доступ к Prisma спрятан за узким репозиторным интерфейсом, а логика тестируется на in-memory реализации.
- PostgreSQL 18 (`apps/api/docker-compose.yaml`).
- `openapi.json` коммитится, CI проверяет drift; web генерирует из него типы, клиент и MSW handlers через orval.
- `src/generate-openapi.ts` собирает Nest-приложение без сети и без базы — новый модуль должен инстанцироваться в этом режиме.
- В `apps/api` действует раскладка «по области использования»: общее — в `src/common/`, специфичное для модуля — в `<module>/` (`constants.ts`, `helpers.ts`, `dto/`, `errors.ts`). Сервисы не хранят константы и хелперы.

## Goals / Non-Goals

**Goals:**

- Совпадение владельца родителя и ребёнка — инвариант базы, а не соглашение кода. Ошибка в прикладном слое не должна приводить к дереву с двумя владельцами.
- Перестановка одного элемента списка не переписывает ранги остальных: изменение позиции — это `UPDATE` ровно одной строки.
- Перемещение поддерева не трогает потомков: поддерево «переезжает» изменением единственной ссылки на родителя.
- Отсутствие цикла проверяется в той же транзакции, что и запись, и не ломается при параллельных перемещениях в одном дереве.
- Модуль тестируется без живой базы: вся работа с Prisma изолирована за узким репозиторным интерфейсом, и бизнес-правила проверяются на in-memory реализации.
- Содержимое документа непрозрачно для API: сервер хранит и отдаёт байты, не завися от версии Tiptap и не разбирая Yjs.

**Non-Goals:**

- Материализованный путь, closure table и `ltree`. Дерево читается целиком одним запросом, поэтому рекурсивные структуры хранения не окупаются.
- Ограничение глубины дерева. Обход предков и сборка дерева линейны по числу страниц владельца; отдельный лимит глубины вводить не нужно, пока нет данных о реальных деревьях.
- Пагинация и частичная загрузка дерева. Дерево одного пользователя в MVP помещается в один ответ.
- Слияние параллельных правок документа на сервере. Запись — замена состояния целиком; разрешение конфликтов остаётся за клиентским Yjs и за будущим realtime-транспортом.
- Уникальность ранга на уровне базы — см. решение 5.

## Decisions

### 1. Именование: Prisma-дефолт вместо `snake_case` из ERD

ERD в постановке использует `PAGES`, `PAGE_DOCUMENTS`, `PROJECTS` и `snake_case` для колонок. В schema заводятся модели `Page`, `PageDocument`, `Project` с camelCase-полями и без `@@map`.

Причина — консистентность: `User` и `Session` уже созданы по Prisma-дефолту, а смешение двух конвенций в одной базе хуже, чем расхождение с нотацией диаграммы. ERD читается как логическая модель, а не как DDL. Альтернатива — перевести всю базу на `@@map`/`@map` со `snake_case` — потребовала бы переписать существующую миграцию и выходит за scope этого изменения.

### 2. Модель данных

Колонки заводятся там, где их требует либо операция этого изменения, либо инвариант, который дешевле заложить сразу, чем добавлять миграцией по живым данным. Колонки sharing (`accessMode`), ассетов (`coverAssetId`), иконки (`icon`) и отдельного последнего редактора (`updatedById`) не заводятся.

```prisma
model Project {
  id      String @id @default(uuid()) @db.Uuid
  ownerId String @db.Uuid
  name    String @db.VarChar(255)

  owner User   @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  pages Page[]

  /// Составной ключ-кандидат: цель — composite FK со стороны Page, а не поиск по паре.
  @@unique([id, ownerId])
  @@index([ownerId])
}

model Page {
  id           String    @id @default(uuid()) @db.Uuid
  ownerId      String    @db.Uuid
  projectId    String    @db.Uuid
  parentPageId String?   @db.Uuid
  createdById  String    @db.Uuid
  title        String    @db.VarChar(255)
  position     String    @db.VarChar(255)
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt
  deletedAt    DateTime?

  owner     User          @relation("PageOwner", fields: [ownerId], references: [id], onDelete: Cascade)
  createdBy User          @relation("PageCreatedBy", fields: [createdById], references: [id], onDelete: Restrict)
  project   Project       @relation(fields: [projectId, ownerId], references: [id, ownerId], onDelete: Cascade)
  parent    Page?         @relation("PageTree", fields: [parentPageId, ownerId, projectId], references: [id, ownerId, projectId], onDelete: Cascade, onUpdate: NoAction)
  children  Page[]        @relation("PageTree")
  document  PageDocument?

  /// Составной ключ-кандидат: цель — composite FK со стороны parent, а не поиск по тройке.
  @@unique([id, ownerId, projectId])
  @@index([ownerId, parentPageId, position])
  @@index([ownerId, deletedAt])
}

model PageDocument {
  pageId              String   @id @db.Uuid
  tiptapSchemaVersion Int
  yjsState            Bytes
  storageRevision     BigInt   @default(0)
  createdAt           DateTime @default(now())
  updatedAt           DateTime @updatedAt

  page Page @relation(fields: [pageId], references: [id], onDelete: Cascade)
}
```

Ключевое здесь — два составных ключа-кандидата и два composite foreign key поверх них:

- `(projectId, ownerId) → Project(id, ownerId)` — проект страницы принадлежит тому же пользователю, что и страница;
- `(parentPageId, ownerId, projectId) → Page(id, ownerId, projectId)` — родитель совпадает с ребёнком и по владельцу, и по проекту.

`id` уже уникален сам по себе, поэтому ни `(id, ownerId)`, ни `(id, ownerId, projectId)` не добавляют ограничения на данные — они существуют ровно для того, чтобы на них могли сослаться составные FK. Дальше PostgreSQL сам гарантирует, что дерево не растянется ни на двух владельцев, ни на два проекта. Оба инварианта перестают быть соглашением кода.

Родитель nullable, а `ownerId` и `projectId` — нет. Составной FK в PostgreSQL по умолчанию `MATCH SIMPLE`: при `parentPageId IS NULL` проверка не выполняется, и root-страница проходит. Это ровно нужное поведение, специальных обходных путей не требуется.

Побочное следствие тройного FK: ни смена владельца, ни смена проекта у страницы с детьми невозможны без одновременной смены у всех потомков. Передачу владения и перенос дерева между проектами это не запрещает, но заставляет реализовывать их как явные операции над всем поддеревом — что и требуется, а обычным перемещением они недостижимы. Цена решения — именно эта: перенос страницы в другой проект перестаёт быть частным случаем `move` и станет отдельной операцией, когда понадобится.

`onDelete: Cascade` на self-relation: удаление страницы удаляет поддерево. Пользовательского удаления в этом изменении нет, но каскад должен быть заложен в миграцию сразу, иначе `onDelete: Cascade` по `ownerId` от `User` упрётся в дочерние строки.

`createdById` — `onDelete: Restrict`, а не `Cascade`: удаление автора не должно удалять чужие страницы. Владелец при этом каскадный — удаление владельца удаляет его дерево. Отдельного `updatedById` нет: без sharing последний редактор всегда совпадает с владельцем, и колонка с заведомо одним и тем же значением создавала бы иллюзию, что они могут разойтись.

`deletedAt` заводится, хотя удаления в scope нет. Причина не в форме таблицы, а в запросах: soft-delete меняет каждое чтение, и дешевле написать все чтения с фильтром сразу, чем ревизовать их позже. Ни один маршрут этого изменения `deletedAt` не выставляет, поэтому фильтр всегда истинен — но он есть, и тест на невидимость помеченной удалённой страницы его проверяет.

`PageDocument` создаётся вместе со страницей, инициализируясь пустым документом: `tiptapSchemaVersion` — константа `TIPTAP_SCHEMA_VERSION` из `src/pages/constants.ts`, `yjsState` — пустой буфер, `storageRevision` — `0`. Связь `1..1` из ERD выполняется с первого дня, поэтому чтение документа никогда не встречает отсутствующую строку и не нуждается в ленивом создании.

### 2a. Минимальный API проектов

`projectId` обязателен, поэтому без способа создать проект маршрут создания страницы неработоспособен. В scope добавляются два маршрута: `POST /api/v1/projects` (имя → созданный проект) и `GET /api/v1/projects` (проекты владельца). Переименование, удаление проекта и перенос страниц между проектами не добавляются — они не нужны ни одной операции над деревом.

Альтернатива — автоматически заводить пользователю личный проект (лениво при первой странице или при регистрации) и не показывать проекты в API вовсе — отвергнута: она прячет обязательную сущность за неявным поведением, а вариант с регистрацией дополнительно потребовал бы миграции-backfill для уже существующих пользователей.

`ProjectsModule` строится по той же схеме, что и `PagesModule`: контроллер без бизнес-логики, сервис, репозиторий поверх `PrismaService` и in-memory репозиторий для тестов.

### 2b. Содержимое документа: непрозрачный Yjs state, полная замена, без версионирования

Два маршрута: `GET /api/v1/pages/{pageId}/document` и `PUT /api/v1/pages/{pageId}/document`. Тело записи — `{ tiptapSchemaVersion: number, yjsState: string }`, где `yjsState` — base64. Создания и удаления документа отдельными маршрутами нет: строка появляется вместе со страницей и уходит каскадом вместе с ней.

`PUT`, а не `PATCH`: Yjs state — цельное состояние, а не набор полей, и запись заменяет его целиком. Частичного обновления содержимого не бывает.

Сервер не разбирает Yjs state. Он проверяет, что это корректный base64 допустимого размера, и кладёт байты в `Bytes`-колонку. Альтернатива — валидировать структуру документа на сервере — потребовала бы зависимости `yjs` в API и продублировала бы работу редактора, ничего не давая: некорректный state всё равно обнаружит клиент, а сервер в MVP ничего с содержимым не делает.

`storageRevision` инкрементируется при каждой записи, но клиент его не присылает и не получает. Версионирование вне scope, поэтому optimistic concurrency нет и запись работает по принципу «последний выигрывает». Колонка при этом наполняется с первого дня — когда понадобится обнаружение конфликтов, у существующих документов уже будет монотонный счётчик, и вводить его задним числом не придётся. Не выставлять колонку в API — сознательное решение: значение, которое клиент видит, но не может использовать, приглашает завязаться на него раньше, чем контракт определён.

**Предел размера.** Express по умолчанию режет JSON-тело на 100 KB, а Yjs state документа с историей правок легко это превышает. Вводится константа `DOCUMENT_MAX_BYTES` (1 MiB), которая применяется дважды: как лимит `express.json` в `configureApplication` и как валидация длины строки в DTO. Двойная проверка нужна потому, что лимит парсера даёт `413` от Express, а валидация DTO — `400` в едином формате ошибок; предел парсера ставится с запасом над `DOCUMENT_MAX_BYTES`, чтобы отказ формировал именно DTO. Отмечу, что конкретное значение предела — решение этого дизайна, а не требование постановки: постановка размер не оговаривает, а без явного предела маршрут записи становится способом исчерпать память процесса.

**Сервис документа отдельно от сервиса дерева.** `PageDocumentService` живёт в `src/pages/`, но не смешивается с `PagesService`: у него нет ни транзакций, ни блокировок, ни рангов — только чтение и замена байтов по проверенной принадлежности страницы. Проверку принадлежности он переиспользует из репозитория страниц, поэтому неразличимость `404` держится одним и тем же кодом.

### 3. Fractional rank в `position`

`position` — строка в алфавите `0-9A-Za-z` (base62), сравниваемая лексикографически. Вставка между соседями `a` и `b` — строка, лежащая строго между ними; вставка в конец — увеличение последнего ранга. Порядок братьев — `ORDER BY position ASC, id ASC`.

Почему не целочисленный `order` с перенумерацией: перестановка одного элемента переписывала бы все следующие строки уровня, что превращает drag-and-drop в массовый `UPDATE` и в источник конфликтов при параллельных правках. Fractional rank даёт `UPDATE` одной строки.

Почему свой генератор, а не пакет `fractional-indexing`: алгоритм — около сорока строк (поиск средней строки между двумя ключами в base62 с добавлением разряда, когда середины нет), а корневой `AGENTS.md` запрещает добавлять зависимость, если она не требуется дизайном. Генератор живёт в `src/pages/helpers.ts` и тестируется как чистая функция: середина между соседями, вставка в начало и в конец, вставка между соседними по алфавиту ключами (`a` и `b` → `aV`), устойчивость к многократным вставкам в одну и ту же щель.

Ранг не принимается от клиента ни в одном запросе. Клиент говорит «между этими двумя», сервер считает строку. Иначе клиент мог бы записать ранг, ломающий монотонность уровня, и инвариант порядка перестал бы быть серверным.

**Деградация.** Многократная вставка в одну щель удлиняет ранг. Длина ограничена `VarChar(255)`; практический предел — сотни последовательных вставок в одно место. Перебалансировка уровня в этом изменении не реализуется — см. «Risks».

### 4. `ORDER BY position, id` вместо уникального ранга

Уникальность `(ownerId, parentPageId, position)` не заводится. У root-страниц `parentPageId IS NULL`, а PostgreSQL по умолчанию считает NULL-значения различными, так что обычный unique index защищал бы только дочерние уровни и оставлял корень без ограничения — половинчатая гарантия хуже отсутствующей, потому что создаёт видимость инварианта. Вариант с `NULLS NOT DISTINCT` (доступен в PostgreSQL 18) в Prisma schema не выражается, а добавление такого индекса сырым SQL в миграцию рассинхронизировало бы миграции и datamodel, что ломает проверку `prisma migrate diff ... --exit-code`, которой пользуется предыдущее изменение.

Вместо этого — детерминированный тай-брейк по `id`. Совпадение рангов не нарушает контракт: порядок остаётся стабильным между чтениями, а требование спеки — именно детерминированность, не уникальность.

### 5. Транзакционное перемещение: advisory lock на дерево владельца

`POST /api/v1/pages/{pageId}/move` выполняется в одной Prisma-транзакции, которая начинается с `pg_advisory_xact_lock` по хешу `ownerId`. Дальше в транзакции: чтение перемещаемой страницы и нового родителя с проверкой владельца и совпадения проекта, проверка отсутствия цикла, чтение рангов соседей, вычисление нового ранга, единственный `UPDATE` с новыми `parentPageId` и `position`. `projectId` в этом `UPDATE` не участвует — тройной FK всё равно отверг бы его смену на несогласованную с потомками.

Проверка цикла — подъём по предкам нового родителя рекурсивным CTE; если среди них встречается перемещаемая страница (или новый родитель равен ей самой), операция отклоняется.

Почему advisory lock, а не только проверка: две одновременные транзакции, каждая корректная по отдельности, могут создать цикл — `A` переносится под `B`, `B` переносится под `A`, и обе проверки проходят до того, как противоположная запись стала видимой. Классическое лечение — `SERIALIZABLE`, но это ставит уровень изоляции на всё приложение или требует ретраев на конфликт сериализации. Advisory lock, взятый по владельцу, сериализует только перемещения внутри одного дерева и ничего не стоит остальным запросам: у каждого владельца свои деревья, и конкуренция между владельцами отсутствует по определению.

Блокировка берётся первой операцией транзакции — иначе две транзакции успеют взять разные строчные блокировки до advisory lock и получат deadlock.

`SELECT ... FOR UPDATE` по отдельным строкам не выбран: цикл — свойство пути, а не двух строк, и залочить «путь» построчно нельзя, не залочив заранее неизвестное множество предков.

### 6. Один маршрут `move` вместо отдельных reparent и reorder

Изменение позиции — частный случай перемещения, у которого новый родитель совпадает со старым. Разделение на два маршрута дало бы две реализации одного инварианта и открыло бы промежуточное состояние при «перенести и поставить на место»: клиенту пришлось бы делать два запроса, между которыми страница висит в конце нового уровня. Тело `move` — `{ parentPageId: string | null, previousSiblingId?: string | null, nextSiblingId?: string | null }`.

Переименование, наоборот, вынесено в `PATCH /api/v1/pages/{pageId}`: у него нет ни транзакции, ни блокировки, ни проверки цикла, и смешивать его со структурной операцией значило бы платить advisory lock за смену заголовка.

### 7. Границы ошибок: `404` для чужого, `409` для цикла, `400` для несогласованного соседа

Чужая и несуществующая страница отвечают одинаковым `404`. Это касается всех идентификаторов запроса, включая `parentPageId` и соседей в теле `move`: иначе `404` на самой странице и, скажем, `403` на родителе давали бы оракул существования чужих страниц.

Цикл — `409`: идентификаторы валидны и доступны вызывающему, конфликт возникает с текущим состоянием дерева. Сосед, существующий в дереве пользователя, но лежащий не под целевым родителем, — `400`: запрос внутренне противоречив, и раскрытия чужих данных здесь нет, потому что сосед и так принадлежит вызывающему. По той же причине `400` отвечает и родитель из другого проекта того же владельца: обе страницы вызывающему видны, противоречив сам запрос.

Собственные типы ошибок (`PageNotFoundError`, `ProjectNotFoundError`, `PageCycleError`, `SiblingParentMismatchError`, `PageProjectMismatchError`) объявляются в `src/pages/errors.ts` и `src/projects/errors.ts` и переводятся в HTTP-исключения сервисом — репозиторий не знает про HTTP, как это уже сделано в `auth/errors.ts`.

### 8. Сборка дерева в приложении, а не рекурсивным CTE

`GET /api/v1/pages` читает все неудалённые страницы владельца одним плоским `SELECT` с фильтром `deletedAt: null` и `ORDER BY parentPageId NULLS FIRST, position, id` и собирает вложенность в памяти за один проход по массиву. Рекурсивный CTE здесь ничего не даёт: выбираются всё равно все строки владельца, а сборка дерева всё равно происходит в приложении, поскольку JSON-ответ вложенный.

Плоский запрос дополнительно означает, что чтение дерева тестируется на in-memory репозитории без SQL.

### 9. Тесты: in-memory репозиторий, без автоматической проверки schema

Бизнес-правила (владелец, проект, цикл, порядок, транзакционность отката) проверяются на `pages.repository.in-memory.ts` и `projects.repository.in-memory.ts` по образцу `auth.repository.in-memory.ts`. HTTP-уровень — точечные `supertest`-тесты на статусы и неразличимость `404`.

Constraints и индексы автоматическими тестами в этом изменении не покрываются. Их исполняет база, а юнит-тесты её не поднимают (`apps/api/AGENTS.md`); тест, который вместо базы читал бы текст schema и миграции, проверял бы лишь то, что инвариант объявлен, и был бы дублированием самого объявления, а не независимой проверкой. Единственной проверкой остаётся ревью SQL миграции человеком (задача 1.5) плюс `prisma migrate diff --exit-code`, подтверждающий, что миграция полностью воспроизводит datamodel.

Настоящая проверка исполнения constraint требует интеграционного прогона против PostgreSQL — окружения для таких тестов в репозитории пока нет, и его создание выходит за scope этого изменения. Следствие для acceptance criteria постановки — см. «Risks».

## Risks / Trade-offs

- **Деградация длины fractional rank при повторных вставках в одну щель** → ранги ограничены `VarChar(255)`, чего хватает на сотни вставок подряд в одно место; перебалансировка уровня не реализуется в этом изменении. Тест генератора фиксирует рост длины, чтобы регрессия была заметна. Когда появятся реальные данные, перебалансировка добавится как фоновая операция без изменения контракта API.
- **Advisory lock сериализует перемещения внутри одного дерева** → пользователь, делающий несколько drag-and-drop подряд, получает их последовательное выполнение. Блокировка держится доли миллисекунды и берётся только на `move`; чтение, создание и переименование её не берут.
- **Constraints и индексы не покрыты автоматическими тестами** → сценарии спеки, где запись отвергает база (разные владельцы у родителя и ребёнка, разные проекты, владелец страницы против владельца проекта), остаются без исполняемой проверки: ошибка в описании composite FK пройдёт CI незамеченной и обнаружится только на живой базе. Митигация — ревью SQL миграции при код-ревью Pull Request (задача 1.5) плюс разовая ручная проверка на живой PostgreSQL 18, выполненная при реализации 27.08.2026: все три запрета сработали нарушением FK, root-страница с NULL-родителем прошла, каскад удаления поддерева сработал. Разовая проверка не заменяет теста — она подтверждает текущую миграцию, но не защитит от регрессии в следующей. Это известное расхождение с acceptance criterion постановки «constraints, индексы, API и бизнес-правила покрыты тестами»: API и бизнес-правила покрыты, constraints и индексы — нет. Закрывается отдельным изменением, вводящим интеграционные тесты против PostgreSQL.
- **Каскадное удаление владельца затрагивает большое дерево** → удаление `User` удаляет все его страницы и документы. Пользовательского удаления учётной записи в продукте пока нет, так что каскад срабатывает только при ручном вмешательстве.
- **Тройной FK делает перенос страницы между проектами недостижимым обычным `move`** → он станет отдельной операцией над всем поддеревом, когда понадобится. Это прямое следствие выбранного инварианта: база не даст дереву растянуться на два проекта, и обойти её частичным обновлением нельзя.
- **`deletedAt` заведён без управляющего поведения** → ни один маршрут его не пишет, поэтому поведенческого теста на удаление нет. Риск снят фильтром во всех чтениях и тестом на невидимость помеченной страницы.
- **`BigInt` в `storageRevision`** → тип не сериализуется в JSON напрямую. `storageRevision` намеренно не выходит наружу ни в одном ответе, поэтому проблема не возникает; если колонку когда-нибудь начнут отдавать, её придётся сериализовать как строку.
- **Запись «последний выигрывает» теряет параллельные правки** → два клиента, редактирующие страницу одновременно, затрут работу друг друга. Это прямое следствие отказа от версионирования и realtime в этом изменении. Митигации на уровне продукта пока нет; закрывается capability совместного редактирования, для которой `storageRevision` уже наполняется.
- **Предел `DOCUMENT_MAX_BYTES` в 1 MiB может оказаться мал для длинных документов** → значение выбрано без данных о реальных документах. Оно вынесено в константу и меняется одной правкой; превышение даёт понятный `400`, а не молчаливое усечение.
- **Sharing, ассеты и иконки потребуют своих миграций `Page`** → `accessMode`, `coverAssetId` и `icon` не заводятся заранее. Миграций будет больше, но каждая придёт вместе с поведением, которое её оправдывает, и с тестами на это поведение; все они аддитивны.

## Migration Plan

1. Миграция аддитивна: три новые таблицы, существующие `User` и `Session` не изменяются, кроме появления обратных связей (обратные связи Prisma — это не DDL). Данных для backfill нет.
2. Миграция создаётся через `prisma migrate dev`, проверяется `prisma migrate status` и `prisma migrate diff --from-config-datasource --to-schema --exit-code` («No difference detected»).
3. Развёртывание — `prisma migrate deploy`, как и для первой миграции.
4. Откат: удаление трёх таблиц. Поскольку до появления UI страниц данных в них нет, откат безопасен. После появления UI откат означает потерю страниц и требует отдельного решения.
