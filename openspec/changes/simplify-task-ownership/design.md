## Context

Схема БД спроектирована, но не реализована: `schema.prisma`, миграции и API задач отсутствуют, поэтому изменение затрагивает только проектные документы и описания задач. Мотивация описана в `proposal.md`, требуемое поведение — в `specs/task-management/spec.md`.

Документы, которые нужно изменить, находятся в незамерженных Pull Request: `docs/database-schema.md` — в #20, `docs/mvp-plan.md` — в #22. Это определяет способ внесения правок.

## Goals / Non-Goals

**Goals:**

- Привести проектные документы к модели «одна задача — один владелец» без расхождений между ER-диаграммой, описанием сущностей и планом MVP.
- Не оставить в документах обоснований, которые перестали быть верными после изменения.
- Сохранить корректность уже заведённых задач на GitHub, чтобы исполнитель не реализовал отменённое требование.

**Non-Goals:**

- Не вводить поле исполнителя, отличное от владельца: в MVP это одно лицо.
- Не проектировать модель workspace и командной работы, даже в виде задела на будущее.
- Не менять модель страниц, блоков и гостевого доступа.

## Decisions

### 1. Удаление `TASK_ASSIGNEE` вместо сохранения таблицы с одной записью

Junction-таблица удаляется полностью, а не остаётся с ограничением «не более одной записи на задачу». Таблица с искусственным ограничением сохраняет сложность соединения при каждом запросе задач и создаёт ложное впечатление, что многопользовательность частично поддержана. Возврат к нескольким исполнителям в будущем — это отдельное изменение вместе с workspace, и тогда таблица создаётся заново вместе с моделью прав.

Владение задачей выражается единственным полем `TASK.owner_id`.

### 2. Переименование `created_by` в `owner_id`

После отказа от отдельных исполнителей автор, владелец и исполнитель задачи — одно лицо, и имя `created_by` описывает только факт создания, оставляя вопрос о владении открытым. Имя `owner_id` согласуется с `PAGE.owner_id`, поэтому во всех сущностях MVP владение выражается одинаково.

Альтернатива — оставить `created_by` и считать автора владельцем по соглашению — отклонена: соглашение, не выраженное в схеме, теряется при чтении документа.

### 3. `TASK.page_id` остаётся необязательным, но с новым обоснованием

Прежнее обоснование опиралось на то, что исполнитель задачи может не иметь доступа к странице. После изменения владелец задачи и владелец страницы — один пользователь, и это обоснование недействительно.

Поле остаётся nullable по продуктовой причине: задача может быть личной и не относиться ни к какому документу. Требование ограничить привязку только своими страницами зафиксировано в спецификации.

Альтернатива — сделать `page_id` обязательным — отклонена: она превращает задачи в придаток страницы и лишает пользователя возможности вести задачи, не заводя документ.

### 4. Явная граница между `TASK` и блоком типа `todo`

До изменения сущности неявно различались многопользовательностью: задача воспринималась как командная, блок — как элемент личного документа. После перехода к одиночной модели это различие исчезло, и без явной формулировки две сущности выглядят дублирующими.

Граница фиксируется в документации схемы: блок `todo` — элемент содержимого страницы с бинарным состоянием, задача — самостоятельная сущность с тремя статусами, сроком и сквозным списком. Синхронизация между ними не предусмотрена, что зафиксировано отдельным требованием в спецификации.

### 5. Правки вносятся в исходные Pull Request, а не поверх `main`

`docs/database-schema.md` и `docs/mvp-plan.md` ещё не смержены. Правка вносится в ветки соответствующих PR, чтобы в историю не попали документы с заведомо отменённым решением и чтобы ревьюер видел итоговую версию, а не цепочку из решения и его отмены.

Артефакты этого change размещаются в ветке PR #20 вместе с документацией схемы: именно там меняется модель данных. PR #22 получает только правку состава этапа 4.

Альтернатива — дождаться мержа обоих PR и внести исправления отдельным изменением — отклонена: она гарантирует, что в `main` какое-то время будут лежать взаимно противоречивые документы, а ревьюеры потратят время на обсуждение уже отменённого решения.

### 6. Синхронизация описаний задач на GitHub

Issue #9 содержит копию ER-диаграммы, issue #17 — требования и критерии приёмки про нескольких исполнителей и их аватары. Оба описания обновляются в рамках этого изменения, иначе исполнитель #17 реализует отменённое требование, а #9 останется источником устаревшей диаграммы.

## Risks / Trade-offs

- [Возврат нескольких исполнителей потребует заново создавать junction-таблицу] → Это осознанная плата за простоту MVP; изменение придёт вместе с workspace, где всё равно потребуется модель прав, и проектировать её заранее без требований преждевременно.
- [Правки в двух открытых PR могут привести к конфликтам при мерже] → Файлы разные, пересечение только в `README.md`, где оба PR добавляют раздел «Документация»; конфликт разрешается объединением списка ссылок.
- [Описания задач на GitHub и документы в репозитории могут снова разойтись] → Обновление обоих issue включено в задачи этого изменения, а не оставлено на потом.
- [Различие между задачей и блоком `todo` может остаться неочевидным для пользователя] → Продуктовое решение вне скоупа этого изменения; на уровне модели различие зафиксировано требованием и таблицей сравнения в документации.

## Migration Plan

Миграция данных не требуется: схема не реализована, таблиц не существует, `schema.prisma` не создан. Изменение сводится к правке проектных документов и описаний задач до начала реализации.

Откат — возврат junction-таблицы `TASK_ASSIGNEE` и прежнего имени поля в документации; поскольку кода нет, откат не затрагивает работающую систему.
