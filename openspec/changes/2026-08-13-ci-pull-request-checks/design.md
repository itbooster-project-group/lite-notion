## Context

Репозиторий — pnpm workspace с двумя приложениями (`apps/web` на Next.js, `apps/api` на NestJS) и корневыми командами `lint`, `typecheck`, `test`, `build`, описанными в `AGENTS.md`. Issue #3 требует, чтобы эти проверки обязательно выполнялись в CI при создании и обновлении PR, а PR с непройденными проверками нельзя было смержить. `main` сейчас не защищён (проверено через `gh api repos/.../branches/main/protection` — `404 Not Found`), прямой push разрешён. Мотивация и границы изменения описаны в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- CI автоматически запускается на каждый PR в `main` и на каждый новый коммит в этом PR.
- `lint`, `typecheck`, `test`, `build` выполняются для затронутых приложений и делают CI failed при любой ошибке.
- Merge PR с failed или незавершёнными обязательными чеками невозможен.
- Прямой push и force-push в `main` невозможны.
- Успешный PR явно показывает статус каждого обязательного чека.

**Non-Goals:**

- Не настраивать деплой или публикацию артефактов.
- Не добавлять e2e-тесты, визуальное тестирование или пороги покрытия.
- Не вводить path-based skip логику (запуск джоба только при изменении конкретного приложения) — при двух небольших приложениях экономия времени незначительна, а сложность конфигурации возрастает. Может быть пересмотрено отдельным изменением при росте монорепозитория.
- Не менять требование обязательного human review (`config.yaml` уже фиксирует это как инженерное правило); в рамках этой задачи оно включается в branch protection как отдельная настройка, но не является предметом технической реализации CI.

## Decisions

### 1. GitHub Actions как CI-платформа

Репозиторий уже размещён на GitHub, поэтому GitHub Actions даёт нативную интеграцию с PR-статусами и branch protection без внешних сервисов и секретов. Альтернативы (self-hosted runner, внешний CI) не рассматриваются: они добавляют инфраструктурную нагрузку, не оправданную текущим масштабом проекта.

### 2. Триггеры и отмена устаревших запусков

Workflow запускается на `pull_request` с типами `opened`, `synchronize`, `reopened` и `branches: [main]`. Дополнительно используется `concurrency`:

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.event.pull_request.number }}
  cancel-in-progress: true
```

Это гарантирует, что при добавлении нового коммита в PR предыдущий незавершённый запуск отменяется, а не расходует ресурсы параллельно с актуальным.

### 3. Структура джобов: `lint`, `web`, `api`

- `lint` — единый джоб, запускающий `pnpm lint` (Biome) для всего workspace, так как Biome конфигурируется в корне и проверяет все пакеты за один проход.
- `web` — джоб, выполняющий последовательно `pnpm --filter @lite-notion/web run typecheck`, `run test`, `run build`.
- `api` — джоб, выполняющий последовательно `pnpm --filter @lite-notion/api run typecheck`, `run test`, `run build`.

Три отдельных джоба идут параллельно (кроме внутренней последовательности шагов каждого джоба) и дают три понятных обязательных статус-чека в PR вместо одного общего, что упрощает диагностику: видно, какое именно приложение не прошло проверку. Job matrix по списку приложений не используется, так как у `web` и `api` разные версии Node-зависимостей и потенциально разное количество шагов в будущем (например, миграции БД для API); отдельные джобы проще расширять независимо.

### 4. Установка зависимостей в каждом джобе

Каждый джоб самостоятельно выполняет `pnpm/action-setup` (версия закреплена как `11.21.0`, синхронно с `packageManager` в `package.json`), `actions/setup-node` (Node 22, `cache: pnpm`) и `pnpm install --frozen-lockfile`. `pnpm/action-setup` сам устанавливает нужную версию pnpm, поэтому отдельный `corepack enable` не требуется. Общий build-джоб с шарингом артефактов между `lint`/`web`/`api` не вводится: три параллельных установки с pnpm-кэшем (`actions/setup-node` кэширует store по хэшу `pnpm-lock.yaml`) быстрее и проще, чем настройка artifact upload/download между джобами при текущем размере репозитория.

### 5. Branch protection на `main`

Настраивается через `gh api repos/itbooster-project-group/lite-notion/branches/main/protection` (PUT) или эквивалентно в Settings → Branches:

- `required_pull_request_reviews`: обязательный PR перед merge (соответствует существующему правилу "human code review is mandatory" из `config.yaml`).
- `required_status_checks.contexts`: `["lint", "web", "api"]`, `strict: true` (ветка должна быть актуальной относительно `main` перед merge).
- `enforce_admins`: включено, чтобы правило действовало без исключений для администраторов.
- `allow_force_pushes: false`, `allow_deletions: false`.
- Прямой push в `main` запрещается тем же правилом required PR reviews: push без PR отклоняется GitHub при включённой защите.

Названия контекстов (`lint`, `web`, `api`) должны точно совпадать с именами джобов в `ci.yml`, иначе GitHub не сможет сопоставить обязательный чек с результатом workflow.

## Risks / Trade-offs

- [Три независимые установки зависимостей увеличивают суммарное время CI по сравнению с одной инсталляцией] → pnpm-кэш через `actions/setup-node` делает повторные установки быстрыми; при росте времени можно вернуться к общему setup-джобу с артефактами.
- [Отсутствие path-based skip означает, что оба приложения проверяются даже при изменении только одного] → при текущем размере репозитория (2 небольших приложения) это не создаёт заметной задержки; пересмотр — отдельное изменение при необходимости.
- [`enforce_admins: true` может заблокировать экстренный hotfix push] → это осознанный компромисс ради соблюдения "PR с failed checks нельзя смержить" без исключений; экстренные изменения тоже идут через PR, при необходимости админ может временно снять защиту через Settings.
- [Названия job id должны совпадать со строками в required status checks] → зафиксировано явно в decision 5, чтобы не разошлось при будущих переименованиях workflow.

## Migration Plan

Изменение аддитивно: добавляется новый workflow-файл, существующий код и scripts не меняются. После мержа PR с `ci.yml` в `main` (единственный PR, который может пройти без required status checks, так как они появятся только после первого успешного запуска на этой ветке) branch protection включается отдельным шагом через `gh api`, применяемым вручную человеком с правами admin. Порядок: сначала merge workflow, затем — после успешного первого прогона на `main` — включение required status checks, чтобы GitHub успел зарегистрировать контексты `lint`/`web`/`api`. Откат — отключение branch protection в Settings и/или удаление `ci.yml`, без миграции данных.
