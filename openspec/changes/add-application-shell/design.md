## Context

См. мотивацию в `proposal.md`. В проекте уже существуют AppShell, Zustand store, modal, PrivateShell и рабочая область с деревом и хлебными крошками. PrivateLayout компонует AppShell и PrivateShell, но дерево пока находится в WorkspacePage, а шапка PrivateShell отображает логотип. Чеклист не подтверждает завершение существующей реализации: её нужно проверить вместе с новой интеграцией.

Каркас должен быть постоянным только для продуктовых маршрутов. Глобальные providers и будущие публичные экраны должны оставаться независимыми от него. Интерактивность и доступ к браузерному хранилищу требуют небольшой клиентской границы, тогда как route layouts и сами продуктовые экраны могут оставаться Server Components.

## Goals / Non-Goals

**Goals:**

- Сохранить общий каркас при переходах между продуктовыми маршрутами.
- Разделить постоянное desktop-предпочтение и временное mobile-состояние.
- Держать клиентскую границу внутри FSD-виджета, не превращая корневой layout в Client Component.
- Предоставить типизированные композиционные слоты без создания пустых продуктовых срезов.
- Реализовать проверяемую клавиатурную и screen-reader доступность.

**Non-Goals:**

- Универсальный layout-конструктор или публичный API для нескольких вариантов сайдбара.
- Новая функциональность дерева страниц, пользовательского блока и действий; существующее дерево переиспользуется.
- Серверная синхронизация предпочтений или межвкладочная синхронизация.
- Устранение любого визуального изменения между серверной разметкой и восстановлением локального предпочтения ценой блокирующего inline-скрипта.

## Decisions

### Каркас размещается в route group продуктовой части

Используется существующая приватная route group и PrivateLayout с PrivateRoute. На app-слое компонуют AppShell, PrivateShell и существующее дерево через публичные API; URL и публичные auth-маршруты сохраняются. Глобальный root layout остаётся серверным.

Это позволяет Next.js сохранять экземпляр layout при навигации внутри группы и не навязывает сайдбар будущим auth/public маршрутам. Альтернатива — поместить каркас в root layout — проще сейчас, но смешивает глобальную и продуктовую композицию и затрудняет появление экранов без сайдбара.

### AppShell является FSD-виджетом с явными слотами

Каркас размещается в `widgets/app-shell` и экспортируется через публичный API. Он принимает `children` основной области и опциональные типизированные слоты `user`, `actions`, `pageTree`. Отсутствующий слот не создаёт фиктивное содержимое.

Widget подходит, потому что компонент соединяет несколько будущих продуктовых блоков и задаёт крупную область страницы. Альтернатива — `shared/ui` — сделала бы продуктовую композицию частью инфраструктурного UI; отдельные пустые widgets для каждого слота нарушили бы правило вводить FSD-слои только вместе с поведением.

### Дерево и хлебные крошки входят в постоянную композицию

AppShell получает существующее дерево через слот `pageTree`; виджеты одного FSD-слоя не импортируют друг друга. Подготовка данных навигации и route-состояния выполняется в композиции app-слоя с существующими entities/features и TanStack Query. Zustand хранит только состояние каркаса. WorkspaceTreeExpansionProvider остаётся над деревом, чтобы раскрытие сохранялось между маршрутами.

WorkspacePage больше не создаёт самостоятельный сайдбар или мобильный оверлей; AppShell управляет обоими представлениями. Сохраняются выбор страницы, раскрытие, создание, переименование, перенос и состояния загрузки/ошибки дерева. Дерево доступно на всех приватных маршрутах, включая профиль; неизвестный маршрут не выделяет чужую страницу.

PrivateShell принимает композиционный слот хлебных крошек вместо ссылки-логотипа. Для `/` отображается «Проекты», для проекта — «Проекты / название проекта», для страницы — проект и цепочка предков с текущей страницей, для профиля — «Проекты / Профиль». Предки являются ссылками, текущий элемент имеет `aria-current="page"`. Используются существующие селекторы дерева и правила отображения пустых заголовков. При загрузке или недоступности данных показывается нейтральный контекст без устаревшего названия. Дублирующие крошки в контенте удаляются. AppShell владеет единственным `main`, внутренние экраны используют `section`/`div`.

Передача через слоты сохраняет границы FSD и постоянство layout; альтернативный отдельный сайдбар в каждом экране дублирует состояние и мобильное управление.

### Курсоры и подсказки интерактивных элементов

Доступные кнопки используют `cursor: pointer` через shared Button и локальные стили нативных кнопок; disabled/aria-disabled элементы не получают курсор действия. Проверяются каркас, шапка и перенесённое дерево, включая кнопки раскрытия и действий.

Каждый интерактивный элемент только с иконкой получает tooltip с названием действия при наведении и клавиатурном фокусе. Tooltip не заменяет `aria-label`, закрывается по Escape и не перехватывает активацию элемента. Название переключателя отражает текущее действие. Используется wrapper в shared/ui над установленным UI-стеком; одного HTML `title` недостаточно для согласованного клавиатурного поведения. Элемент с видимым текстом не требует дублирующей подсказки.

### Zustand store разделяет desktop и mobile состояния

Store внутри модели `app-shell` содержит `desktopCollapsed`, `mobileOpen` и узкие actions для их изменения. Middleware persist сохраняет только `desktopCollapsed` под версионированным ключом; `mobileOpen` всегда начинается закрытым. Ошибки storage обрабатываются с fallback на память, чтобы layout оставался доступным.

Такое разделение предотвращает открытие mobile-overlay после reload и изменение desktop-предпочтения мобильными действиями. Альтернатива с одним `open` зависит от текущего media query и создаёт неоднозначное состояние при смене ширины.

### Responsive-режим определяется CSS, а поведение оверлея изолировано

CSS/Tailwind breakpoint управляет видимостью постоянного desktop-сайдбара и mobile-trigger. Мобильный оверлей использует доступный modal/dialog primitive из уже принятого UI-стека либо минимальный wrapper над имеющимся Base UI, экспортируемый через `shared/ui`. Это обеспечивает focus trap, Escape и возврат фокуса без самостоятельной реализации сложной focus-модели.

JavaScript media-query не становится источником истины для desktop-предпочтения. При переходе к широкому режиму временный mobile-overlay закрывается, но сохранённое desktop-состояние не меняется. Альтернатива — полностью управлять layout через `matchMedia` — увеличивает риск расхождения серверной и клиентской разметки.

### Hydration использует безопасное начальное представление

Серверная разметка и первый клиентский render используют развёрнутое desktop-состояние по умолчанию; persist восстанавливает предпочтение после hydration. До восстановления интерактивные элементы не должны сообщать состояние, противоречащее показанному представлению. Возможен краткий визуальный переход к сохранённому свёрнутому состоянию.

Альтернатива с inline-скриптом до hydration уменьшает переход, но добавляет глобальный imperative-код и усложняет CSP. Для первого каркаса эта сложность не оправдана.

### Семантика является частью контракта компонентов

Сайдбар рендерится как именованный `aside`, а содержимое маршрута — как единственный `main`. Нативные `button` используют `aria-expanded`, `aria-controls` и состояние-зависимые доступные названия. Мобильный оверлей объявляется модальным, удерживает фокус, закрывается по Escape/подложке/кнопке и возвращает фокус trigger.

Тесты используют React Testing Library и доступные queries. Store-тесты проверяют partial persistence и fallback storage; компонентные тесты — слоты, desktop toggle, modal lifecycle, клавиатуру и route-change close. Responsive CSS проверяется через классы/контракт отображения, поскольку jsdom не выполняет layout.

### Зависимость принадлежит web-приложению

`zustand` добавляется непосредственно в `apps/web/package.json`, поскольку импортируется только web-приложением. Версия не выносится в workspace catalog до появления второго потребителя. Lockfile обновляется pnpm 11.21.0 под Node.js не ниже 22.13, как требует репозиторий.

API, база данных, realtime и авторизация не изменяются. Предпочтение не содержит чувствительных данных; ключ `localStorage` хранит только boolean и не является границей безопасности.

## Risks / Trade-offs

- [После hydration сайдбар может кратко сменить ширину при восстановлении сохранённого состояния] → использовать согласованное состояние по умолчанию и отключить transition до завершения hydration; не добавлять блокирующий скрипт в этом change.
- [Перенос навигации может сбросить раскрытие или продублировать main] → сохранить provider в постоянной композиции и проверить переходы и семантические области.
- [Тесты focus trap зависят от поведения modal primitive в jsdom] → проверять наблюдаемые фокус и Escape-сценарии, не внутренние детали primitive.
- [Недоступный или повреждённый `localStorage` может сорвать rehydration] → ограничить persisted shape, версионировать запись и обеспечить fallback без падения UI.
- [Содержимое будущих слотов в свёрнутом режиме пока не определено] → каркас отвечает только за контейнер и видимость; конкретные widgets позже определят компактное представление в собственных изменениях.

## Migration Plan

1. Добавить Zustand и UI-примитив мобильного оверлея в web-область.
2. Ввести store и `AppShell` с тестами.
3. Интегрировать дерево и хлебные крошки в существующий приватный layout, убрать дублирующую навигацию и вложенные main, добавить курсоры и tooltip.
4. Проверить lint, Steiger, typecheck, тесты и production build web-приложения.

Откат интеграции возвращает дерево и хлебные крошки в прежнюю композицию; миграции пользовательских или серверных данных не требуются.
