## Context

См. `proposal.md` — Why. Человеческая документация сейчас не объясняет полный lifecycle, хотя репозиторий уже содержит сгенерированные OpenSpec skills и slash-команды для четырёх agent clients. Имена команд различаются между клиентами, а OpenSpec CLI установлен вне pnpm workspace.

## Goals / Non-Goals

**Goals:**

- Дать участнику команды практический путь от идеи до merge без чтения внутренних skill-файлов.
- Разделить стабильные этапы workflow и client-specific синтаксис вызова агента.
- Согласовать human-facing документацию и корневые инструкции агента.
- Зафиксировать проверяемую версию CLI, соответствующую generated integrations в репозитории.

**Non-Goals:**

- Не обучать внутреннему формату OpenSpec CLI JSON и реализации skills.
- Не регенерировать `.codex`, `.claude`, `.cursor` или `.opencode`.
- Не менять branching conventions за пределами короткоживущей ветки и обязательного PR.
- Не изменять код приложений, данные, API, безопасность или realtime-поведение.

## Decisions

### 1. Отдельный гайд и компактная точка входа в README

Полный workflow размещается в `docs/openspec-workflow.md`, а README содержит prerequisites, краткую последовательность и ссылку. Это сохраняет README пригодным для первого запуска и позволяет развивать процесс без перегрузки основной документации. Альтернатива с полным регламентом только в README отклонена из-за объёма.

### 2. Один lifecycle и таблица client-specific команд

Гайд сначала описывает общие этапы `explore → propose → review/update → apply → validate/PR → archive`, затем сопоставляет их командам Codex, Claude Code, Cursor и OpenCode. OpenSpec CLI-команды используются для прозрачных проверок состояния, но участникам не требуется вручную воспроизводить внутреннюю работу skills.

### 3. OpenSpec CLI фиксируется на версии 1.7.0

Для установки документируется `npm install -g @fission-ai/openspec@1.7.0`, поскольку этой версией сгенерированы текущие integrations. `openspec init` не запускается повторно, а обновление CLI и generated files оформляется отдельным tooling change. Включение CLI в pnpm workspace отклонено: существующие agent commands ожидают глобально доступный бинарник `openspec`.

### 4. Human review остаётся управляющим gate

Агент помогает исследовать, создавать артефакты и реализовывать задачи, но человек утверждает planning artifacts, scope и результат. Один логический OpenSpec change ведётся в одной короткоживущей ветке и одном PR. При изменении решения сначала вызывается update workflow, и только затем продолжается реализация.

### 5. Архивирование выполняется в том же PR после review реализации

После завершения задач, проверок и human review вызывается archive workflow. Он синхронизирует delta specs при необходимости, переносит change в архив, после чего PR получает финальное одобрение и merge. Сам change `document-openspec-agent-workflow` остаётся активным после первичной реализации документации и архивируется только после её review.

### 6. Значимые документационные изменения используют OpenSpec

Изменения процесса, архитектурных решений и командных правил планируются через OpenSpec. Исправления опечаток, ссылок и небольшие уточнения могут идти напрямую через PR. Эта граница предотвращает лишние planning artifacts для механических правок, сохраняя review значимых решений.

## Risks / Trade-offs

- [Синтаксис agent commands изменится после обновления OpenSpec] → фиксировать CLI 1.7.0 и обновлять гайд вместе с generated integrations в отдельном change.
- [README и подробный гайд разойдутся] → держать в README только краткую стабильную схему и одну каноническую ссылку.
- [Архивирование добавит diff после review] → требовать финальное одобрение PR после перемещения change и возможной синхронизации specs.
- [Участник примет действия агента за автоматическое одобрение] → явно разделить обязанности человека и агента и перечислить human gates.

## Migration Plan

1. Добавить гайд, ссылку из README и согласованные правила в `AGENTS.md`.
2. Проверить команды по закоммиченным integrations, Markdown, lint и OpenSpec validation.
3. Передать документацию на human review, не архивируя change.
4. После одобрения архивировать change в том же PR, повторно проверить diff и получить финальное approval.
