## Context

Репозиторий пока содержит только рабочую конфигурацию OpenSpec и не имеет приложений, package manifest или общей системы команд. Изменение затрагивает frontend, backend и корневой tooling, поэтому технические решения нужно зафиксировать до реализации. Мотивация и границы описаны в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Получить минимальный воспроизводимый pnpm workspace, который запускается одной корневой командой.
- Установить единые обязательные проверки качества для обоих приложений.
- Оставить структуру готовой к последующему развитию принятой frontend- и backend-архитектуры без преждевременного добавления продуктовых слоёв.

**Non-Goals:**

- Не создавать shared packages, пока нет реально переиспользуемого кода.
- Не связывать web с API и не настраивать CORS или клиент для запросов.
- Не добавлять хранилища данных, фоновые задачи, realtime, авторизацию, контейнеризацию и deployment-конфигурацию.

## Decisions

### 1. Минимальный pnpm workspace без дополнительного оркестратора

Корневой `pnpm-workspace.yaml` включает только `apps/*`. Корневой `package.json` содержит `private: true`, `packageManager: pnpm@11.21.0`, требование Node.js 22 и общие scripts. `private` защищает только от случайной публикации корневого пакета в npm и не влияет на доступ к репозиторию.

Версии `typescript`, `vitest` и `@types/node`, используемых обоими приложениями, задаются в основном pnpm catalog: `^5.9.0`, `^4.0.0` и `^22.0.0` соответственно. Web и API продолжают явно объявлять эти прямые зависимости через протокол `catalog:`, поэтому каждый пакет остаётся корректным при filtered install, а политика версий управляется в одном месте. Biome остаётся корневой зависимостью, поскольку запускается только корневым script; framework-specific зависимости не переносятся в catalog, пока они не переиспользуются.

Команды `build`, `typecheck` и `test` запускаются рекурсивно через pnpm, а `dev` — параллельно для пакетов в `apps/*`. Дополнительный оркестратор вроде Turborepo пока не нужен: два независимых приложения не требуют графа кэширования и добавления ещё одного уровня конфигурации.

### 2. Раздельные приложения с общим TypeScript baseline

`apps/web` создаётся как минимальное Next.js-приложение с TypeScript, `src/app` и App Router. Tailwind, shadcn/ui и Feature Sliced Design откладываются до изменения, в котором появятся интерфейс и продуктовые модули. Стартовая страница содержит только технический заголовок, позволяющий проверить запуск.

`apps/api` создаётся как минимальное NestJS-приложение. Оно слушает порт из `PORT` с fallback на `3001` и предоставляет `GET /health`, возвращающий `{ "status": "ok" }`. Endpoint является технической проверкой доступности, не содержит бизнес-логики и не требует авторизации.

Корневой `tsconfig.base.json` задаёт общие безопасные параметры, включая strict mode. Конфигурации приложений расширяют baseline и самостоятельно задают несовместимые параметры модулей, JSX, emit и module resolution для Next.js и NestJS. Это позволяет разделять гарантии типов, не навязывая двум фреймворкам одну compiler-конфигурацию.

### 3. Единый набор корневых команд

Публичный интерфейс разработки состоит из следующих команд:

- `pnpm dev` — параллельно запускает Next.js на `http://localhost:3000` и NestJS на `http://localhost:3001`;
- `pnpm build` — собирает оба приложения и завершается ошибкой при сбое любого из них;
- `pnpm lint` — выполняет неизменяющую файлы проверку `biome check` для workspace;
- `pnpm format` — явно применяет исправления Biome и не вызывается из `lint`;
- `pnpm typecheck` — запускает `tsc --noEmit` с конфигурацией каждого приложения;
- `pnpm test` — запускает тесты обоих приложений один раз без watch mode.

Biome настраивается один раз в корне и исключает зависимости и генерируемые каталоги (`node_modules`, `.next`, `dist`, coverage). Framework-specific lint-инструменты не добавляются, чтобы `pnpm lint` имел единственный источник правил.

### 4. Vitest для обоих приложений

Web использует Vitest в окружении jsdom, React Testing Library и setup-файл с DOM matchers. Базовый тест рендерит стартовую страницу и проверяет технический заголовок.

API использует Vitest в Node environment и Nest testing utilities. Базовый тест собирает модуль контроллера и проверяет результат health endpoint. Использование одного test runner уменьшает число конфигураций; framework-default Jest не добавляется.

### 5. Воспроизводимость и документация

Lockfile коммитится в репозиторий, а версия pnpm фиксируется через поле `packageManager`. README пишется на русском языке и описывает Node.js 22, активацию pnpm через Corepack, установку, корневые команды, адреса приложений и проверку health endpoint. Имена файлов, scripts, маршрутов и программные идентификаторы остаются на английском языке.

Существующий `openspec/config.yaml` уже является корректной инициализацией OpenSpec; повторный `openspec init` не выполняется и конфигурация не перезаписывается.

### 6. Иерархия инструкций для coding agents

В репозитории создаются три англоязычных файла: корневой `AGENTS.md` и scoped-дополнения в `apps/web` и `apps/api`. Корневой файл содержит общие команды, workspace-политику, архитектурные границы, требования к качеству и OpenSpec-first workflow. Файлы приложений наследуют эти правила и добавляют только framework-specific инструкции, поэтому общие требования не дублируются и не расходятся.

Root `AGENTS.md` явно разделяет аудиторию документации: README и OpenSpec-артефакты остаются русскоязычными источниками для команды, а `AGENTS.md` служат машинно-читаемым контекстом для совместимых coding agents. Инструменты, которые не поддерживают этот формат, игнорируют Markdown-файлы; runtime и рабочий процесс разработчиков без агентов не меняются.

Web-инструкции закрепляют App Router, Server Components по умолчанию, осознанное использование `"use client"`, постепенное внедрение Feature Sliced Design и текущий Vitest/RTL-контур. API-инструкции закрепляют модульную слоистую NestJS-архитектуру, transport-only controllers, текущий health endpoint и Node-based Vitest-контур. Запланированные, но ещё не установленные продуктовые и инфраструктурные библиотеки нельзя добавлять без отдельного OpenSpec change.

В `next.config.ts` сохраняется `agentRules: false`, чтобы Next.js не генерировал и не перезаписывал вручную поддерживаемые agent-файлы. `CLAUDE.md` и другие дублирующие файлы не создаются.

## Risks / Trade-offs

- [Зависимости Next.js и NestJS требуют разных TypeScript-настроек] → Общий baseline содержит только совместимые правила, а framework-specific параметры остаются в приложениях.
- [Генерируемые файлы могут попадать под проверки Biome] → Все build-, dependency- и coverage-каталоги явно исключаются в корневой конфигурации.
- [Версии инструментов могут расходиться на разных машинах] → Node.js документируется и проверяется через `engines`, pnpm фиксируется в `packageManager`, зависимости — в lockfile.
- [Диапазоны общих инструментов могут разойтись между приложениями] → Диапазоны задаются один раз в pnpm catalog, а точные разрешённые версии фиксируются lockfile.
- [Параллельный `dev` смешивает вывод двух процессов] → pnpm запускает только фильтр `apps/*` и сохраняет префиксы пакетов в выводе.
- [Health endpoint увеличивает публичную поверхность API] → Endpoint возвращает только статический статус и не раскрывает конфигурацию или состояние будущих зависимостей.
- [Agent-инструкции могут устареть относительно конфигурации] → В них указываются только проверяемые команды и действующие ограничения; изменения toolchain должны обновлять ближайший `AGENTS.md` в том же change.

## Migration Plan

Изменение применяется аддитивно к пустому репозиторию: сначала создаётся корневая конфигурация workspace, затем приложения, тесты и документация. После установки зависимостей выполняется полный набор корневых проверок и ручной smoke test `pnpm dev`. Откат не требует миграции данных и сводится к отмене файлов этого изменения.
