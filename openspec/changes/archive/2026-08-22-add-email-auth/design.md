## Context

Мотивация — см. `proposal.md` → «Why». Требуемое поведение — см. `specs/user-authentication/spec.md`.

Существующие ограничения, формирующие подход:

- `apps/api` уже настраивает глобальный `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`) и глобальный `HttpExceptionFilter` в едином формате ошибок. Ни то, ни другое переписывать не нужно — новый модуль просто ими пользуется.
- `PrismaService` намеренно ленивый: процесс API поднимается при недоступной базе. Модуль аутентификации не должен это ломать, то есть не должен требовать соединения на этапе инициализации модулей.
- Prisma schema пуста, миграций нет. Это первая продуктовая миграция в проекте.
- Redis, BullMQ и Socket.IO в `apps/api` отсутствуют осознанно (`apps/api/AGENTS.md`).
- `openapi.json` коммитится и проверяется CI на drift; web генерирует из него типы, клиент и MSW handlers.
- Текущий CORS выставлен с `credentials: false`, и это зафиксировано требованием в `openspec/specs/api-runtime-foundation/spec.md`.
- `src/generate-openapi.ts` собирает Nest-приложение без сети и без базы. Любой новый модуль должен инстанцироваться в этом режиме.

## Goals / Non-Goals

**Goals:**

- Единственный инвариант отзыва: у цепочки ротаций не более одной действующей сессии — это то, что делает reuse detection осмысленным.
- Проверка access-токена не обращается к базе данных, поэтому защищённый маршрут не платит за аутентификацию запросом к PostgreSQL, а горизонтальное масштабирование не требует общего session store.
- Grace-период 30 секунд снимает основную практическую проблему ротации — гонки и потерянные ответы — не открывая окно для бесконечного переиспользования токена.
- Модуль тестируется без живой базы: вся работа с Prisma изолирована за узким репозиторным интерфейсом.

**Non-Goals:**

- Мгновенный отзыв access-токена. Отзыв сессии вступает в силу не позднее `ACCESS_TOKEN_TTL_S`; денилист `jti` в Redis сознательно не вводится.
- Асимметричная подпись (RS256/EdDSA) и JWKS. Пока API единственный потребитель токена, HS256 достаточно.
- Отдельные CSRF-токены на эндпоинтах с cookie — см. «Risks».

## Decisions

### 1. Access JWT + opaque refresh в базе, а не чистые серверные сессии

Выбрано: короткоживущий подписанный JWT для доступа и случайный opaque refresh-токен, строка которого материализована в PostgreSQL.

Альтернатива — единый session ID в cookie с проверкой в базе на каждом запросе — проще и даёт мгновенный отзыв, но привязывает каждый защищённый запрос к базе. Требования явно фиксируют «выдачу токена» и grace-период, что осмысленно только при ротации refresh, поэтому выбрана связка JWT + refresh.

Refresh делается opaque, а не вторым JWT: подписанный refresh не даёт ничего сверх строки в базе, но соблазняет проверять его без обращения к базе, что ломает отзыв.

### 2. Модель данных

Две новые модели в `prisma/schema.prisma`:

```prisma
model User {
  id           String    @id @default(uuid()) @db.Uuid
  email        String    @unique
  nickname     String
  passwordHash String
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt
  sessions     Session[]
}

model Session {
  id           String    @id @default(uuid()) @db.Uuid
  userId       String    @db.Uuid
  familyId     String    @db.Uuid
  tokenHash    String    @unique
  expiresAt    DateTime
  revokedAt    DateTime?
  replacedById String?   @db.Uuid
  userAgent    String?
  ip           String?
  createdAt    DateTime  @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([familyId])
  @@index([expiresAt])
}
```

- `email` хранится уже нормализованным (`trim` + нижний регистр), поэтому уникальность обеспечивает обычный `@unique`, а не функциональный индекс. Нормализация выполняется в DTO-трансформации, чтобы контроллер и сервис работали с уже каноническим значением.
- `tokenHash` — SHA-256 от refresh-токена в hex. Для случайного 256-битного секрета SHA-256 достаточно: перебор невозможен, а bcrypt здесь только замедлил бы горячий путь обновления. Уникальность `tokenHash` даёт поиск сессии одним индексным запросом.
- `familyId` — цепочка ротаций. Отдельная колонка, а не обход `replacedById` рекурсией: отзыв цепочки становится одним `UPDATE ... WHERE familyId = ?`.
- `onDelete: Cascade` закрывает требование «удаление учётной записи удаляет все её сессии».
- `userAgent` и `ip` пишутся для будущего экрана активных сессий; в текущем изменении они не читаются.

### 3. Алгоритм обновления и grace-период

Grace-период нельзя реализовать «вернуть ту же пару токенов, что и первый запрос»: в базе лежит только хеш, plaintext refresh-токена после ответа не восстановим, а класть его в базу ради 30 секунд — сознательное ослабление хранения. Поэтому grace реализован как **скользящая ротация с инвариантом единственной действующей сессии в цепочке**.

`POST /auth/refresh` с токеном `T`:

1. `S = findByTokenHash(sha256(T))`. Не найдена → `401`.
2. `S.expiresAt <= now` → `401`, очистить cookie.
3. `S.revokedAt !== null && now - S.revokedAt > 30s` → **reuse detected**: `UPDATE Session SET revokedAt = now() WHERE familyId = S.familyId AND revokedAt IS NULL`, затем `401` и очистка cookie.
4. Иначе (`S` действующая либо отозвана в пределах grace) — ротация в одной транзакции:
   - `SELECT id FROM "Session" WHERE "familyId" = $1 AND "revokedAt" IS NULL FOR UPDATE` — блокировка головы цепочки;
   - **если действующей сессии в цепочке нет — вернуть `401`, ничего не создавая**;
   - пометить найденную голову отозванной, создать новую сессию с тем же `familyId` и `expiresAt = now + REFRESH_TOKEN_TTL_S`;
   - проставить `replacedById` у головы, а также у `S`, если это разные строки и ссылка у `S` ещё пустая;
   - вернуть новую пару токенов.

Проверка на отсутствие действующей сессии обязательна и не сводится к шагу 3. Отзыв цепочки происходит по трём разным поводам — выход, выход со всех устройств и сработавшее обнаружение повторного использования, — и во всех трёх голова цепочки оказывается «только что отозванной». Без этой проверки она попадала бы в собственный grace-период и продолжала выдавать токены уже после отзыва: реализация без неё проходила все остальные тесты и падала ровно на сценарии «Действующая сессия после отзыва цепочки». Проверка обязана выполняться внутри транзакции — снаружи между ней и вставкой остаётся окно, в котором цепочку успевают отозвать.

Отсюда же следует, что grace-период применяется только к ротации: выход инвалидирует refresh-токен немедленно, а не через 30 секунд.

**Выход удаляет цепочку, а не отзывает её.** Отозванные строки читает единственный потребитель — обнаружение повторного использования, и для входа, завершённого самим пользователем, расследовать нечего: предъявление удалённого токена и предъявление отозванного одинаково дают `401`. Область — `familyId`, а не `sessionId`, и это не оптимизация, а исправление: выход по устаревшему access-токену (вторая вкладка, гонка с фоновой ротацией) отзывал бы уже отозванную строку, оставляя действующую голову цепочки живой, то есть не разлогинивал устройство. Выход со всех устройств удаляет по `userId`.

Строки, отозванные ротацией, при этом удалять нельзя ни в коем случае: именно на том, что предъявленный старый токен находится в базе и оказывается отозванным, держатся и grace-период, и обнаружение утечки. Если бы ротация удаляла предыдущую строку, украденный токен выглядел бы просто неизвестным, цепочка не отзывалась бы, и кража перестала бы детектироваться. Эти строки составляют основной объём таблицы, и разгребает их плановая очистка.

`FOR UPDATE` обязателен: без него два одновременных обновления одной цепочки прочитают одну и ту же голову и создадут две действующие сессии, после чего инвариант — а с ним и вся ценность reuse detection — теряется. Блокировка берётся по `familyId`, поэтому конкурирующие цепочки друг друга не ждут.

Свойство, которое это даёт: refresh-токен, отозванный ротацией, остаётся рабочим ровно 30 секунд — этого хватает на гонку параллельных запросов клиента и на повтор после потерянного ответа, но не хватает на отложенное использование украденного токена.

### 4. Транспорт refresh-токена и изменение контракта CORS

Refresh уходит в cookie `refresh_token` с `HttpOnly`, `Path=/api/v1/auth`, `Max-Age = REFRESH_TOKEN_TTL_S`. `SameSite` и `Secure` выводятся из `NODE_ENV`: `Lax` без `Secure` в development, `None` с `Secure` в остальных окружениях — production-развёртывание предполагает разные домены web и API, а `SameSite=None` без `Secure` браузеры отклоняют.

Это вынуждает изменить `credentials: false` на `credentials: true` в `configureApplication` и, соответственно, требование «Ограниченный CORS-доступ». Существующая проверка origin по точному совпадению с `CORS_ORIGIN` сохраняется без изменений, поэтому `Access-Control-Allow-Origin` никогда не станет wildcard — единственное сочетание, которое действительно опасно при включённых credentials.

Альтернатива — отдавать refresh в теле ответа — не требует правок CORS и bootstrap, но делает долгоживущий токен доступным клиентскому JavaScript. Отклонено.

Добавляется `cookie-parser` как глобальный middleware в `configureApplication` — рядом с остальной конфигурацией приложения, чтобы `generate-openapi.ts` и e2e-тесты собирали то же приложение, что и `bootstrap`.

### 5. Защита по умолчанию: глобальный guard + `@Public()`

`JwtAuthGuard` регистрируется как `APP_GUARD` и закрывает все маршруты. Публичные помечаются `@Public()` — декоратор поверх `SetMetadata`, читаемый через `Reflector` с `getAllAndOverride` по handler и class.

Deny-by-default выбран сознательно: забытый декоратор на новом приватном маршруте даёт `401` (заметно и безопасно), а не молчаливую утечку данных. Обратный вариант — `@Auth()` на приватных — при той же забывчивости открывает маршрут наружу.

Публичными помечаются `GET /api/v1/health`, `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`.

Guard проверяет подпись и `exp` через `passport-jwt` и **не обращается к базе данных вообще** — ни к сессиям, ни к пользователям. В `request.user` кладётся `{ id: sub, sessionId: sid }` прямо из полезной нагрузки токена; `sessionId` нужен `logout`, чтобы отозвать именно текущую сессию.

Рассматривался вариант с загрузкой пользователя по `sub` на каждом защищённом запросе — он позволял бы отклонять токены удалённых учётных записей. Отклонён: удалить учётную запись в этом изменении нечем, эндпоинта удаления нет, то есть проверка защищала бы от недостижимого состояния ценой индексного запроса к базе на каждом запросе — ровно той платы, ради ухода от которой берут JWT вместо серверных сессий. Устаревание токена относительно состояния учётной записи и так ограничено сверху `ACCESS_TOKEN_TTL_S`.

Следствие для будущих изменений: как только появится удаление учётных записей или продуктовые модели с внешним ключом на `User`, запрос с токеном несуществующего пользователя даст нарушение внешнего ключа и `500` вместо `401`. К этому моменту нужно будет либо вернуть проверку в guard, либо кешировать признак существования пользователя. Отдельного требования в спецификации на это нет — сейчас такое состояние недостижимо, и выдумывать под него поведение преждевременно.

`GET /auth/me` загружает профиль сам: это единственный маршрут изменения, которому нужны поля пользователя сверх идентификатора.

### 6. Неразличимость ответа на неверные учётные данные

`login` возвращает `401` с одинаковым сообщением `Invalid email or password` и для несуществующего email, и для неверного пароля. Этого недостаточно: если при отсутствии пользователя пропустить `bcrypt.compare`, ответ вернётся на порядок быстрее и разница во времени сама станет оракулом существования email.

Поэтому при ненайденном пользователе сервис всё равно выполняет `bcrypt.compare` против фиксированного dummy-хеша, посчитанного один раз при инициализации сервиса с текущим `BCRYPT_ROUNDS`.

Регистрация при этом отвечает `409` на занятый email — это неизбежное раскрытие, присущее любой форме регистрации без подтверждения email, и оно принято требованиями.

### 7. Конфигурация

Четыре новые переменные проходят через существующий `EnvironmentConfig` (`class-validator` + `class-transformer`) и `createApplicationConfig`, то есть отдельного механизма конфигурации не появляется:

| Переменная | Контракт | Локальное значение |
| --- | --- | --- |
| `JWT_SECRET` | строка, не короче 32 символов | значение-заглушка в `.env.example` |
| `ACCESS_TOKEN_TTL_S` | целое, 60…3600 | `900` |
| `REFRESH_TOKEN_TTL_S` | целое, 3600…7776000, строго больше `ACCESS_TOKEN_TTL_S` | `2592000` |
| `BCRYPT_ROUNDS` | целое, 4…15 | `12` |

Взаимная проверка TTL реализуется `ValidateBy` на свойстве `REFRESH_TOKEN_TTL_S`: `ValidationArguments.object` даёт доступ ко всему валидируемому объекту, поэтому второе поле видно и без валидатора уровня класса. Свойство предпочтительнее именно из-за формата ошибки — существующий сборщик сообщений печатает `${error.property}: ${constraint}`, а у класс-уровневого constraint свойства нет, и сообщение получилось бы с пустым ключом.

`BCRYPT_ROUNDS` вынесен в окружение именно ради тестов: с `12` каждый тест на регистрацию и вход стоит сотни миллисекунд, с `4` — единицы. Нижняя граница `4` совпадает с минимумом самого bcrypt.

Сообщение валидации окружения не должно печатать значение `JWT_SECRET`. Существующий формат ошибки печатает только `property: constraint`, поэтому достаточно не добавлять значение в текст constraint — но это требует внимания при формулировке сообщения.

Пароль ограничен 72 символами сверху, потому что bcrypt молча обрезает вход на 72 байтах: без явной верхней границы пользователь с длинным паролем получил бы ложное ощущение стойкости.

### 8. Плановая очистка сессий

`@nestjs/schedule` с `@Cron(CronExpression.EVERY_HOUR)`. Задача удаляет строки, где `expiresAt < now()` либо `revokedAt < now() - 7 дней`, одним `deleteMany`.

Отозванные сессии удаляются не сразу, а спустя порог хранения: строка, отозванная ротацией, ещё 30 секунд нужна для grace, а сверх того сохраняется как след для расследования сработавшего reuse detection.

BullMQ отклонён: он тянет Redis-сервис в Compose, модуль очередей и конфигурацию подключения — несоразмерно одному идемпотентному `DELETE`. Обратная сторона `@nestjs/schedule` — при нескольких инстансах API задача выполнится на каждом. Для идемпотентного удаления это безвредно; когда появится Redis, задача переедет в BullMQ без изменения наблюдаемого поведения, то есть без изменения спецификации.

Задача обёрнута в `try/catch` с логированием: недоступная база в момент запуска не должна ронять процесс. Планировщик регистрируется в `AuthModule`, а `ScheduleModule.forRoot()` — в `AppModule`.

### 9. Структура модулей

```
src/auth/
  auth.module.ts
  auth.controller.ts          // только транспорт: DTO → сервис → DTO, работа с cookie
  auth.service.ts             // регистрация, вход, выход
  session.service.ts          // выдача, ротация, grace, reuse detection, отзыв
  session.repository.ts       // единственное место, знающее про Prisma и SQL-блокировку
  session-cleanup.service.ts  // @Cron
  password.service.ts         // bcrypt, dummy-хеш
  token.service.ts            // подпись и разбор access JWT, генерация refresh
  refresh-cookie.ts           // имя, флаги, set/clear
  jwt-auth.guard.ts
  jwt.strategy.ts
  public.decorator.ts
  current-user.decorator.ts
  dto/
src/users/
  users.module.ts
  users.service.ts
```

`session.repository.ts` выделен отдельно не ради слоя как такового, а потому что ротация — единственное место в проекте с явной транзакцией и `SELECT ... FOR UPDATE`. Изоляция этого в одном файле оставляет `session.service.ts` тестируемым без базы и не даёт SQL-специфике расползтись по модулю.

`users` вынесен из `auth`, поскольку доступ к `User` понадобится будущим продуктовым модулям, а зависеть от `AuthModule` ради чтения профиля они не должны.

### 10. Стратегия тестирования

Unit-тесты Vitest рядом с исходниками, база подменяется in-memory реализацией репозитория:

- `password.service.spec.ts` — хеш не совпадает с паролем, проверка верного и неверного пароля, отклонение пароля длиннее 72 символов.
- `session.service.spec.ts` — основная нагрузка: успешная ротация; grace-повтор внутри 30 секунд; отклонение и отзыв цепочки после 30 секунд; сохранение инварианта единственной действующей сессии; изоляция других цепочек того же пользователя; истёкшая сессия. Время подменяется фейковыми таймерами, чтобы граница в 30 секунд проверялась детерминированно с обеих сторон.
- `auth.service.spec.ts` — регистрация, конфликт email, нормализация регистра, одинаковый ответ и вызов `compare` при несуществующем email.
- `session-cleanup.service.spec.ts` — удаление истёкших и давно отозванных, сохранение действующих, проглатывание ошибки базы с логированием.
- `jwt-auth.guard.spec.ts` — публичный маршрут без токена, приватный без токена, просроченный токен, подделанная подпись, а также отсутствие обращений к `PrismaService` при успешной проверке.
- `auth.controller.spec.ts` — флаги cookie на выдаче и очистке, отсутствие refresh-токена и хеша пароля в телах ответов.

HTTP-уровень через `supertest` берётся только там, где проверяется поведение самого Nest, а не сервисов: работа глобального guard на реальном маршруте и присутствие `Set-Cookie` с ожидаемыми флагами.

Живая база в unit-тестах не используется. Корректность SQL-блокировки и каскадного удаления unit-тестами не покрывается — это проверяется миграцией и ручной проверкой на локальном PostgreSQL.

## Risks / Trade-offs

- **Grace-период ослабляет reuse detection.** Атакующий, предъявивший украденный токен в пределах 30 секунд после легитимной ротации, попадает на путь обновления, а не на путь обнаружения. → Окно ограничено 30 секундами и не продлевается; инвариант единственной действующей сессии гарантирует, что после этого действующая сессия ровно одна, поэтому следующая же ротация проигравшей стороны выходит за grace и отзывает цепочку.
- **Гонка порядка ответов при параллельном обновлении.** Если два обновления идут одновременно и ответ первого приходит клиенту последним, клиент сохранит токен, отозванный секунды назад. Пока клиент обновляется чаще, чем раз в 30 секунд, это самовосстанавливается; при простое дольше 30 секунд следующий запрос будет распознан как reuse и разлогинит пользователя. → Web-клиент обязан выполнять обновление через single-flight: один общий in-flight запрос, остальные ждут его результат. Это условие для frontend-изменения, которое здесь вне scope, и его нужно зафиксировать при реализации web-части.
- **`POST /auth/refresh` уязвим к CSRF**, поскольку авторизуется cookie. → `SameSite` отсекает основной вектор, а тело ответа атакующему недоступно: CORS разрешает чтение только `CORS_ORIGIN`. Максимальный ущерб — принудительная ротация токена, не компрометация. Отдельные CSRF-токены отложены осознанно и должны появиться до первого мутирующего cookie-авторизованного маршрута.
- **`credentials: true` — необратимое ослабление CORS-контракта.** → Разрешение выдаётся только при точном совпадении origin; wildcard невозможен по построению существующей callback-проверки. Тест на запрет чужого origin должен остаться в наборе.
- **Отзыв сессии не мгновенен**: access-токен живёт до `ACCESS_TOKEN_TTL_S` после logout или отзыва цепочки. → TTL по умолчанию 15 минут; это принятая цена отказа от session store на горячем пути.
- **Гарантия «одна действующая сессия в цепочке» держится на `FOR UPDATE`.** Любая будущая правка, выносящая ротацию из транзакции или заменяющая блокировку на оптимистичную проверку, тихо ломает reuse detection, не ломая ни одного unit-теста. → Инвариант вынесен в требование спецификации и покрыт отдельным тестом на уровне сервиса; в `session.repository.ts` он должен быть закреплён комментарием.
- **Задача очистки выполняется на каждом инстансе API.** → `deleteMany` идемпотентен, параллельные запуски безопасны. Проблемой это станет только при переходе к нескольким инстансам с заметным объёмом таблицы.
- **Первая миграция в проекте.** Ошибка в ней дороже обычной правки кода. → Миграция создаётся через `prisma migrate dev`, применяется на чистой локальной базе и проверяется повторным `prisma migrate deploy`.
- **`openapi.json` и сгенерированный web-код разъедутся при незапущенной генерации.** → CI уже проверяет drift; `pnpm api:generate` входит в задачи изменения отдельным шагом.

## Migration Plan

Изменение вводится одной миграцией на пустых таблицах — данных для переноса нет.

1. `prisma migrate dev --name add-user-and-session` создаёт `User` и `Session`.
2. Развёртывание требует заполнить четыре новые переменные окружения **до** старта: без них API упадёт на валидации конфигурации. Это намеренное fail-fast поведение существующего контракта, а не регрессия.
3. Web-клиент должен начать отправлять запросы с `credentials: 'include'`, иначе refresh cookie не уйдёт на API. Frontend-часть вне scope этого изменения, поэтому до её реализации обновление токенов работает только из Swagger UI и HTTP-клиентов, сохраняющих cookie.

Откат: `prisma migrate resolve` с обратной миграцией и возврат `credentials: false`. Поскольку продуктовых данных, зависящих от `User`, ещё нет, откат безопасен.
