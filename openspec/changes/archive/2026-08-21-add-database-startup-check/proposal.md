## Why

Сейчас API устанавливает соединение с PostgreSQL лениво — при первом database operation. Если база недоступна или `DATABASE_URL` указывает не туда, разработчик узнаёт об этом только когда первый запрос к `/api/v1/health` или к данным вернёт `503`. Стартовый лог при этом выглядит полностью успешным, что маскирует проблему окружения и удлиняет цикл диагностики.

## What Changes

- API при старте выполняет однократную проверку подключения к PostgreSQL через существующий `PrismaService.checkConnection()`.
- Успешная проверка пишется в лог как подтверждение готовности базы.
- Неудачная проверка пишется в лог как предупреждение с безопасным сообщением (без `DATABASE_URL`, credentials и исходной database error) и **NOT** препятствует запуску: API продолжает подниматься и обслуживать маршруты, не зависящие от базы.
- Проверка ограничена по времени существующим `DATABASE_CONNECTION_TIMEOUT_MS` и не вводит новых переменных окружения.
- Контракт `GET /api/v1/health` не меняется: он остаётся источником истины о текущем состоянии базы.

Явно вне scope:
- fail-fast поведение (отказ запуска при недоступной базе) — сознательно отклонено, см. design.md;
- retry/backoff при стартовой проверке;
- периодические фоновые проверки подключения;
- изменения frontend и Docker Compose.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `database-runtime-foundation`: требование «Валидируемое подключение Prisma» дополняется наблюдаемой стартовой проверкой подключения; требование «Управляемый lifecycle database client» уточняется — соединение теперь пробуется при старте, а ленивое подключение остаётся поведением после неуспешной стартовой проверки.

## Impact

Затронутый код (`apps/api`):
- `src/database/prisma.service.ts` — добавление `OnModuleInit` со стартовой проверкой и логированием.
- `src/database/prisma.service.spec.ts` — покрытие успешного и неуспешного пути.

Не затронуто:
- HTTP API и OpenAPI-документ — новых или изменённых маршрутов нет.
- Конфигурация окружения — новых переменных нет, `.env.example` не меняется.
- Зависимости — используется штатный `Logger` из `@nestjs/common`.
- Frontend и инфраструктура.
