## Context

См. proposal.md — Why. Требования зафиксированы в `specs/database-runtime-foundation/spec.md`.

Текущее состояние, важное для подхода:

- `PrismaService` (`apps/api/src/database/prisma.service.ts`) уже наследует `PrismaClient`, конфигурируется через `PrismaPg` adapter с `connectionTimeoutMillis` из `ApplicationConfig` и реализует `OnModuleDestroy`.
- `PrismaService` уже имеет `checkConnection()` (`SELECT 1`), который сегодня используется только `HealthService`.
- `DatabaseModule` экспортирует `PrismaService`; `bootstrap.ts` создаёт приложение через `NestFactory.create(AppModule, { abortOnError: false })` и не знает о базе.
- Существующая спека явно требует, что недоступный PostgreSQL не препятствует запуску процесса API.

Ключевое ограничение: добавить наблюдаемость, не превращая недоступность базы в отказ запуска.

## Goals / Non-Goals

**Goals:**

- Результат подключения к базе виден в стартовом логе сразу, без внешнего запроса к `/api/v1/health`.
- Стартовая проверка ограничена по времени и не удлиняет запуск сверх настроенного connection timeout.
- Изменение локализовано в database-модуле и не расширяет публичный API `PrismaService`.

**Non-Goals:**

- Кеширование результата стартовой проверки для последующего переиспользования в `/api/v1/health`.
- Изменение сигнатуры или семантики `checkConnection()`.
- Введение отдельного модуля, провайдера или lifecycle-хука уровня приложения ради одной проверки.

## Decisions

### Решение 1: Проверка в `OnModuleInit` у `PrismaService`, а не в `bootstrap.ts`

`PrismaService` реализует `OnModuleInit` и выполняет проверку там.

Почему: сервис уже владеет lifecycle-контрактом подключения (`OnModuleDestroy`), поэтому парная инициализация остаётся в том же классе; проверка автоматически работает в любом контексте, поднимающем `DatabaseModule`, включая интеграционные тесты и `generate-openapi.ts`; `bootstrap.ts` не получает зависимости от database-слоя.

Альтернативы:
- Вызов `app.get(PrismaService).checkConnection()` в `startApplication()` — заставил бы bootstrap знать о базе и не сработал бы в контекстах, не проходящих через `startApplication`.
- Отдельный `DatabaseStartupChecker` провайдер — новая абстракция ради нескольких строк; project context требует предпочитать существующие абстракции.

### Решение 2: Предупреждение вместо отказа запуска

Неуспешная проверка логируется через `Logger.warn` и проглатывается; исключение не пробрасывается из `onModuleInit`.

Почему: `abortOnError: false` в `bootstrap.ts` означает, что проброшенное исключение из `onModuleInit` остановит инициализацию контекста, то есть де-факто даст fail-fast и нарушит действующее требование «временно недоступный сервер PostgreSQL MUST NOT препятствовать запуску процесса API». Локально база поднимается Docker Compose параллельно с API, поэтому недоступность на старте — ожидаемое переходное состояние, а не ошибка конфигурации. `/api/v1/health` остаётся авторитетным источником текущего состояния для orchestrator readiness probe.

Альтернатива — fail-fast (с retry или без) — рассмотрена и отклонена: даёт более резкий сигнал, но это BREAKING-изменение двух существующих требований и ломает сценарий частичной работоспособности API без базы.

### Решение 3: Переиспользование `checkConnection()` и существующего timeout

Стартовая проверка вызывает тот же `checkConnection()`, что и `HealthService`; ограничение по времени обеспечивается уже настроенным `connectionTimeoutMillis` у `PrismaPg` adapter.

Почему: одна проверка — один контракт, стартовый лог и health не могут разойтись в трактовке «база доступна». Новый `DATABASE_STARTUP_CHECK_TIMEOUT_MS` дублировал бы существующую настройку и потребовал бы изменений в валидации окружения и `.env.example`.

### Решение 4: Формат сообщений

Успех — `Logger.log` с фиксированным текстом о готовности базы. Неуспех — `Logger.warn` с фиксированным текстом о том, что база недоступна и подключение будет установлено при первом запросе. Исходная ошибка в сообщение не подставляется.

Почему: спека запрещает раскрывать connection URL, credentials и исходную database error; ошибки Prisma и драйвера регулярно содержат host, порт и имя пользователя, поэтому безопаснее не форматировать их вовсе, чем пытаться вычищать.

## Risks / Trade-offs

- **Стартовая проверка добавляет задержку запуска при недоступной базе** → задержка ограничена сверху `DATABASE_CONNECTION_TIMEOUT_MS`, который уже валидируется как положительное целое с верхней границей.
- **Исходная причина ошибки не попадает в лог, что усложняет диагностику** → предупреждение указывает на `/api/v1/health` и на проверку `DATABASE_URL`; детальная ошибка по-прежнему доступна при первом реальном database operation.
- **Предупреждение можно не заметить в production-логах** → стартовая проверка не заменяет readiness probe; контракт `/api/v1/health` не меняется и остаётся механизмом, на который опирается orchestrator.
- **Проверка выполняется во всех контекстах, поднимающих `DatabaseModule`, включая unit-тесты** → тесты создают `PrismaService` напрямую и вызывают lifecycle-методы явно, поэтому фоновых обращений к базе не появляется.

## Migration Plan

Миграция не требуется: изменение аддитивно, не затрагивает схему базы, конфигурацию окружения и HTTP-контракт. Откат — revert коммита.
