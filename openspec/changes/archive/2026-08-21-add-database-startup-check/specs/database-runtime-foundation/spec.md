## MODIFIED Requirements

### Requirement: Валидируемое подключение Prisma
API MUST получать PostgreSQL connection URL и ограниченный timeout установки соединения из валидируемой конфигурации. Невалидная или отсутствующая конфигурация MUST останавливать запуск с безопасной ошибкой без раскрытия credentials; временно недоступный сервер PostgreSQL MUST NOT препятствовать запуску процесса API.

При старте API MUST однократно проверять доступность PostgreSQL и сообщать её результат в серверном логе. Проверка MUST завершаться в пределах настроенного connection timeout. Сообщение о неуспешной проверке MUST быть предупреждением, MUST NOT раскрывать connection URL, credentials или исходную database error и MUST NOT прерывать запуск.

#### Scenario: Запуск с корректным URL при недоступной базе
- **WHEN** connection URL синтаксически корректен, но PostgreSQL временно недоступен
- **THEN** API запускается и продолжает обслуживать независимые от базы маршруты

#### Scenario: Невалидный database URL
- **WHEN** database URL отсутствует либо использует неподдерживаемый protocol
- **THEN** API не начинает слушать порт и сообщает только имя и безопасное описание невалидной настройки

#### Scenario: Успешная стартовая проверка подключения
- **WHEN** API запускается и PostgreSQL принимает запросы
- **THEN** серверный лог содержит подтверждение установленного подключения к базе, и запуск продолжается штатно

#### Scenario: Неуспешная стартовая проверка подключения
- **WHEN** API запускается, а стартовая проверка PostgreSQL завершается ошибкой или timeout
- **THEN** серверный лог содержит предупреждение с безопасным сообщением без connection URL, credentials и исходной database error
- **AND** API продолжает запуск, начинает слушать настроенный порт и завершает процесс с нулевым кодом при штатной остановке

### Requirement: Управляемый lifecycle database client
API MUST пробовать установить соединение с PostgreSQL один раз при старте приложения. Если стартовая попытка не удалась, API MUST устанавливать соединение лениво при первом последующем database operation. API MUST закрывать ресурсы database client через lifecycle приложения.

#### Scenario: Завершение API после использования базы
- **WHEN** приложение завершает работу после выполненной database operation
- **THEN** зарегистрированный shutdown lifecycle закрывает database client без принудительного обрыва процесса

#### Scenario: Первая database operation после неуспешной стартовой проверки
- **WHEN** стартовая проверка подключения не удалась, PostgreSQL затем становится доступен и приходит запрос, требующий базы
- **THEN** API устанавливает соединение при обработке этого запроса и отвечает без перезапуска процесса

#### Scenario: Health-проверка после успешной стартовой проверки
- **WHEN** стартовая проверка подключения прошла успешно и клиент запрашивает `GET /api/v1/health`
- **THEN** API отвечает `200` и `{ "status": "ok", "database": "up" }`, не полагаясь на закешированный результат стартовой проверки
