## Context

См. `proposal.md` для мотивации и `specs/web-trash/spec.md` для пользовательского контракта.

В backend уже есть owner-scoped чтение, restore и purge страниц/проектов. `Page.deletedOrigin` различает самостоятельно удалённые страницы, удалённые предком и удалённые проектом. `DeletedPageTreeNodeDto` содержит `parentPageId` и `children`, но не раскрывает `deletedOrigin`; `PagesService.findDeletedTree` формирует отображаемое дерево с учётом происхождения удаления. Самостоятельно удалённый узел может поэтому быть отдельным корнем ответа, даже если его физический `parentPageId` указывает на удалённую страницу. Не выводить `deletedOrigin` из `parentPageId` и не расширять DTO ради UI.

Каждый узел ответа можно адресовать существующими restore и purge endpoints. Restore выбранного узла восстанавливает его и физические потомки, удалённые вместе с ним, оставляя потомков с `deletedOrigin=SELF` в корзине. Если прежний родитель выбранного узла остаётся удалённым, узел восстанавливается корнем активного проекта. Purge узла физически удаляет его поддерево по FK cascade; самостоятельные удалённые страницы внутри него требуют отдельного `cascade=true` подтверждения. Родитель, соседние ветви и элементы вне поддерева выбранного узла не затрагиваются.

Существующие тесты `trash.integration-spec.ts` проверяют, что purge вложенной ветви сохраняет её родителя и соседнюю ветвь, и что purge выбранного проекта удаляет его страницы. Проектный purge тест не содержит отдельного project sentinel; перед реализацией задача 1.1 должна подтвердить достаточность имеющихся тестов и фактической owner-scoped реализации для изоляции других проектов. Backend tests в рамках этого change не добавляются.

Сгенерированные hooks существуют в `shared/api/generated`, но не все операции корзины экспортированы через публичный `shared/api`. UI soft delete в дереве и подтверждение уже реализованы; корзины и маршрута `/trash` нет. Route-группа `(private)` использует общий приватный layout и защищает все вложенные страницы.

Текущий collaboration lifecycle проверяет живость страницы при записи документа. Отказ сохранения удалённой страницы закрывает комнату; отдельного события немедленного закрытия при soft delete нет.

## Goals / Non-Goals

**Goals:**

- Добавить интерфейс корзины поверх уже существующих API и единообразно обновлять server state после операций.
- Сохранить осознанное двухэтапное подтверждение необратимого cascade purge.
- Зафиксировать поведение для удалённых проектов, независимо удалённых потомков и подключённых редакторов.

**Non-Goals:**

- Изменения backend, Prisma schema, migrations, API lifecycle и permissions не входят в scope данного change.
- Массовая очистка корзин, немедленная рассылка realtime-события при soft delete, Yjs snapshot restore, assets, publication, search, расписание очистки, поиск в корзине, bulk selection или drag-and-drop.
- Глобальное состояние вкладки; выбранная вкладка остаётся локальным состоянием экрана.

## Decisions

### Маршрут и FSD-границы

- Разместить тонкий Next.js route `/trash` в существующей приватной route-группе. Route импортирует публичный API screen slice и не содержит логики.
- Добавить экран в `pages/trash`; взаимодействия корзины разместить в `features/trash-management`; переиспользуемые wrappers брать из `shared/ui`. Новые entity или универсальные CRUD abstractions не вводить.
- Ссылку добавить в существующий sidebar через его область действий. Существующая навигация и mobile sidebar должны вести на один маршрут; route остаётся в общем private shell.
- Использовать доступные tab controls, семантические списки/деревья и focus-visible управление. На узких экранах действия остаются доступны без горизонтального переполнения.

### API и загрузка данных

- Использовать существующие generated операции: `GET /api/v1/pages/trash`, `GET /api/v1/projects/trash`, `POST /api/v1/pages/{pageId}/restore`, `POST /api/v1/projects/{projectId}/restore`, `DELETE` для индивидуального purge страницы или проекта.
- Экспортировать нужные уже сгенерированные hooks, query keys, DTO и error types через `shared/api`; не писать второй fetch client и не редактировать generated output вручную.
- Вкладка страниц использует дерево корзины, активные проекты и выдачу удалённых проектов для сопоставления `projectId → name`. Вкладка проектов использует project trash query. Неизвестное имя проекта показывает безопасный fallback, не скрывая страницу.
- Запросы вкладок имеют независимые loading/error/empty состояния. Мутации показывают pending/error локально у соответствующего действия; server state остаётся в TanStack Query.

### Восстановление и cache consistency

- Для каждого узла дерева показывать restore и permanent-delete actions. При restore выбранного узла backend восстанавливает только узел и его потомков, не помеченных как самостоятельно удалённые; независимо удалённые потомки остаются отдельными элементами корзины. Если прежний родитель остаётся удалённым, API восстанавливает выбранный узел как корень активного проекта.
- Если исходный проект страницы присутствует среди удалённых, до запроса открыть выбор одного из активных проектов. Передавать его как `projectId`. Если активных проектов нет, не отправлять restore, объяснить, что нужен активный проект, и оставить страницу в корзине.
- После успеха инвалидировать обе корзины, page tree и project list. Для конкурирующих изменений или ошибки дополнительно перечитать актуальные данные; не оптимистично убирать элемент до успешного ответа.
- После удаления страницы, открытой у текущего пользователя, использовать существующую replace-navigation/cleanup orchestration workspace при необходимости; не дублировать этот lifecycle в route-компоненте.

### Purge и информированное подтверждение

- Перед индивидуальным irreversible purge открыть подтверждение с типом и названием выбранного элемента, предупредив о физическом удалении выбранного поддерева страницы либо содержимого выбранного проекта.
- Для индивидуального page/project purge сначала отправить запрос без `cascade=true`. Сгенерированный API error принимать как подтверждение каскада только при `error.status === 409` и валидном `error.info.message`: массив минимум из двух строк, все элементы — строки, первая строка непустая и служебная, остальные — названия затрагиваемых страниц (пустое название страницы допустимо). Показывать служебное пояснение отдельно от названий. Если статус или структура не распознаны, показать обычную ошибку, обновить состояние и не отправлять `cascade=true`.
- Только submit отдельного второго подтверждения может повторить ту же индивидуальную операцию с `cascade=true`. Закрытие/отмена второго подтверждения оставляет элемент в корзине и не отправляет повторный запрос.
- Не считать `cascade=true` подтверждением на клиенте само по себе: параметр допустим только из обработчика второго явно принятого диалога. При закрытии диалога запрос не отправляется.
- При purge выбранной страницы уничтожается выбранный узел и его физическое поддерево; список SELF-потомков из распознанного `409` уточняет дополнительный каскадный охват. При purge проекта затрагивается выбранный проект и страницы, которые он содержит; операция адресуется фиксированным ID. После individual purge обновлять обе корзины, дерево и список проектов. Повторные запросы блокируются локально на время pending; при устаревшем ID/404 перечитать состояние и показать ошибку, не выдавая успех.

### Owner permissions и collaboration

- Не выводить чужие shared pages в корзину: owner-scoped API — источник истины. Для viewer/editor не добавлять клиентский обход или новые permission rules.
- Для редакторов Hocuspocus сохраняется существующая гарантия: запись удалённой страницы отклоняется, а комната закрывается при отказе persistence. Интерфейс не обещает немедленное закрытие соединений и не вводит новый realtime-сигнал в этот change.
- API, owner-scoped permissions, CQRS/use-case architecture и Yjs/Hocuspocus lifecycle остаются без изменений. Используются только существующие endpoints, DTO и generated API operations; OpenAPI contract не обновляется.

### Проверка

- UI behavior проверять Vitest + React Testing Library через доступные роли/имена, MSW handlers и существующие generated operations.
- Проверить действия на каждом узле, selective subtree restore, оставшийся в корзине удалённый родитель, сохранение SELF-потомков, охват purge поддерева, project-name fallbacks, cache invalidation, pending/error и корректный/некорректный `409`.
- На этапе аудита сверить существующие backend tests для selective subtree restore/purge и owner-only доступа. В частности, подтвердить тестами, что individual page purge ограничен выбранной ветвью, а project purge — выбранным проектом и его страницами. В рамках этого change не добавлять backend tests и не менять backend; если существующие tests или код обнаруживают критический дефект либо не подтверждают изоляцию операции, отметить соответствующий сценарий как blocker и сообщить о нём.
- Финальная проверка включает lint, typecheck, tests, build и ручные основные браузерные потоки. API/OpenAPI generation в scope не входит: используются существующие contracts и generated client.

## Risks / Trade-offs

- **[Trade-off]** Существующие endpoints массовой очистки проектов выбирают динамический набор проектов на момент вызова; между `409` и retry с `cascade=true` состав корзины может измениться. → Массовая очистка обеих корзин полностью исключена из MVP и UI; её возможное включение требует отдельного планирования безопасного подтверждения охвата.
- **[Ограничение]** Индивидуальный purge повторно адресует фиксированный page/project ID. До реализации необходимо подтвердить существующими backend tests и аудитом use cases, что каскад ограничен выбранной страницей и её физическим поддеревом либо выбранным проектом и его содержимым. Конкурентный restore/удаление может изменить состояние или привести к `404`; UI показывает ошибку и обновляет данные, не выдавая ложный успех. Backend locks не считаются межзапросной блокировкой.
- **[Риск]** `409` с отсутствующим или неверно сформированным `info.message` нельзя безопасно показать как подтверждение. → Валидировать status и массив строк, отделять первую служебную строку от имён и не переходить к `cascade=true` при любой ошибке формата.
- **[Риск]** Подключённые Yjs редакторы могут получить отказ не одновременно с soft delete. → Сохранение после удаления не проходит; room закрывается при отказе persistence. Немедленное уведомление остаётся вне MVP.
- **[Риск]** Новые будущие сущности (assets/publications/search) могут иметь отдельный retention lifecycle. → UI не кодирует FK/cascade-предположений и в рамках MVP не меняет эти подсистемы; их физическая очистка должна планироваться в соответствующих lifecycle changes.

## Migration Plan

Backend/API rollout и миграция БД не нужны. Web change использует текущий API contract и generated client. При проблеме UI можно откатить без изменения сохранённых данных.
