## Context

См. `proposal.md` — Why.

Ограничения, которые формируют решение:

- Проверки, обязанные видеть то же состояние, что и запись, выполняются под `pg_advisory_xact_lock` внутри транзакции. Вынести их наружу нельзя ни при какой раскладке слоёв — можно только перенести вместе с границей транзакции.
- Ключ `hashtext(ownerId)` сериализует все пишущие операции владельца между собой: создание, перемещение, мягкое удаление, восстановление и окончательное удаление страниц и проектов. Это единственное, что не даёт перемещению вставить живое поддерево под страницу, которую в этот момент помечает удаление.
- Prisma различает клиент пула и клиент транзакции. Запрос, выполненный на клиенте пула внутри `$transaction`, уходит на другое соединение: не видит незакоммиченного, не покрыт локом, не откатывается — и при этом не падает.
- In-memory репозитории обслуживают весь HTTP-слой тестов через `testing/http-application.ts`; `apps/api/AGENTS.md` запрещает юнит-тестам ходить в живую базу. Удалить двойники нельзя.
- `PagesModule` импортирует `ProjectsModule`, обратный импорт дал бы цикл. `PageDocumentModule` импортировал `PagesModule` ради одной проверки владельца — см. решение 7.

## Goals / Non-Goals

**Goals:**

- Ни одного `if … throw` доменной ошибки в репозиториях, включая in-memory.
- Ни одного обращения к чужой таблице из репозитория модуля.
- Ни одной проверки, выехавшей из-под лока: всё, что сегодня выполняется внутри транзакции, продолжает выполняться внутри неё.
- Блокировок ровно столько, сколько нужно: лишняя не даёт защиты, но выглядит как защита.
- Двойная валидация при создании страницы устранена.

**Non-Goals:**

- Единый стиль для всех модулей: `auth` остаётся как есть — он подпадает под критерий «транзакция без решений».
- Отказ от абстрактных портов и in-memory двойников.
- Полный Unit of Work по Фаулеру: identity map и отложенная запись не вводятся — Prisma пишет немедленно, накапливать нечего.
- Приведение `TrashCleanupRepository` к тому же правилу: он тоже чистит обе таблицы, но это запланированная очистка по сроку хранения, а не операция агрегата.

## Decisions

### 1. Границу транзакции держит use-case класс

Транзакцию открывает юзкейс, а не репозиторий. Всё, что было причиной утечки, снимается сразу: проверки идут внутри транзакции и под локом, потому что весь юзкейс — внутри транзакции.

Альтернатива — оставить транзакции в репозитории и вынести только «чистые» правила. Отвергнута: правил, которые можно вынести, не читая состояние под локом, в этом коде почти нет, а те, что остались бы, разорвали бы одно правило на две половины в разных слоях.

### 2. Шов проходит по линии «запрос/команда против решения», а не «SQL против TypeScript»

Рекурсивные CTE остаются в репозитории. Переписать обход поддерева построчным циклом в приложении значило бы обменять корректность и стоимость запроса на формальную чистоту слоя.

| Что | Куда | Пример |
| --- | --- | --- |
| Запрос, возвращающий факт | Repository | `findSelfDeletedDescendantTitles(id)` |
| Команда, меняющая множество строк | Repository | `markSubtreeDeleted(id, ownerId, at)` |
| Примитив согласованности | TransactionScope | `lock(ownerLock(ownerId))` |
| Решение — `if … throw` | Use case | `if (doomed.length > 0 && !cascade) throw …` |
| Вычисление домена | Use case | `positionBetween(previous, next)` |

Метод репозитория, содержащий и запрос, и решение, разваливается на две части: запрос остаётся, решение поднимается.

### 3. `TransactionRunner` и `TransactionScope`, а не `UnitOfWork`

```
database/transaction.ts
  DatabaseClient          = Prisma.TransactionClient    // покрывает и пул, и транзакцию
  LockKey                 = { value }
  TransactionScope        // интерфейс: lock(key)
  PrismaTransactionScope  // + client
  TransactionRunner       // run(operation) -> $transaction(tx => operation(scope))
```

`PrismaService extends PrismaClient`, а `Prisma.TransactionClient` — тот же клиент без `$transaction`. Поэтому один тип `DatabaseClient` покрывает оба случая, и в сигнатурах методов репозитория не появляется лишних параметров.

Имя `UnitOfWork` отвергнуто: оно обещает change tracking и `flush()`, которых не будет.

Публичный `TransactionScope` объявляет только `lock`; `client` живёт в `PrismaTransactionScope`. Prisma-репозиторий сужает тип через `instanceof` и отказывает с явной ошибкой на чужом скоупе — `any` и широкие приведения запрещены `AGENTS.md`.

### 4. Блокировка одна: владелец

`hashtext(ownerId)` берут все десять юзкейсов, и он сериализует пишущие операции владельца между собой. Уровневая блокировка `(projectId, parentPageId)`, которая была в исходном коде, мельче: две транзакции не могут оказаться внутри неё одновременно, потому что обе сначала упрутся в блокировку владельца. Защиты она не добавляла, а round-trip на каждое создание, перемещение и восстановление — да.

Проверено мутациями на живой базе:

| конфигурация | результат |
| --- | --- |
| owner + level | всё зелёное |
| только owner | всё зелёное |
| только level, у `create` | падает гонка с удалением родителя и проекта |
| только level, у `move` | падает гонка с удалением будущего родителя |
| только level, у `restore` | падает гонка с удалением проекта |
| без обоих, у `create` | падают три теста на дубли рангов |

Гонки `move` и `restore` тестами не покрывались — их пришлось написать, иначе снятие блокировки владельца у этих двух операций осталось бы зелёным.

Обратный ход — оставить уровневую и снять владельца ради параллелизма разных веток дерева — закрыт последними тремя строками таблицы: удаление проекта не знает, какие уровни затронет, и уровневым ключом эта гонка не выражается.

Ранги классов и проверка их порядка сняты вместе с уровневой блокировкой: при одном классе упорядочивать нечего. `LockKey` остаётся объектом, а не строкой, чтобы ключ по-прежнему нельзя было собрать на месте мимо `ownerLock`.

### 5. Юзкейс зависит от репозиториев, а не от чужих сервисов

Репозиторий хранит `client: DatabaseClient` и получает метод `bind(scope)`, возвращающий **новый экземпляр**, а не мутирующий текущий. Провайдер Nest — синглтон, один на приложение; мутация `this.client` привела бы к тому, что транзакция одного запроса выполняла бы запросы другого при первом же `await`.

Через `bind` юзкейс работает и со своими репозиториями, и с чужими: `CreatePageUseCase` зовёт `ProjectsRepository` и `PageDocumentRepository`, проектные юзкейсы — `PagesRepository`. Сервис-прослойки между ними нет: решения принимает юзкейс, а сервису в этой цепочке нечего добавить, кроме лишнего слоя.

Репозиторий остаётся в модуле своего агрегата и экспортируется наружу. Взаимная нужда `pages` и `projects` даёт цикл модулей, и он разрешается `forwardRef`:

```
PagesModule ──forwardRef──▶ ProjectsModule ──forwardRef──▶ PagesModule
     │
     └──▶ PageDocumentModule (зависит только от DatabaseModule)
```

Цикл настоящий, а не мнимый: без `forwardRef` Nest отказывается создавать `ProjectsModule` — «The module at index [1] of the imports array is undefined». Проверено снятием `forwardRef`.

Альтернатива — вынести `PagesRepository` в модуль без зависимостей, который импортируют оба, — отвергнута: репозиторий уехал бы из модуля своего агрегата, а раскладка стала бы асимметричной, потому что такой модуль понадобился бы только страницам.

Альтернатива — ходить в чужой модуль через его сервис — отвергнута: она требует, чтобы сервисы не зависели друг от друга, а `CreatePageUseCase` и `SoftDeleteProjectUseCase` нужны друг другу в обе стороны. Раньше это лечилось параметром `scope: TransactionScope | null` на публичных методах сервиса; теперь этого параметра нет нигде — скоуп передаётся только в `bind`.

Альтернатива «раздавать репозитории из общего runner-а» отвергнута отдельно: runner пришлось бы импортировать репозитории всех модулей и править при каждом новом.

### 6. Критерий появления юзкейса

Юзкейс заводится там, где есть транзакция **и** хотя бы одно решение внутри неё. Один публичный метод `execute`, приватный модулю, в каталоге `use-cases/`.

Остальное остаётся в сервисе: сборка дерева и корзины, `findById`, `rename`, `requireOwnedPage`. Сервис сохраняет роль публичного лица модуля — `exports` у `PagesModule` и `ProjectsModule` не меняются.

Без этого критерия рефакторинг вырождается в юзкейс на каждый маршрут и четвёртый слой без выгоды.

### 7. Пустой документ создаёт `CreatePageUseCase` через `PageDocumentRepository`

Связь «страница — документ» 1..1 с первой строки, поэтому обе вставки идут одной транзакцией. Но вторая из них — чужая таблица, и оставлять её в `PagesRepository` значило бы сохранить ровно то нарушение границы модуля, ради которого затеяно изменение.

Цикл модулей, мешавший этому, держался на одной зависимости: `PageDocumentService` звал `PagesService.findById` ради проверки «страница жива и моя». Проверка переехала в условие самого запроса через связь с `Page`:

```
where: { pageId, page: { deletedAt: null, ownerId } }
```

Половина условия там уже была — `replace` фильтровал `page: { deletedAt: null }`. После переноса `PageDocumentModule` не зависит ни от чего, кроме `DatabaseModule`, и экспортирует свой репозиторий; `CreatePageUseCase` вставляет документ через `documents.bind(scope).insertEmpty(...)`.

Побочный выигрыш: `read` и `replace` перестают делать отдельный запрос страницы — права и живость спрашивает один запрос вместо двух.

### 8. In-memory двойники сохраняются и худеют

Порты остаются абстрактными, `bind(scope)` у in-memory возвращает `this`. Добавляется `InMemoryTransactionRunner`: `run(operation)` вызывает операцию со скоупом, у которого `lock` — no-op. Однопоточность JavaScript уже сериализует операции, а роль лока в Prisma-версии — не дать двум транзакциям увидеть состояние до чужой записи.

Двойники теряют доменные ошибки и правила, сохраняя эмуляцию хранилища: обход поддерева, фильтр удалённых, изоляцию по владельцу.

### 9. Стратегия тестирования

| Уровень | Что проверяет | Что происходит с ним |
| --- | --- | --- |
| Юнит-тесты юзкейсов | решения и порядок вызовов; репозиторий — `vi.fn()` | новые |
| Юнит-тесты сервисов | сборка дерева и корзины, простые чтения | сокращаются до оставшегося в сервисе |
| HTTP-тесты | контракт на настоящем стеке Nest поверх двойников | не меняются |
| Интеграционные тесты | гонки, локи, CTE на живой базе | вызовы переезжают вслед за операцией, утверждения сохраняются дословно |

Интеграционные тесты драйвят репозиторий напрямую, а не проходят через устойчивый шов, поэтому пережить перенос операций без правок они не могут. Каждый остаётся на том уровне, который на самом деле проверяет:

| Файл | Что проверяет | Куда переезжает |
| --- | --- | --- |
| `create-concurrency` | параллельная вставка не даёт одинаковых рангов | на `CreatePageUseCase` — локи теперь берёт он |
| `create-under-deleted` | гонка создания с удалением родителя и проекта | на юзкейсы страниц и проектов |
| `create-atomicity` | страница и документ появляются одной транзакцией | новый: двойник отката не воспроизводит |
| `trash` | рекурсивные CTE, значения enum, FK-каскады | остаётся на репозитории с переименованными вызовами; утверждения об отказах переезжают на юзкейсы вместе с решениями |
| `position-collation` | collation колонки `position` | не затрагивается: работает сырым `pg`-клиентом |
| `trash-cleanup` | запланированная очистка по сроку хранения | не затрагивается |

Страховкой при этом остаются утверждения, а не файлы: ни одно `expect` и ни один сценарий не меняются, правятся только вызовы переехавших операций. Изменённое утверждение в интеграционном тесте — стоп-сигнал для ревью.

Тест гонки опаснее прочих: после переноса локов в юзкейс `create-concurrency` продолжил бы компилироваться и зеленеть, вызывая вставку без блокировок, то есть перестал бы проверять названное. Поэтому его перевод — часть той же задачи, что и перенос операции, а не отдельная уборка.

## Risks / Trade-offs

- **Потеря дисциплины локов при размазывании по юзкейсам** → блокировка одна, ключ строится только `ownerLock`, и каждая операция, которая её берёт, покрыта тестом гонки на живой базе.
- **Молчаливая регрессия семантики гонок** → интеграционный тест гонки переводится на юзкейс той же задачей, что переносит операцию; утверждения в интеграционных тестах не правятся, и изменённое `expect` — стоп-сигнал для ревью.
- **Забытый `scope` уводит запрос мимо транзакции** → параметр обязателен (`TransactionScope | null`), проверка типом.
- **Утечка транзакции между параллельными запросами** → `bind` возвращает новый экземпляр; мутация `this.client` запрещена явно.
- **`TrashCleanupRepository` чистит обе таблицы напрямую** → правило «репозиторий трогает только свою таблицу» там не выполняется. Модуль запускается по расписанию, агрегатов не знает и в предмет этого изменения не входит; приводить его к правилу — отдельное изменение.
- **Двойник расходится с Prisma-реализацией в эмуляции хранилища** → не устраняется этим изменением, только сужается. Правила уходят в юзкейсы, у которых одна реализация и один набор тестов, поэтому расхождение остаётся возможным лишь в обходе поддерева, фильтре удалённых и изоляции по владельцу. Закрыть его полностью можно контрактным набором сценариев, запускаемым и против `PrismaPagesRepository` на живой базе, и против двойника; это стало осуществимо именно после сужения контракта репозитория, но выносится за рамки изменения. Подмена на уровне ORM-клиента вместо репозитория рассмотрена и отвергнута: пять рекурсивных CTE в `pages` и четыре raw-запроса в `projects` пришлось бы либо сопоставлять по тексту SQL, либо заменять заготовленными ответами — дублирование не исчезло бы, а переехало за match по строке запроса.
- **Крупный Pull Request** → задачи разбиты по одной операции; интеграционные и HTTP-тесты обязаны быть зелёными после каждой.
- **Рост числа файлов** → десять юзкейсов вместо двух сервисов. Принято сознательно: критерий из решения 6 удерживает их число от разрастания.

## Migration Plan

Одно изменение, один Pull Request, порядок задач:

1. Инфраструктура: `transaction.ts`, `transaction.in-memory.ts`, ранги и построители ключей, регистрация в `DatabaseModule` и в `testing/http-application.ts`. Поведение не меняется, тесты зелёные.
2. `projects`: четыре юзкейса, утоньшение репозитория и двойника. Тесты зелёные.
3. `pages`: шесть юзкейсов по одному за раз, утоньшение репозитория и двойника. Тесты зелёные после каждого.
4. Очистка: удаление осиротевших приватных методов, сверка критериев из Goals грепом.

Схема базы, миграции, HTTP-контракт и `openapi.json` не затрагиваются, поэтому откат — обычный revert Pull Request без обратной миграции.

## Open Questions

- Нужна ли `TransactionRunner` политика повторов при отказе сериализации. Сегодня изоляция `READ COMMITTED` и advisory-локи, отказов сериализации не ожидается. Ответ не меняет ни спецификацию, ни подход, ни раскладку задач: политика добавляется в один метод `run` позже, если появятся операции с более строгим уровнем изоляции.
