## ADDED Requirements

### Requirement: Отказ называет неподошедший идентификатор
Тело запроса перемещения несёт до четырёх идентификаторов страниц: перемещаемую, родителя, предыдущего и следующего соседа. Отказ `404` MUST называть, какой именно из них не найден, а не сообщать об этом одинаково для всех.

Отказ `400` о соседе, лежащем не под целевым родителем, MUST называть, какой из двух соседей не подошёл.

Создание страницы MUST отличать отказ о родителе от отказа о проекте.

Различимость MUST ограничиваться идентификатором из запроса: для каждого из них чужая, удалённая и несуществующая запись MUST оставаться неразличимыми между собой. Различается место в запросе, а не судьба записи, поэтому оракулом существования чужих страниц отказ не становится.

#### Scenario: Ненайденные родитель и сосед различимы между собой
- **GIVEN** пользователь перемещает свою страницу
- **WHEN** он указывает несуществующий идентификатор родителя, а затем — несуществующий идентификатор предыдущего соседа
- **THEN** оба ответа имеют статус `404`, но тела различаются
- **AND** тело первого называет родителя, а тело второго — `previousSiblingId`

#### Scenario: Ненайденные предыдущий и следующий соседи различимы между собой
- **WHEN** пользователь указывает несуществующий идентификатор в `previousSiblingId`, а затем тот же идентификатор в `nextSiblingId`
- **THEN** оба ответа имеют статус `404`, и тела различаются

#### Scenario: Чужая и несуществующая запись неразличимы в пределах одного идентификатора
- **WHEN** пользователь указывает родителем чужую страницу, а затем — идентификатор, которому не соответствует ни одна страница
- **THEN** оба ответа имеют одинаковый статус `404` и одинаковое тело
- **AND** то же верно для `previousSiblingId` и для `nextSiblingId`

#### Scenario: Отказ о соседе не под целевым родителем называет соседа
- **GIVEN** существует страница, лежащая под другим родителем
- **WHEN** пользователь указывает её в `previousSiblingId`, а затем в `nextSiblingId`
- **THEN** оба ответа имеют статус `400`, и тела различаются

#### Scenario: Отказ о родителе при создании отличается от отказа о проекте
- **WHEN** пользователь создаёт страницу с несуществующим `projectId`, а затем — с живым проектом и несуществующим `parentPageId`
- **THEN** оба ответа имеют статус `404`, и тела различаются

## MODIFIED Requirements

### Requirement: Очистка корзины страниц
API MUST публиковать защищённый `DELETE /api/v1/pages/trash`, безвозвратно удаляющий из хранилища всё, что возвращает чтение корзины страниц того же пользователя, вместе с поддеревьями и документами.

Очистка MUST затрагивать только записи текущего пользователя и MUST NOT затрагивать неудалённые страницы. Страницы удалённых проектов MUST удаляться наравне с остальными: корзина страниц показывает их, а очистка удаляет ровно то, что показывает парное ей чтение. Сами проекты при этом MUST оставаться в корзине проектов и MUST оставаться восстановимыми — восстановленный проект MUST возвращаться пустым, если все его страницы были очищены.

Очистка MUST быть идемпотентной: вызов на пустой корзине MUST отвечать успехом, а не ошибкой. Успешная очистка MUST отвечать `204` без тела.

Очистка MUST выполняться в одной транзакции: при отказе на любом шаге ни одна страница MUST NOT исчезнуть из хранилища. Очистка MUST быть согласована с остальными операциями того же владельца: она MUST NOT удалять страницу, которую параллельный запрос восстановил, и MUST NOT оставлять в хранилище страницу, которую параллельный запрос удалил до начала очистки.

#### Scenario: Очистка непустой корзины
- **GIVEN** пользователь удалил несколько страниц с потомками
- **WHEN** он отправляет `DELETE /api/v1/pages/trash`
- **THEN** API отвечает `204`, и последующее чтение корзины возвращает пустой список
- **AND** ни одна из этих страниц и ни один их документ не остаются в хранилище

#### Scenario: Очистка не трогает живое дерево
- **WHEN** пользователь очищает корзину страниц
- **THEN** чтение дерева возвращает то же дерево, что и до очистки

#### Scenario: Очистка уносит и страницы удалённого проекта
- **GIVEN** пользователь удалил проект со страницами
- **WHEN** он очищает корзину страниц
- **THEN** страницы этого проекта исчезают из хранилища
- **AND** сам проект остаётся в списке удалённых проектов, а его восстановление отвечает `200` и возвращает проект без страниц

#### Scenario: Очистка не трогает чужую корзину
- **WHEN** пользователь очищает свою корзину страниц
- **THEN** удалённые страницы других пользователей остаются в хранилище

#### Scenario: Очистка пустой корзины
- **WHEN** пользователь, не удаливший ни одной страницы, отправляет `DELETE /api/v1/pages/trash`
- **THEN** API отвечает `204` и ничего не изменяет

#### Scenario: Отказ в середине очистки не оставляет частичного результата
- **GIVEN** пользователь удалил несколько страниц с потомками
- **WHEN** очистка отказывает на одном из шагов
- **THEN** чтение корзины возвращает тот же список, что и до запроса
- **AND** ни одна страница и ни один документ не исчезают из хранилища

#### Scenario: Очистка и мягкое удаление не пересекаются
- **GIVEN** пользователь отправляет очистку корзины и мягкое удаление живой страницы одновременно
- **WHEN** обе операции завершаются успехом
- **THEN** страница либо остаётся в корзине целиком, либо отсутствует в хранилище целиком вместе со своим поддеревом
- **AND** в хранилище не остаётся страницы, помеченной удалённой, но лишённой части своего поддерева

#### Scenario: Очистка корзины без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и ничего не удаляет
