## Purpose

Определяет доступные пользователю web-сценарии создания учётной записи, входа, восстановления и завершения сессии, защиты приватных экранов и просмотра текущего профиля.

## ADDED Requirements

### Requirement: Регистрация и вход через web
Web MUST предоставлять отдельные публичные формы регистрации и входа, выполнять клиентскую валидацию до запроса и использовать существующий типизированный API-контракт. Регистрация MUST принимать имя, email, пароль и подтверждение пароля; подтверждение MUST использоваться только клиентом и не отправляться в API. Ошибки MUST быть безопасными и не раскрывать технические детали ответа.

#### Scenario: Успешная регистрация
- **WHEN** гость вводит допустимые имя, email, пароль и совпадающее подтверждение
- **THEN** web создаёт учётную запись, считает пользователя аутентифицированным и открывает запрошенный приватный экран либо главную

#### Scenario: Клиентская ошибка регистрации
- **WHEN** имя пусто, email некорректен, пароли не совпадают либо пароль короче 8 символов или длиннее 72 UTF-8 байт
- **THEN** web показывает ошибку у соответствующего поля и не отправляет API-запрос

#### Scenario: Занятый email
- **WHEN** API отклоняет регистрацию со статусом `409`
- **THEN** web показывает понятное сообщение о существующем аккаунте без вывода сырого тела ошибки

#### Scenario: Неверные данные входа
- **WHEN** API отклоняет вход со статусом `401`
- **THEN** web показывает одинаковое сообщение о неверном email или пароле независимо от причины отказа

### Requirement: Восстановление и жизненный цикл сессии
Web MUST при запуске попытаться восстановить сессию по HttpOnly refresh cookie, затем загрузить текущего пользователя. Во время восстановления MUST отображаться loading state; отсутствие действительной refresh cookie MUST считаться unauthenticated состоянием, а network или server failure MUST показывать recoverable error с повтором.

Access-токен MUST храниться только в памяти browser runtime. Пароли, access-токены и refresh-токены MUST NOT сохраняться в persistent storage, глобальном UI state, TanStack Query mutation cache или клиентских логах.

#### Scenario: Сессия восстановлена
- **WHEN** refresh cookie действительна и текущий профиль доступен
- **THEN** web восстанавливает access-токен, загружает профиль и показывает приватный экран без повторного входа

#### Scenario: Сессия отсутствует
- **WHEN** refresh endpoint отвечает `401`
- **THEN** web очищает локальное auth-состояние и показывает гостевой сценарий без технической ошибки

#### Scenario: Временная ошибка восстановления
- **WHEN** восстановление завершается network либо server failure
- **THEN** web показывает безопасное error-состояние с действием повторить восстановление и не считает пользователя разлогиненным

### Requirement: Защита приватных маршрутов
Главная `/` и профиль `/profile` MUST быть недоступны без восстановленной сессии. Публичные `/login` и `/register` MUST перенаправлять уже аутентифицированного пользователя на главную. После входа web MAY вернуть пользователя только на допустимый локальный приватный маршрут.

#### Scenario: Гость открывает приватный маршрут
- **WHEN** восстановление сессии завершилось unauthenticated состоянием на `/` или `/profile`
- **THEN** web перенаправляет на `/login` и сохраняет безопасный локальный адрес возврата

#### Scenario: Аутентифицированный пользователь открывает форму входа
- **WHEN** пользователь с восстановленной сессией открывает `/login` или `/register`
- **THEN** web перенаправляет его на `/`

#### Scenario: Внешний адрес возврата
- **WHEN** auth-маршрут получает внешний, protocol-relative или неизвестный адрес `next`
- **THEN** web игнорирует его и после успешной аутентификации открывает `/`

#### Scenario: Переход между формами аутентификации
- **WHEN** гость с допустимым локальным `next` переходит между `/login` и `/register`
- **THEN** противоположная форма сохраняет этот адрес, а небезопасное значение не переносится

### Requirement: Минимальная приватная главная
Основное содержимое приватной главной MUST показывать персонализированное приветствие текущего пользователя без дублирования brand, состояния сессии или перехода в профиль из private header.

#### Scenario: Просмотр главной
- **WHEN** аутентифицированный пользователь открывает `/`
- **THEN** основное содержимое показывает только heading `Добро пожаловать, {name}` и не показывает brand-label, описание восстановленной сессии или отдельную ссылку в профиль

### Requirement: Выход и профиль
Аутентифицированный пользователь MUST иметь возможность завершить текущую сессию и просмотреть имя, email и дату регистрации из существующего profile response. Профиль MUST быть только для чтения до появления отдельного API-контракта обновления.

#### Scenario: Просмотр профиля
- **WHEN** аутентифицированный пользователь открывает `/profile`
- **THEN** web показывает `name`, `email` и `createdAt` из current-user query и не выводит внутренний `id`

#### Scenario: Успешный выход
- **WHEN** пользователь подтверждает выход и API завершает текущую session chain
- **THEN** web очищает in-memory токен и current-user cache и перенаправляет на `/login`

#### Scenario: Ошибка выхода
- **WHEN** logout завершается recoverable network или server failure
- **THEN** web сохраняет текущий authenticated state и показывает безопасное сообщение с возможностью повторить

### Requirement: Навигация приватного header
Private header MUST предоставлять прямой переход на главную через логотип и прямой переход в профиль через имя текущего пользователя. Отдельные текстовые ссылки «Главная» и «Профиль» MUST NOT дублировать эти действия. Переход в профиль MUST оставаться доступным на mobile viewport.

#### Scenario: Переход на главную по логотипу
- **WHEN** аутентифицированный пользователь активирует логотип `Lite Notion` в private header
- **THEN** web открывает `/`

#### Scenario: Переход в профиль по имени
- **WHEN** аутентифицированный пользователь активирует отображаемое имя в private header на desktop или mobile viewport
- **THEN** web открывает `/profile`

### Requirement: Семантическая типографика web-экранов
Auth, session и private screens MUST использовать общие типографические primitives для повторяющихся заголовков и текстовых состояний, сохраняя семантические HTML-элементы, доступные имена и роли обратной связи.

#### Scenario: Основной заголовок экрана
- **WHEN** web показывает auth form, главную, профиль или session error с основным заголовком
- **THEN** заголовок остаётся доступным heading соответствующего уровня независимо от его визуального варианта

#### Scenario: Текст ошибки после унификации
- **WHEN** форма, session bootstrap или logout показывает ошибку
- **THEN** сообщение сохраняет `role="alert"` и доступно assistive technologies
