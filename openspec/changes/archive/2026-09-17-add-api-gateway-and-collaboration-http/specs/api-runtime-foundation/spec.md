## MODIFIED Requirements

### Requirement: Валидируемая конфигурация окружения
API MUST требовать и при запуске валидировать `NODE_ENV`, `PORT`, `CORS_ORIGIN`, `DATABASE_URL`, `DATABASE_CONNECTION_TIMEOUT_MS`, `JWT_SECRET`, `ACCESS_TOKEN_TTL_S`, `REFRESH_TOKEN_TTL_S`, `BCRYPT_ROUNDS` и сервисный креденшл для внутренних вызовов, преобразовывать числовые значения и не начинать принимать HTTP-запросы при отсутствующей или невалидной конфигурации. Допустимыми значениями `NODE_ENV` MUST быть `development`, `test` и `production`; `PORT` MUST быть целым числом от 1 до 65535; `CORS_ORIGIN` MUST быть HTTP(S) origin без path, query и fragment; `DATABASE_URL` MUST использовать protocol `postgresql` или `postgres`; `DATABASE_CONNECTION_TIMEOUT_MS` MUST быть положительным целым числом с установленной верхней границей; `JWT_SECRET` MUST быть непустой строкой длиной не менее 32 символов; `ACCESS_TOKEN_TTL_S` и `REFRESH_TOKEN_TTL_S` MUST быть положительными целыми числами с установленными верхними границами, причём `REFRESH_TOKEN_TTL_S` MUST быть строго больше `ACCESS_TOKEN_TTL_S`; `BCRYPT_ROUNDS` MUST быть целым числом от 4 до 15; сервисный креденшл MUST быть непустой строкой длиной не менее 32 символов.

API MUST оставаться единственным процессом, знающим `JWT_SECRET`: он выпускает access-токены и он же их проверяет. Ни шлюз, ни collaboration runtime MUST NOT получать это значение в своей конфигурации.

Сообщение об ошибке конфигурации MUST NOT содержать значение `JWT_SECRET` или сервисного креденшла.

#### Scenario: Запуск с локальной конфигурацией из шаблона
- **WHEN** environment содержит все обязательные значения из локального `.env`, созданного по `.env.example`
- **THEN** API запускается в development, слушает настроенный порт и использует настроенные frontend origin, database URL, connection timeout, ключ подписи токенов, сроки жизни токенов, стоимость bcrypt и сервисный креденшл

#### Scenario: Запуск с допустимой пользовательской конфигурацией
- **WHEN** все обязательные переменные содержат допустимые пользовательские значения
- **THEN** API использует эти значения, включая числовые значения порта, database connection timeout, сроков жизни токенов и стоимости bcrypt

#### Scenario: Отказ запуска при отсутствующей конфигурации
- **WHEN** хотя бы одна обязательная переменная не задана
- **THEN** API не начинает слушать порт, завершает запуск с ненулевым кодом и сообщает безопасную ошибку для отсутствующего ключа без дампа окружения

#### Scenario: Отказ запуска при невалидной конфигурации
- **WHEN** хотя бы одна контролируемая переменная окружения не соответствует своему контракту
- **THEN** API не начинает слушать порт, завершает запуск с ненулевым кодом и сообщает только безопасное описание ошибок конфигурации без дампа окружения, database credentials или значения ключа подписи токенов

#### Scenario: Отказ запуска при слабом ключе подписи
- **WHEN** `JWT_SECRET` не задан либо короче 32 символов
- **THEN** API не начинает слушать порт, завершает запуск с ненулевым кодом и сообщает только имя и безопасное описание невалидной настройки

#### Scenario: Отказ запуска при слабом сервисном креденшле
- **WHEN** сервисный креденшл не задан либо короче установленного минимума
- **THEN** API не начинает слушать порт и сообщает только имя и безопасное описание невалидной настройки

#### Scenario: Отказ запуска при противоречивых сроках жизни токенов
- **WHEN** `REFRESH_TOKEN_TTL_S` меньше либо равен `ACCESS_TOKEN_TTL_S`
- **THEN** API не начинает слушать порт и сообщает безопасное описание несогласованной настройки

#### Scenario: Ошибка конфигурации не раскрывает сервисный креденшл
- **WHEN** запуск прерывается ошибкой валидации конфигурации
- **THEN** сообщение об ошибке не содержит значение сервисного креденшла

### Requirement: Непроизводственная OpenAPI-документация
При `NODE_ENV`, отличном от `production`, API MUST публиковать Swagger UI на `/api/docs` и только OpenAPI JSON на `/api/openapi.json`. Документ MUST иметь title `Lite Notion API`, version `1.0`, учитывать глобальный prefix и описывать каждую опубликованную operation, её документированные ответы и стабильный явный operation ID. Документ MUST объявлять bearer-схему безопасности для access-токена и помечать ею защищённые operations. Swagger endpoints MUST находиться вне `/api/v1`.

Внутренние маршруты, предназначенные для обращений между сервисами, MUST NOT попадать в этот документ: он описывает публичный контракт, а у внутренних маршрутов другая модель аутентификации и другой круг вызывающих.

#### Scenario: Просмотр Swagger UI вне production
- **WHEN** API запущен в `development` или `test` и клиент открывает `/api/docs`
- **THEN** клиент получает Swagger UI, настроенный на опубликованный OpenAPI JSON, с возможностью задать bearer-токен

#### Scenario: Получение OpenAPI JSON вне production
- **WHEN** API запущен в `development` или `test` и клиент запрашивает `/api/openapi.json`
- **THEN** клиент получает валидный JSON-документ, где каждый опубликованный path имеет явный operation ID и документированные response schemas, включая health path `/api/v1/health` с operation ID `getHealth` и ответами `200` и `503`

#### Scenario: Документирование защищённых операций
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ объявляет bearer-схему безопасности, помечает ею операции, требующие аутентификации, и документирует для них ответ `401`

#### Scenario: Внутренние маршруты отсутствуют в документе
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ не содержит описания внутренних маршрутов

#### Scenario: YAML-представление не опубликовано
- **WHEN** клиент запрашивает Swagger-derived YAML endpoint
- **THEN** API отвечает статусом `404` в едином формате ошибок

#### Scenario: Документация недоступна в production
- **WHEN** API запущен с `NODE_ENV=production` и клиент запрашивает `/api/docs` или `/api/openapi.json`
- **THEN** API отвечает статусом `404` в едином формате ошибок

## ADDED Requirements

### Requirement: Личность запроса приходит от шлюза

Для запросов к публичным прикладным маршрутам API MUST выводить личность вызывающего из заголовков, проставленных шлюзом, а не из самостоятельной проверки access-токена. Идентификатор пользователя и идентификатор сессии, полученные таким образом, MUST использоваться теми же обработчиками, что прежде использовали результат проверки токена.

Запрос к прикладному маршруту без заголовков личности MUST отклоняться статусом `401` в едином формате HTTP-ошибок: отсутствие личности означает, что запрос пришёл мимо шлюза.

API MUST оставаться недостижимым мимо шлюза средствами сетевой изоляции. Доверие к заголовкам личности MUST NOT быть единственным контролем: оно допустимо ровно потому, что до API не доходит трафик, не прошедший шлюз.

#### Scenario: Обработчик получает личность из заголовков
- **WHEN** запрос доходит до прикладного маршрута с заголовками личности от шлюза
- **THEN** обработчик получает того же пользователя, которому принадлежал предъявленный шлюзу токен

#### Scenario: Запрос без заголовков личности отклоняется
- **WHEN** запрос к прикладному маршруту не содержит заголовков личности
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и не выполняет обработчик

### Requirement: Предел тела запроса покрывает размер документа

Предел размера тела HTTP-запроса MUST быть задан явно и MUST покрывать `DOCUMENT_MAX_BYTES` в той кодировке, в которой содержимое документа передаётся внутренним документным маршрутом. Предел MUST NOT оставаться значением по умолчанию используемого HTTP-слоя: документ предельного размера MUST приниматься, а не отклоняться из-за необъявленного лимита.

Превышение предела MUST отклоняться ошибкой в едином формате HTTP-ошибок, не приводя к частичной записи.

#### Scenario: Документ предельного размера проходит
- **WHEN** внутренний документный маршрут получает содержимое размером `DOCUMENT_MAX_BYTES`
- **THEN** запрос не отклоняется из-за предела размера тела

#### Scenario: Превышение предела отклоняется предсказуемо
- **WHEN** тело запроса превышает объявленный предел
- **THEN** API отвечает ошибкой в едином формате HTTP-ошибок
- **AND** ранее сохранённые данные остаются неизменными

### Requirement: Внутренние маршруты отделены от публичных

API MUST размещать маршруты, предназначенные для обращений между сервисами, под отличимым от публичного префиксом. К таким маршрутам MUST относиться проверка access-токена для шлюза, проверка эффективного доступа к странице и операции над содержимым документа.

Внутренние маршруты MUST NOT применять модель аутентификации публичных маршрутов: они MUST аутентифицироваться либо предъявленным пользовательским токеном, переданным вызывающим сервисом без изменений, либо сервисным креденшлом — в зависимости от того, есть ли у операции пользователь в скоупе.

Внутренние маршруты MUST NOT быть достижимы через шлюз.

#### Scenario: Внутренний маршрут отличим по префиксу
- **WHEN** сервис обращается к внутреннему маршруту
- **THEN** путь маршрута отличается от префикса публичного API

#### Scenario: Внутренний маршрут не принимает заголовки личности от шлюза
- **WHEN** обращение к внутреннему маршруту содержит только заголовки личности без пользовательского токена и без сервисного креденшла
- **THEN** API отклоняет обращение
