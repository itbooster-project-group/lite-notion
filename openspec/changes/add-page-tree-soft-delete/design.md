## Context

Мотивацию см. `proposal.md` — раздел «Why»; требования — `specs/page-tree/spec.md`, `specs/projects/spec.md`, `specs/trash-retention/spec.md`.

Существующее состояние, которое определяет подход:

- `Page.deletedAt DateTime?` уже есть в схеме и уже участвует в каждом `where` репозитория страниц (`deletedAt: null`). Проставлять её некому: операции удаления нет. У `Project` отметки удаления нет вовсе.
- Дерево держится тройным composite FK `Page(parentPageId, ownerId, projectId) → Page(id, ownerId, projectId)` с `onDelete: Cascade`, `Page.project → Project(id, ownerId)` тоже `Cascade`, `PageDocument.page` — `Cascade`. Все каскады — физические, на уровне базы; для мягкого удаления они не срабатывают, но пригодятся окончательной очистке.
- Репозитории — абстрактные классы, служащие DI-токенами; у каждого есть Prisma-реализация и in-memory реализация для тестов, обязанная воспроизводить наблюдаемый контракт. Каждое новое поведение репозитория придётся реализовать дважды.
- Правила дерева, которым нужна одна транзакция (перемещение, проверка цикла), уже живут в репозитории, а не в сервисе, — сознательное решение прошлого изменения. Рекурсивный обход дерева уже делается рекурсивным CTE (`assertParentAccepts`).
- Запланированные задачи выполняются в процессе через `@nestjs/schedule`; образец — `auth/session/session-cleanup.service.ts`. Redis и BullMQ намеренно отсутствуют.

## Goals / Non-Goals

**Goals:**

- Держать инвариант «нет живой страницы под удалённым предком и в удалённом проекте» так, чтобы он не зависел от порядка вызовов в сервисах.
- Сделать удаление и восстановление обратимыми по составу: восстановление возвращает ровно то множество страниц, которое пометила парная ему операция удаления. Место в дереве сохраняется, пока жив родитель; иначе поддерево поднимается в корень проекта.
- Уместить каскад по поддереву произвольной глубины в один запрос и одну транзакцию.
- Не расширять контракт `PageDto` полем `deletedAt`: удалённые страницы в обычные выдачи не попадают, и поле там всегда было бы `null`.

**Non-Goals:**

- Версионирование и история удалений: хранится только последнее удаление записи.
- Блокировки и сериализация конкурентных удалений разных поддеревьев: каскад пишет только собственное поддерево, пересечения между поддеревьями невозможны.
- Оптимизация очистки под большие объёмы (батчи, курсоры): при текущих объёмах достаточно одного `deleteMany`.

## Decisions

### 1. Отметка удаления — `deletedAt DateTime?`, а не boolean `isDeleted`

`Page.deletedAt` уже существует и уже фильтруется во всех чтениях. `Project` получает такую же колонку.

Формулировка требований говорила про флаг `isDeleted`. Boolean отвергнут: он не даёт срока хранения, а срок хранения нужен запланированной очистке (`specs/trash-retention`). Держать оба поля пришлось бы синхронно, и рассинхронизация была бы невидимой — оба фильтра дали бы разные множества. `deletedAt IS NOT NULL` — тот же флаг, только с временем; ничего из требований он не теряет.

**Это отклонение от буквы требований, не выведенное из кода: решение принято на этапе планирования и подлежит человеческому ревью вместе с остальными артефактами.**

Альтернатива — `isDeleted Boolean` рядом с `deletedAt`: отклонена как источник расхождения двух источников правды.

### 2. Источник удаления — enum-колонка `Page.deletedOrigin`, парная `deletedAt`

```prisma
enum PageDeletionOrigin {
  SELF         // страница удалена самостоятельно — корень корзины
  PARENT_PAGE  // удалена каскадом от предка-страницы
  PROJECT      // удалена каскадом от своего проекта
}
```

`deletedOrigin PageDeletionOrigin?`, `null` ровно тогда, когда `deletedAt` равно `null`. Согласованность закрепляется CHECK-constraint в миграции (`("deletedAt" IS NULL) = ("deletedOrigin" IS NULL)`) — Prisma такое ограничение не выражает, поэтому оно добавляется сырым SQL в той же миграции. Тот же приём, что и с collation `Page.position` в существующей миграции.

Отрисовка дерева опирается на уже существующие `parentPageId` и `projectId`; источник добавляет к ним ровно то, чего в них нет, — кто именно инициировал удаление. Он нужен в четырёх местах:

- **Корни корзины.** `GET /pages/trash` собирает дерево тем же способом, что и `findTree`, но узел подвешивается к родителю только когда он удалён не самостоятельно (`deletedOrigin ≠ SELF`) и родитель тоже удалён; всё остальное — корни выдачи. Именно поэтому отдельно удалённое ранее поддерево рисуется отдельным корнем, а не вложенным в позже удалённого предка.
- **Границы восстановления страницы.** Спуск восстановления идёт только по детям с `PARENT_PAGE` и останавливается на `SELF`: ранее и отдельно удалённое поддерево не воскресает. Право на восстановление источник не гоняет — адресовать можно любую удалённую страницу; он задаёт только, что уедет вместе с ней.
- **Границы восстановления проекта.** Восстанавливаются только страницы проекта с `PROJECT`. Это единственное место, где `PARENT_PAGE` и `PROJECT` обязаны различаться: без различения восстановление проекта подняло бы и `PARENT_PAGE`-потомков страницы, удалённой самостоятельно ещё до проекта, и они ожили бы под удалённым родителем.
- **Отказ по проекту.** `PROJECT` — единственный источник, по которому восстановление отказывает: живая страница в удалённом проекте невозможна. Отдельной проверки источника для этого не нужно — проект такой страницы всегда в корзине, — но именно `PROJECT` делает отказ неизбежным.

Проект своим удалением помечает `PROJECT` все свои живые страницы — и root-страницы, и вложенные. Поэтому правило вложенности сформулировано через «удалена не самостоятельно», а не через `PARENT_PAGE`: иначе каждая страница удалённого проекта стала бы отдельным корнем и дерево проекта в корзине рассыпалось бы в плоский список.

Альтернатива — boolean «удалена каскадом»: покрывает первые два пункта, но проваливает третий, а вместе с ним и инвариант «нет живой страницы под удалённым предком». Отвергнута по нему.

Альтернатива — `deletedRootId` со ссылкой на инициатора удаления: рабочая, и в одном месте лучше — восстановление становится `WHERE deletedRootId = $1` вместо рекурсивного CTE. Отвергнута по двум причинам: ссылка полиморфна (инициатор — либо страница, либо проект), поэтому FK на неё не поставить, и после окончательного удаления инициатора в колонке остаются висящие идентификаторы, которые база не подчистит. Enum держит ту же информацию значением, а не ссылкой, и потому не может рассинхронизироваться с тем, на что ссылается.

`Project` источника не получает: у проекта нет родителя, и любое его удаление самостоятельно.

### 3. Каскад — рекурсивный CTE в одном `UPDATE`, а не обход в приложении

Удаление страницы:

```sql
WITH RECURSIVE subtree AS (
  SELECT "id" FROM "Page" WHERE "id" = $1 AND "ownerId" = $2 AND "deletedAt" IS NULL
  UNION ALL
  SELECT child."id" FROM "Page" child
  JOIN subtree ON child."parentPageId" = subtree."id"
  WHERE child."deletedAt" IS NULL
)
UPDATE "Page" SET "deletedAt" = $3,
       "deletedOrigin" = CASE WHEN "id" = $1 THEN 'SELF' ELSE 'PARENT_PAGE' END
WHERE "id" IN (SELECT "id" FROM subtree)
```

Спуск не проходит сквозь уже удалённые узлы (`child."deletedAt" IS NULL` в рекурсивной ветви): их поддеревья уже помечены, и перемечать их нельзя. Одно и то же `$3` у всех строк делает отметку времени поддерева единой — это то, что потом отсчитывает срок хранения для всего поддерева разом.

Восстановление — тот же CTE с другим условием спуска:

```sql
... UNION ALL
SELECT child."id" FROM "Page" child
JOIN subtree ON child."parentPageId" = subtree."id"
WHERE child."deletedOrigin" <> 'SELF'
```

и `SET "deletedAt" = NULL, "deletedOrigin" = NULL`. Условие спуска — то же самое «удалена не самостоятельно», которым корзина подвешивает узел к родителю, а не `= 'PARENT_PAGE'`: иначе восстановление страницы из удалённого проекта не забрало бы её детей, помеченных `PROJECT`, и вернуло бы одинокий узел вместо того, что нарисовано под ним. Источник самого корня восстановления не проверяется: адресовать можно любую удалённую страницу.

Когда родительская страница корня восстановления остаётся удалённой, тот же `UPDATE` дополнительно ставит корню `parentPageId = NULL` и новый ранг (см. раздел 6). Потомки при этом не трогаются: их `parentPageId` уже указывают друг на друга, и поддерево поднимается целиком одним изменением одной строки. Смена проекта — единственное, что не укладывается в этот `UPDATE`: она идёт отдельным statement'ом перед ним, см. раздел 7.

Обход в приложении отвергнут: он дал бы N+1 запросов на глубину дерева и окно между чтением потомков и записью. CTE выполняется одним запросом, поэтому и каскад, и его атомарность обеспечивает сама база.

Удаление и восстановление проекта рекурсии не требуют вовсе: `updateMany` по `projectId` — «все живые страницы проекта» при удалении и «все страницы проекта с `deletedOrigin = PROJECT`» при восстановлении. Дерево тут ни при чём: `projectId` уже есть в каждой строке.

### 4. Блокировки: создание, удаление и восстановление берут advisory lock владельца

`move` уже берёт `pg_advisory_xact_lock(hashtext(ownerId))` первым действием транзакции. Удаление и восстановление берут тот же ключ по той же причине: иначе перемещение могло бы вставить живое поддерево под страницу, которую параллельная транзакция в этот момент помечает удалённой, — и инвариант «нет живой страницы под удалённым предком» нарушился бы, не нарушив ни одного FK.

Восстановление, поднимающее страницу в корень, дополнительно берёт блокировку уровня назначения тем же ключом `siblingLevelLockKey(projectId, null)`, что берут `create` и `move`: оно читает «последнего брата» среди root-страниц проекта и обязано делать это под той же блокировкой, что и они. **`create` тоже встаёт в этот порядок.** До появления мягкого удаления он брал только уровневую блокировку, а живость родителя проверял `PagesService` — до открытия транзакции. Пока `deletedAt` никто не проставлял, это было безвредно. С появлением удаляющего проверка стала устаревать между сервисом и вставкой: `softDelete` под блокировкой владельца помечает поддерево и коммитит, `create` берёт свободную уровневую блокировку и вставляет живую строку под удалённым предком. Ни один FK этого не ловит — тройной сверяет `(id, ownerId, projectId)` и про `deletedAt` не знает.

Поэтому `create` берёт блокировку владельца первой, до уровневой, и повторяет проверки проекта и родителя внутри транзакции. Одной блокировки мало: она сериализует, но не сообщает, что за это время родителя пометили. Одной перепроверки тоже мало: без блокировки она читает состояние до чужого коммита. Нужны обе.

Уровневая блокировка здесь бы не помогла и `softDelete` не подошла бы вовсе: он охватывает поддерево из многих уровней, и блокировок понадобилось бы столько же, с непредсказуемым порядком захвата. Ранг он при этом не вычисляет — а уровневая блокировка существует ровно для того, чтобы сериализовать «прочитать последнего брата → записать новый ранг».

Все операции над проектами берут ту же блокировку, и каждая по своей причине. `softDelete` и `restore` — иначе создание успело бы вставить живую страницу в проект, уезжающий в корзину. `purge` и `purgeTrash` — иначе подсчёт обречённых страниц и физическое удаление разъезжаются: READ COMMITTED позволяет параллельному мягкому удалению закоммититься между `assertConfirmed` и `delete`, и страница уедет навсегда, не попав в перечень, который подтверждал вызывающий. Одной транзакции тут мало — защищает именно блокировка.

Порядок захвата у всех один — «владелец → уровень», — поэтому взаимных блокировок схема не добавляет. Цена: создание страниц одного владельца сериализуется, как уже сериализованы перемещение, удаление и восстановление.

### 5. Проверки восстановления — в репозитории, в той же транзакции

Восстановление обязано убедиться, что проект страницы жив, и узнать, жив ли её родитель. Оба чтения касаются строк, которые параллельная транзакция может изменить, поэтому идут внутри транзакции восстановления, под тем же advisory lock, и живут в репозитории — по тому же принципу, по которому там уже живёт проверка цикла у `move`. Сервис остаётся местом маршрутизации ошибок, контроллер — переводом их в HTTP.

Источник удаления восстановление **не проверяет**. Адресовать можно любую удалённую страницу: и корень корзины, и вложенную в него ветку. У вложенной ветки прежний родитель остался в корзине, поэтому она попадает в ту же ветку поведения, что и страница с удалённым родителем, — подъём в корень (раздел 6). Отказывать тут было бы произволом: страница нарисована в корзине, у неё есть адрес, и вернуть её пользователю есть куда.

Удалённый проект — единственная ошибка: подъём в корень ничего не решает, корень принадлежит тому же удалённому проекту, и живая страница в удалённом проекте нарушила бы инвариант из `specs/page-tree`. Отдельной проверки источника для этого не нужно: страница с `PROJECT` всегда лежит в удалённом проекте, потому что восстановление проекта снимает отметку со всех них разом.

Новая доменная ошибка в `pages/errors.ts` одна: `PageRestoreProjectDeletedError` (проект в корзине → `409`). Отсутствие страницы по-прежнему `PageNotFoundError` → `404`. `helpers.ts` (`toHttpException`) расширяется одной ветвью.

### 6. Восстановление под удалённым родителем поднимает страницу в корень проекта

Отказать было бы проще, но заставило бы пользователя восстанавливать всю цепочку предков ради одной страницы. Подъём в корень сохраняет содержимое и поддерево и не создаёт живую страницу под удалённой — инвариант держится.

Правило одно на два случая: страница, удалённая самостоятельно раньше своего предка, и страница, удалённая вместе с предком, при восстановлении ведут себя одинаково. Различать их незачем — у обеих родитель в корзине, и вернуть их на место некуда.

Новый ранг берётся тем же способом, что у `create` и у перемещения в конец уровня: `positionBetween(последний_root_ранг, null)` под блокировкой уровня `(projectId, null)`. Прежний ранг не переиспользуется: он считался среди братьев другого уровня и мог бы совпасть с рангом существующей root-страницы.

Прежний `parentPageId` не сохраняется отдельной колонкой «где страница лежала раньше»: восстановление после подъёма перестаёт быть точно обратным удалению, и это цена решения — см. «Risks».

### 7. Проект назначения — параметр восстановления, а не отдельная операция

Страницу из удалённого проекта восстановить некуда: живая страница в удалённом проекте невозможна, а подъём в корень не помогает — корень принадлежит тому же проекту. Но требовать восстановить весь проект ради одной страницы — плохой ответ: пользователь получит обратно всё, а удалить проект снова он уже не сможет, не потеряв ту самую страницу.

Поэтому `POST /pages/{pageId}/restore` принимает необязательный `projectId` в теле, и восстановление переносит страницу в него.

Альтернатива — отдельный маршрут смены проекта, который клиент вызывает между двумя попытками восстановления: `restore` → `409` → `PATCH projectId` → `restore`. Отвергнута по трём причинам. Последовательность неатомарна: если последний шаг не пройдёт, страница останется перенесённой в чужой проект, хотя пользователь просил только восстановить её. Такой маршрут пришлось бы защищать от вызова на живой странице, на чужой и на странице из живого проекта — иначе он и есть запрещённый перенос между проектами. И он ломает требование из `specs/page-tree` целиком, тогда как параметр восстановления вырезает из него узкое исключение.

Шагов для пользователя столько же: клиент показывает отказ, даёт выбрать проект из уже загруженного `GET /projects` и повторяет запрос.

`projectId` принимается только когда собственный проект страницы в корзине. Иначе — `400`: принимать его на живой странице значило бы завести перенос между проектами чёрным ходом.

**Переносится всё физическое поддерево, а не только восстанавливаемая часть.** Вложенное поддерево, удалённое раньше и самостоятельно, остаётся удалённым, но его `projectId` меняется вместе с остальными: тройной FK не допускает ребёнка в одном проекте с родителем в другом, и оставить его позади нельзя. Отвязать его тоже нельзя — он превратился бы в корень корзины проекта, который пользователь не трогал.

Отсюда два statement'а в одной транзакции, а не один. Первый меняет `projectId` по всему физическому поддереву: `onUpdate: NoAction` у тройного FK означает, что база не протянет смену сама, а проверяет ограничения в конце statement'а — поэтому предок и потомки обязаны меняться одним запросом. Второй снимает отметку удаления с восстанавливаемого набора и обнуляет корню `parentPageId`. Порядок именно такой: снятие ссылки на родителя FK-безопасно всегда, а смена проекта — только целиком.

Полагаться на «FK проверяются в конце statement'а» на слово нельзя, поэтому перенос закреплён интеграционным тестом на живой базе.

### 8. Форма выдачи корзины

`GET /pages/trash` возвращает `PageTreeNodeDto`-подобную структуру, но с полем `deletedAt` — фронтенду нужно показать, сколько записи осталось лежать. Поэтому вводится отдельный `DeletedPageDto`/`DeletedPageTreeNodeDto`, а не расширяется `PageDto`: у живой страницы `deletedAt` всегда `null`, и nullable-поле в основном контракте было бы шумом. `deletedOrigin` наружу не публикуется — вложенность ответа уже несёт всю информацию, которую он кодирует.

`ProjectDto` аналогично дополняется отдельным `DeletedProjectDto` с `deletedAt`. Страниц он не содержит: удалённая страница показывается ровно в одном месте — в корзине страниц, — и отдельного чтения содержимого удалённого проекта нет.

Отсюда следует, что клиент, показывающий корзину, читает оба маршрута: `projectId` есть в каждом узле корзины страниц, и по нему узлы сопоставляются со списком удалённых проектов. Так фронтенд заранее знает, какие корни отдельно не восстанавливаются, вместо того чтобы узнавать это из `409`.

Альтернатива — `GET /projects/trash/{projectId}/pages` с деревом одного проекта: тогда страницу, удалённую самостоятельно до удаления её проекта, пришлось бы либо показывать дважды, либо оставлять дыру в дереве проекта. Отвергнута в пользу единственного места показа.

Сборку дерева корзины делает `PagesService` тем же проходом, что и `findTree`. Мягкое удаление не трогает `parentPageId` и `position` — они нужны восстановлению, — поэтому у страницы, удалённой отдельно и раньше своего предка, ссылка на родителя по-прежнему указывает внутрь удалённого поддерева. Из-за этого сборка корзины отличается от сборки живого дерева двумя правилами:

- **Кто корень.** В живом дереве — узел с `parentPageId = null`. В корзине — всё, что не подвешено: узел подвешивается к родителю тогда и только тогда, когда он удалён не самостоятельно и родитель тоже удалён. Отсюда сразу три нужных следствия: отдельно удалённый потомок становится вторым корнем и в детей своего предка не попадает; страницы удалённого проекта сохраняют вложенность и дают корнями только root-страницы проекта; узел попадает в выдачу ровно один раз.
- **Как упорядочены корни.** Корни корзины не братья: они приходят с разных уровней живого дерева, их ранги из разных групп и несравнимы — два корня вполне могут иметь одинаковый `position`. Поэтому корни сортируются по убыванию `deletedAt` с тай-брейком по `id`, а по рангу сортируются только вложенные узлы, которые действительно братья. Тем же правилом упорядочен список удалённых проектов.

Общий проход выносится в приватный helper, параметризованный этими двумя правилами, чтобы сборка и детерминированность считались одним кодом в обеих выдачах.

### 9. Маршрутизация: `GET /pages/trash` объявляется до `GET /pages/:pageId`

`trash` — не UUID, и `ParseUUIDPipe` на `:pageId` вернул бы `400` вместо корзины, если статический маршрут окажется ниже параметрического. Это касается обоих глаголов: `GET /pages/trash` должен стоять выше `GET /pages/:pageId`, а `DELETE /pages/trash` — выше `DELETE /pages/:pageId`. `DELETE /pages/trash/:pageId` конфликта не имеет: у него другая длина пути. Порядок объявления методов в контроллере становится значимым; в контроллере это фиксируется комментарием, в тестах — HTTP-тестами на оба маршрута. То же для проектов.

Альтернатива — `deleted` вместо `trash` в пути: отвергнута в пользу `trash`, потому что `trash` называет место, а не состояние, и естественно продолжается в `DELETE /pages/trash` («очистить корзину») и `DELETE /pages/trash/{pageId}` («выбросить из корзины насовсем»).

Альтернатива — `GET /pages?deleted=true`: размывает контракт основной выдачи (тот же путь, две разные формы ответа) и не даёт места для операций очистки.

### 10. Ручное окончательное удаление — те же маршруты корзины, физический `delete`

Четыре операции, все отвечают `204` в успешном случае:

| Маршрут | Что удаляет |
| --- | --- |
| `DELETE /pages/trash/{pageId}` | одну страницу из корзины — корень или вложенную ветку — и всё её физическое поддерево; при `?cascade=true`, если в нём есть отдельно удалённые страницы |
| `DELETE /pages/trash` | все удалённые страницы владельца; подтверждения не требует — всё уничтожаемое корзина показывала |
| `DELETE /projects/trash/{projectId}` | один удалённый проект; каскад уносит все его страницы и документы; при `?cascade=true`, если среди них есть отдельно удалённые |
| `DELETE /projects/trash` | все удалённые проекты владельца, с тем же `?cascade=true` |

Правило одно на все четыре: **если операция уничтожает записи, которые парное чтение корзины показывало не внутри удаляемого, она отказывает, пока вызывающий не подтвердит это явно**. Адресное удаление доступно всему, что видно в корзине, — и корням (`SELF`), и вложенным веткам (`PARENT_PAGE`), и страницам удалённых проектов; отказов по источнику удаления нет, а единственный отказ по адресату — `404` на живой, чужой и несуществующей записи.

Нужда в правиле возникает из того, что нарисованная вложенность и физическая расходятся. Страница, удалённая раньше и самостоятельно, нарисована отдельным корнем, но физически лежит внутри поддерева позже удалённого предка, и FK-каскад унесёт её вместе с ним. Сохранить её нельзя — вне своего родителя страница существовать не может, — значит остаётся сказать об этом до того, как она погибнет. То же и у проекта: его страницы, удалённые самостоятельно до его удаления, нарисованы отдельными корнями, а деться им вне проекта тоже некуда.

**Механика — `?cascade=true`.** Перед физическим удалением собираются записи, которые погибнут сверх нарисованного: у страницы — `SELF`-потомки в её поддереве, у проекта — его страницы с источником, отличным от `PROJECT`. Если их нет, параметр не нужен и запрос проходит сразу — подтверждение спрашивается только там, где есть о чём спрашивать. Если есть и параметр не передан, операция отвечает `409` с причиной и их заголовками; повтор с `?cascade=true` выполняет удаление целиком.

Собирать нужно тем же обходом, что и удалять: у страницы это рекурсивный CTE по поддереву, у проекта — выборка по `projectId` с фильтром по источнику. Оба идут в той же транзакции, что и `delete`, иначе между сбором и удалением вклинилась бы чужая запись, и подтверждённое множество разошлось бы с уничтоженным.

**Заголовки едут в `message`.** `HttpExceptionFilter` нормализует тело ответа и пропускает наружу только `error` и `message`, отбрасывая всё остальное; `message` при этом уже умеет быть массивом строк — так отдаются validation messages. Поэтому отказ кладёт в `message` массив, первым элементом которого идёт причина, а дальше — заголовки обречённых страниц. Клиенту не нужно разбирать строку, а единый формат ошибок и `HttpErrorResponseDto` остаются нетронутыми.

Идентификаторы в ответ не кладутся: клиент, показывающий корзину, уже держит все удалённые страницы с их `id` и `parentPageId` и при желании подсветит обречённые узлы сам. Менять общий формат ошибок ради подсветки в одном эндпоинте не стоит.

Заголовки отдаются как хранятся, включая пустые: страница может быть создана без заголовка, и подставлять за пользователя «Без заголовка» — дело интерфейса, а не API.

Перечень ничем не ограничен сверху. Обречённая страница — это та, которую пользователь удалил отдельно до удаления её предка, поэтому на практике их единицы; если однажды окажется иначе, перечень придётся усечь и добавить в отказ общее число. Сейчас этого нет сознательно: усечение без счётчика врёт, а счётчик ради гипотетического случая усложняет ответ.

Безопасно по умолчанию, разрушительно по явному требованию — и одинаково для любого клиента, а не только для того, который не забыл показать диалог.

Альтернатива — поднимать уцелевшие корни в корень проекта вместо отказа, как это делает восстановление из-под удалённого родителя (раздел 6): у страниц потерь не было бы вовсе. Отвергнута, потому что у проектов так сделать нельзя — поднимать некуда, — и пришлось бы держать две разные механики на одну операцию. Единый контракт важнее.

Альтернатива — оставить как есть и положиться на диалог во фронтенде: клиент действительно может вычислить обречённые страницы сам, `parentPageId` и `projectId` есть в каждом узле корзины. Отвергнута потому, что противоречие между чтением и удалением создаёт сервер, и чинить его в каждом клиенте отдельно — значит оставить ловушку в контракте.

Проверки живут в репозитории, в той же транзакции и под тем же advisory lock владельца, что удаление и восстановление: иначе параллельное восстановление могло бы поднять потомка в корень ровно между проверкой и `DELETE`, и удаление разошлось бы с тем, что оно посчитало.

Остаток поддерева удаляется по-прежнему одним `delete` по корню: физические `onDelete: Cascade` уже описаны в «Context» и уносят вложенное сами.



Методы остаются в доменных репозиториях (`PagesRepository.purge`, `purgeTrash`; `ProjectsRepository.purge`, `purgeTrash`), а не переезжают в модуль очистки: они фильтруют по владельцу и по источнику удаления, то есть работают доменными правилами, тогда как запланированная задача фильтрует по одному сроку и владельца не знает вовсе.

Альтернатива — единый `DELETE /api/v1/trash`, очищающий обе корзины разом: одна атомарная операция вместо двух вызовов с фронтенда, но контракт корзины расползается по трём модулям, а чтение корзины остаётся доменным. Отвергнуто в пользу симметрии с чтением; фронтенд делает два вызова, и оба идемпотентны, поэтому частичный отказ чинится повтором.

Альтернатива — soft-delete-флаг «в процессе окончательного удаления» и асинхронная дочистка: нужна только при объёмах, при которых `delete` не укладывается в запрос. Таких объёмов сейчас нет.

### 11. Очистка — `@Cron` раз в сутки, физическое удаление, каскады базы

`TrashCleanupService` по образцу `SessionCleanupService`: `@Cron(CronExpression.EVERY_DAY_AT_3AM)`, ошибки логируются и не выпускаются наружу, задача идемпотентна и безвредна при запуске на нескольких экземплярах.

Порядок внутри одного запуска: сначала `deleteMany` по `Project` с `deletedAt < cutoff`, затем `deleteMany` по `Page` с `deletedAt < cutoff`. Физические FK-каскады уносят страницы удаляемых проектов, поддеревья удаляемых страниц и их документы — отдельного обхода не нужно.

**Почему у крона нет подтверждения, хотя у ручного удаления оно есть.** Каскад не может унести запись, которой ещё рано: отметка времени потомка всегда не позже отметки его предка. Каскадно помеченный потомок получает ровно ту же отметку, что и предок. Самостоятельно удалённый потомок сохранил источник `SELF` только потому, что был помечен раньше предка, — иначе предок перемечал бы его. Оказаться помеченным позже предка, оставаясь внутри его поддерева, он не может: для этого он должен был бы быть живым позже, а живая страница под удалённым предком запрещена инвариантом из `specs/page-tree`. Единственный выход из-под удалённого предка — восстановление, но оно поднимает страницу в корень проекта (раздел 6), то есть выводит её из этого поддерева.

Отсюда: всё, что физически вложено в просроченную запись, просрочено тоже, и крон не уничтожает ничего, у чего оставалось время. Предупреждать не о чем, и `?cascade=true` ему не нужен — асимметрия с ручным удалением не пробел, а следствие: только пользовательское удаление способно снести запись, у которой ещё оставался срок. Инвариант закрепляется тестом, а не только рассуждением.

Из того же следует, что `Page.projectId` незачем делать nullable ради «спасения» страниц уничтожаемого проекта: спасать нечего. А цена была бы высокой — оба FK у `Page` объявлены `MATCH SIMPLE`, поэтому при `projectId IS NULL` тройной FK `(parentPageId, ownerId, projectId)` перестал бы проверяться целиком, и требование «родитель и ребёнок совпадают по владельцу и проекту, закреплено на уровне базы» превратилось бы в проверку в коде ровно для тех строк, где всё и может разъехаться. Вдобавок занулять пришлось бы всё поддерево сразу, `projectId` стал бы nullable в опубликованном контракте, а осиротевшую страницу было бы некуда восстанавливать без новой операции «восстановить в проект».

Срок хранения — константа `TRASH_RETENTION_MS = 30 * 24 * 60 * 60 * 1000` рядом с уже существующей `REVOKED_SESSION_RETENTION_MS`, но в `common/constants.ts`: она общая для страниц и проектов, и класть её в один из двух модулей значило бы сделать второй зависимым от первого ради числа. Через окружение срок не настраивается — см. `proposal.md`, «Out of Scope».

Куда положить сервис: `apps/api/src/pages/trash-cleanup.service.ts` был бы неверен — задача чистит и проекты. Сервис получает собственный модуль `apps/api/src/trash/trash-cleanup.module.ts`, зависящий только от `DatabaseModule`: чистка физическая, доменных правил у неё нет, и проходить ради неё через `PagesService` и `ProjectsService` значило бы добавить в них методы, не нужные ни одному маршруту.

### 12. Индексы

- `Page`: существующий `@@index([ownerId, deletedAt])` покрывает и обычные чтения, и выборку корзины. Добавляется `@@index([deletedAt])` — под `WHERE "deletedAt" < cutoff` очистки, которая идёт без владельца.
- `Page`: рекурсивный спуск идёт по `parentPageId`; существующий `@@index([ownerId, parentPageId, position])` его покрывает.
- `Project`: добавляется `@@index([ownerId, deletedAt])` под список проектов и список удалённых, и `@@index([deletedAt])` под очистку.

## Risks / Trade-offs

- **Каскад CTE обходит проверки Prisma и пишет сырым SQL** → мимо типов Prisma Client проходит только `UPDATE`; значения enum и имена колонок фиксируются тестами на живой базе (`*.integration-spec.ts`), как уже сделано для collation и для проверки цикла.
- **Восстановление в другой проект переставляет и то, что осталось в корзине** → вложенное поддерево, удалённое раньше и самостоятельно, меняет проект вместе с переносимой страницей, хотя пользователь его не трогал и восстановленным оно не становится. Альтернатив нет: тройной FK не допускает ребёнка в одном проекте с родителем в другом. Зафиксировано отдельным сценарием спеки, чтобы поведение не выглядело случайным.
- **Перенос опирается на то, что Postgres проверяет FK в конце statement'а** → разбей смену `projectId` на два запроса, и тройной FK отвергнет первый же. Свойство не выражено ни в схеме, ни в типах, поэтому закреплено интеграционным тестом на живой базе, а не комментарием.
- **Подъём в корень теряет прежнее место страницы** → восстановление под удалённым родителем перестаёт быть точно обратным удалению: вернув предка потом, пользователь не получит поддерево обратно на прежний уровень и переносит его руками через `move`. Принято сознательно (раздел 6); альтернатива — отказ с `409` — заставляла бы восстанавливать всю цепочку предков ради одной страницы. Смягчается тем, что подъём происходит только при явном восстановлении страницы, чей предок остался в корзине.
- **Восстановление отказывает с `409`, когда проект всё ещё в корзине** → фронтенду нужно объяснить, что сначала восстанавливается проект. Подъём в корень тут не альтернатива: корень лежит в том же удалённом проекте.
- **Подъём в корень меняет ранг страницы внутри операции восстановления** → операция, которую пользователь считает «вернуть как было», незаметно переупорядочивает верхний уровень проекта, ставя страницу последней. Прикрывается сценарием спеки и тестом на неизменность рангов остальных root-страниц.
- **Единая отметка времени у поддерева** → потомок, удалённый вместе с предком, теряет собственный «возраст». Это осознанно: срок хранения отсчитывается для поддерева целиком, иначе очистка могла бы вынести часть поддерева и оставить его корень.
- **Очистка одним `deleteMany` без батчей** → при большой корзине один запуск может держать долгую транзакцию. Приемлемо при текущих объёмах; батчи добавляются без изменения контракта, когда объёмы появятся. То же относится к ручному `DELETE /pages/trash`, только там долгая транзакция держится внутри пользовательского запроса и видна как медленный ответ.
- **Ручное окончательное удаление необратимо и подтверждается только на фронтенде** → API выполняет его без второго шага: один неверный вызов уносит поддерево со всеми документами. Диалог подтверждения — задача UI (вне объёма, см. `proposal.md`); на стороне API страховкой служит только то, что операция адресует лишь уже удалённые записи, то есть живую страницу ею не уничтожить.
- **`?cascade=true` легко превратить в формальность** → клиент, всегда передающий параметр, ничем не отличается от отсутствия проверки. Сервер этого не различает; страховкой остаётся то, что `409` с заголовками обречённых записей приходит первым и его нужно осознанно обойти, а не то, что параметр трудно передать.
- **Перечень в отказе — не обещание** → между `409` и повторным запросом с подтверждением состав корзины может измениться, и уничтожено будет не ровно то, что было перечислено. Сбор идёт заново в транзакции самого удаления, поэтому уничтожается всегда согласованное множество, но показанный пользователю список мог устареть.
- **Перечень заголовков не ограничен сверху** → страница с сотней отдельно удалённых потомков даст стострочный `message`. Ограничение не введено сознательно (см. раздел 9); если объёмы появятся, добавляется усечение с общим числом, и это изменение контракта ошибки, а не поведения удаления.
- **`DELETE /pages/trash` очищает и страницы удалённых проектов, и такой проект восстанавливается пустым** → пользователь, нажавший «очистить корзину страниц», может не ожидать, что это выпотрошит проект, лежащий в другой корзине. Прямое следствие того, что эти страницы показывались в очищаемой корзине; смягчается предупреждением в UI, которое вне объёма этого изменения.
- **Корзина страниц может оказаться очень широкой** → все страницы всех удалённых проектов приходят одним ответом, тогда как раньше они не приходили вовсе. Пагинации у корзины нет — как её нет и у чтения живого дерева; при появлении объёмов оба чтения придётся резать одинаково, и делать это порознь не стоит.
- **`deletedOrigin` — денормализация** → её можно вычислить обходом дерева и сравнением отметок времени, но только при допущении, что отметки внутри одной операции совпадают до миллисекунды. Явная колонка не зависит от точности часов.
- **Порядок маршрутов `trash` против `:pageId`** → перестановка методов в контроллере ломает корзину и даёт `400` вместо `200`. Прикрывается HTTP-тестом.
- **Хард-каскад при очистке трогает строки, которых нет в `deleteMany`** → если инвариант отметок времени когда-нибудь нарушится, очистка унесёт непросроченные записи. Прикрывается тестом на смешанное поддерево (предок просрочен, потомок помечен позже — построить такой случай штатными операциями невозможно, тест это фиксирует).

## Migration Plan

Одна миграция Prisma, аддитивная и обратимая:

1. `ALTER TABLE "Project" ADD COLUMN "deletedAt" TIMESTAMP(3)` — nullable, существующие проекты остаются живыми.
2. `CREATE TYPE "PageDeletionOrigin"`, `ALTER TABLE "Page" ADD COLUMN "deletedOrigin"` — nullable; существующие строки имеют `deletedAt IS NULL`, поэтому CHECK выполняется сразу и backfill не нужен (проставлять отметку было некому — см. «Context»).
3. `ALTER TABLE "Page" ADD CONSTRAINT ... CHECK (("deletedAt" IS NULL) = ("deletedOrigin" IS NULL))`.
4. Новые индексы по `deletedAt` у обеих таблиц.

Развёртывание: миграция накатывается до выкладки кода; старый код новые колонки не читает и не пишет, поэтому окно совместимости безопасно в обе стороны. Откат — обратная миграция, снимающая CHECK, индексы и колонки; уже удалённые записи при откате станут снова видимыми, безвозвратной потери данных откат не вызывает.

Задача очистки начинает удалять записи не раньше, чем через срок хранения после выкладки: до неё не существует ни одной записи с проставленной отметкой.
