# page-tree Specification

## Purpose

Определяет наблюдаемый контракт иерархических страниц Lite Notion: как страницы создаются в дереве одного владельца внутри одного проекта, как это дерево читается, переименовывается, перемещается и упорядочивается, и почему чужое дерево неотличимо от несуществующего.

## Requirements

### Requirement: Страница как узел дерева владельца
Страница MUST принадлежать ровно одному пользователю-владельцу, ровно одному проекту и MUST иметь необязательную ссылку на родительскую страницу. Страница без родителя — root-страница дерева.

Родитель и ребёнок MUST совпадать и по владельцу, и по проекту. Оба ограничения MUST быть закреплены на уровне базы данных, а не только проверкой в приложении: сохранение страницы, у которой родитель принадлежит другому пользователю либо лежит в другом проекте, MUST быть невозможно. Как следствие, дерево MUST NOT растягиваться на два проекта.

Каждая страница MUST иметь заголовок, строковый ранг порядка среди братьев и создателя. Создание страницы MUST в той же транзакции создавать ровно одну связанную запись документа страницы; страница без документа и документ без страницы MUST быть невозможны. Создаваемая запись документа MUST инициализироваться пустым содержимым.

Страница MUST иметь отметку удаления. Все операции чтения MUST исключать страницы с проставленной отметкой удаления. Единственное исключение — чтение корзины, которое возвращает только их.

Удаление MUST быть согласованным по дереву: страница без отметки удаления MUST NOT иметь ни родительской страницы с отметкой удаления, ни проекта с отметкой удаления. Живая страница внутри удалённого поддерева и живая страница в удалённом проекте MUST быть невозможны.

#### Scenario: Владелец root-страницы
- **GIVEN** аутентифицированный пользователь со своим проектом
- **WHEN** он создаёт страницу без родителя
- **THEN** созданная страница принадлежит ему, лежит в указанном проекте, не имеет родителя и получает связанную запись документа с пустым содержимым
- **AND** создателем страницы записан он сам

#### Scenario: Владелец и проект наследуются от родителя
- **WHEN** пользователь создаёт страницу с родителем из своего дерева
- **THEN** созданная страница принадлежит тому же владельцу и лежит в том же проекте, что и родитель

#### Scenario: Разные владельцы у родителя и ребёнка отвергаются базой
- **WHEN** предпринимается попытка сохранить страницу, чей идентификатор владельца не совпадает с идентификатором владельца её родителя, в обход прикладных проверок
- **THEN** база данных отклоняет запись нарушением constraint, и страница не появляется

#### Scenario: Разные проекты у родителя и ребёнка отвергаются базой
- **WHEN** предпринимается попытка сохранить страницу, чей идентификатор проекта не совпадает с идентификатором проекта её родителя, в обход прикладных проверок
- **THEN** база данных отклоняет запись нарушением constraint, и страница не появляется

#### Scenario: Удалённая страница не видна в чтениях
- **WHEN** у страницы проставлена отметка удаления
- **THEN** ни выдача дерева, ни чтение одной страницы её не возвращают

#### Scenario: Живой потомок удалённой страницы невозможен
- **WHEN** страница помечена удалённой
- **THEN** ни один её потомок на любой глубине не остаётся без отметки удаления

#### Scenario: Живая страница в удалённом проекте невозможна
- **WHEN** проект помечен удалённым
- **THEN** ни одна его страница не остаётся без отметки удаления

### Requirement: Создание страницы
API MUST публиковать защищённый `POST /api/v1/pages`, принимающий обязательный идентификатор проекта, необязательный идентификатор родителя и необязательный заголовок. Владельцем и создателем создаваемой страницы MUST становиться текущий пользователь; идентификатор владельца и идентификатор создателя MUST NOT приниматься от клиента.

Проект MUST принадлежать текущему пользователю. При указанном родителе идентификатор проекта в запросе MUST совпадать с проектом родителя.

При отсутствии идентификатора родителя MUST создаваться root-страница. При указанном родителе MUST создаваться дочерняя страница. Новая страница MUST помещаться последней среди своих братьев. Клиент MUST NOT иметь возможности задать ранг порядка напрямую.

Успешное создание MUST отвечать `201` и возвращать созданную страницу с её идентификатором, владельцем, проектом, родителем, заголовком, рангом и временными метками.

#### Scenario: Создание root-страницы
- **WHEN** аутентифицированный пользователь отправляет `POST /api/v1/pages` с идентификатором своего проекта и без идентификатора родителя
- **THEN** API отвечает `201` и возвращает страницу без родителя, принадлежащую этому пользователю и этому проекту
- **AND** страница появляется последней среди root-страниц дерева этого проекта

#### Scenario: Создание дочерней страницы
- **WHEN** пользователь отправляет `POST /api/v1/pages` с идентификатором своей существующей страницы в качестве родителя и проектом этого родителя
- **THEN** API отвечает `201`, возвращает страницу с этим родителем, тем же владельцем и тем же проектом
- **AND** страница появляется последней среди детей этого родителя

#### Scenario: Создание в чужом проекте
- **WHEN** пользователь указывает проект, принадлежащий другому пользователю
- **THEN** API отвечает `404` в едином формате HTTP-ошибок и не создаёт страницу

#### Scenario: Создание в несуществующем проекте
- **WHEN** пользователь указывает идентификатор проекта, которому не соответствует ни один проект
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при чужом проекте

#### Scenario: Проект запроса не совпадает с проектом родителя
- **WHEN** пользователь указывает свой проект и своего родителя, лежащего в другом своём проекте
- **THEN** API отвечает `400` в едином формате HTTP-ошибок и не создаёт страницу

#### Scenario: Создание страницы без заголовка
- **WHEN** запрос не содержит заголовок
- **THEN** API отвечает `201` и создаёт страницу с пустым заголовком, а не отклоняет запрос

#### Scenario: Создание с родителем из чужого дерева
- **WHEN** пользователь указывает родителем страницу, принадлежащую другому пользователю
- **THEN** API отвечает `404` в едином формате HTTP-ошибок и не создаёт страницу

#### Scenario: Создание с несуществующим родителем
- **WHEN** пользователь указывает родителем идентификатор, которому не соответствует ни одна страница
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при родителе из чужого дерева

#### Scenario: Создание с недопустимыми данными
- **WHEN** запрос не содержит идентификатор проекта, содержит идентификатор проекта или родителя не в формате UUID, заголовок длиннее допустимого либо лишнее поле
- **THEN** API отвечает `400` в едином формате HTTP-ошибок с перечнем validation messages и не создаёт страницу

#### Scenario: Создание без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и не создаёт страницу

### Requirement: Чтение дерева владельца
API MUST публиковать защищённый `GET /api/v1/pages`, возвращающий все неудалённые страницы текущего пользователя и только его. Ответ MUST передавать иерархию: у каждой страницы MUST быть перечислены её дочерние страницы.

Братья на каждом уровне MUST быть упорядочены по возрастанию ранга. Порядок MUST быть детерминированным: два последовательных чтения без изменяющих операций MUST возвращать одинаковую последовательность.

Пользователь без страниц MUST получать пустое дерево, а не ошибку.

#### Scenario: Чтение непустого дерева
- **WHEN** пользователь с несколькими уровнями вложенности запрашивает `GET /api/v1/pages`
- **THEN** API отвечает `200` и возвращает его root-страницы с вложенными потомками
- **AND** ответ не содержит ни одной страницы другого пользователя

#### Scenario: Чтение пустого дерева
- **WHEN** пользователь, не создавший ни одной страницы, запрашивает `GET /api/v1/pages`
- **THEN** API отвечает `200` и возвращает пустой список root-страниц

#### Scenario: Детерминированный порядок братьев
- **WHEN** пользователь дважды подряд запрашивает дерево, не выполняя между запросами изменяющих операций
- **THEN** порядок братьев на каждом уровне в обоих ответах совпадает

### Requirement: Чтение одной страницы
API MUST публиковать защищённый `GET /api/v1/pages/{pageId}`, возвращающий одну страницу текущего пользователя.

#### Scenario: Чтение своей страницы
- **WHEN** пользователь запрашивает страницу своего дерева
- **THEN** API отвечает `200` и возвращает её идентификатор, проект, родителя, заголовок, ранг и временные метки

#### Scenario: Чтение чужой страницы
- **WHEN** пользователь запрашивает страницу, принадлежащую другому пользователю
- **THEN** API отвечает `404` в едином формате HTTP-ошибок

#### Scenario: Чтение несуществующей страницы
- **WHEN** пользователь запрашивает идентификатор, которому не соответствует ни одна страница
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при чтении чужой страницы

### Requirement: Переименование страницы
API MUST публиковать защищённый `PATCH /api/v1/pages/{pageId}`, изменяющий заголовок страницы. Переименование MUST NOT изменять владельца, родителя, ранг и состав дерева.

Запрос MUST NOT позволять изменить владельца, проект, родителя, ранг, создателя или отметку удаления.

#### Scenario: Успешное переименование
- **WHEN** пользователь отправляет `PATCH /api/v1/pages/{pageId}` со своим идентификатором страницы и новым заголовком
- **THEN** API отвечает `200`, возвращает страницу с новым заголовком и обновлённой меткой изменения
- **AND** родитель, ранг и владелец страницы остаются прежними

#### Scenario: Переименование чужой страницы
- **WHEN** пользователь переименовывает страницу, принадлежащую другому пользователю
- **THEN** API отвечает `404` в едином формате HTTP-ошибок и не изменяет страницу

#### Scenario: Попытка изменить структурные поля переименованием
- **WHEN** запрос переименования содержит идентификатор владельца, проекта, родителя, ранг или отметку удаления
- **THEN** API отвечает `400` в едином формате HTTP-ошибок и не изменяет страницу

### Requirement: Перемещение поддерева и упорядочивание
API MUST публиковать защищённый `POST /api/v1/pages/{pageId}/move`, задающий нового родителя страницы и её место среди братьев. Пустой родитель MUST означать перенос страницы в корень дерева. Место среди братьев MUST задаваться соседями — страницей, после которой и страницей, перед которой должна оказаться перемещаемая; при отсутствии обоих соседей страница MUST становиться последней среди братьев. Клиент MUST NOT передавать ранг напрямую.

Перемещение MUST переносить всё поддерево: потомки перемещаемой страницы MUST сохранять своих родителей и свой относительный порядок.

Смена родителя и вычисление нового ранга MUST выполняться в одной транзакции. При отказе на любом шаге дерево MUST оставаться в состоянии, предшествовавшем запросу: ни родитель, ни ранг, ни какая-либо другая страница MUST NOT остаться изменёнными.

Перемещение MUST NOT изменять ни владельца, ни проект перемещаемой страницы и её потомков. Новый родитель MUST лежать в том же проекте, что и перемещаемая страница. Соседи MUST принадлежать тому же родителю, в который выполняется перенос. Соседи MUST задавать существующую щель: один и тот же идентификатор с обеих сторон и обратный порядок MUST отклоняться.

#### Scenario: Перемещение под другого родителя
- **WHEN** пользователь перемещает страницу под другую свою страницу
- **THEN** API отвечает `200`, страница появляется среди детей нового родителя и исчезает из прежнего уровня
- **AND** её потомки остаются её потомками в прежнем относительном порядке

#### Scenario: Перемещение в корень
- **WHEN** пользователь перемещает дочернюю страницу, не указывая родителя
- **THEN** API отвечает `200` и страница становится root-страницей дерева своего проекта
- **AND** её проект не изменяется

#### Scenario: Изменение позиции среди братьев
- **WHEN** пользователь перемещает страницу между двумя её соседями по тому же родителю
- **THEN** API отвечает `200` и последующее чтение дерева возвращает её ровно между указанными соседями
- **AND** ранги остальных братьев не изменяются

#### Scenario: Перемещение в конец уровня
- **WHEN** пользователь перемещает страницу, указывая нового родителя и не указывая ни одного соседа
- **THEN** страница становится последней среди детей этого родителя

#### Scenario: Перемещение в саму себя
- **WHEN** пользователь указывает перемещаемую страницу её собственным родителем
- **THEN** API отвечает `409` в едином формате HTTP-ошибок и не изменяет дерево

#### Scenario: Перемещение в собственного потомка
- **WHEN** пользователь указывает новым родителем страницу, являющуюся потомком перемещаемой на любой глубине
- **THEN** API отвечает `409` в едином формате HTTP-ошибок и не изменяет дерево

#### Scenario: Перемещение под родителя из чужого дерева
- **WHEN** пользователь указывает новым родителем страницу, принадлежащую другому пользователю
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, дерево не изменяется, и владелец перемещаемой страницы остаётся прежним

#### Scenario: Перемещение под родителя из другого проекта
- **WHEN** пользователь указывает новым родителем свою страницу, лежащую в другом его проекте
- **THEN** API отвечает `400` в едином формате HTTP-ошибок, дерево не изменяется, и проект перемещаемой страницы остаётся прежним

#### Scenario: Перемещение чужой страницы
- **WHEN** пользователь перемещает страницу, принадлежащую другому пользователю
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при перемещении несуществующей страницы

#### Scenario: Сосед из другого уровня
- **WHEN** указанный сосед существует в дереве пользователя, но принадлежит не тому родителю, в который выполняется перенос
- **THEN** API отвечает `400` в едином формате HTTP-ошибок и не изменяет дерево

#### Scenario: Противоречивая пара соседей
- **WHEN** оба соседа заданы одним и тем же идентификатором либо «предыдущий» лежит среди братьев не раньше «следующего»
- **THEN** API отвечает `400` в едином формате HTTP-ошибок и не изменяет дерево

#### Scenario: Несуществующий сосед
- **WHEN** указанный сосед не существует либо принадлежит другому пользователю
- **THEN** API отвечает `404` и не изменяет дерево

#### Scenario: Отказ в середине перемещения
- **WHEN** перемещение прерывается ошибкой после смены родителя, но до сохранения нового ранга
- **THEN** ни смена родителя, ни изменение ранга не сохраняются, и дерево остаётся в исходном состоянии

### Requirement: Источник удаления страницы
Каждая удалённая страница MUST хранить источник своего удаления: удалена ли она самостоятельно, вместе с родительской страницей или вместе со своим проектом. Источник MUST проставляться той операцией, которая удалила страницу, и MUST NOT приниматься от клиента.

Источник и отметка удаления MUST быть согласованы: страница без отметки удаления MUST NOT иметь источника, страница с отметкой удаления MUST иметь источник. Согласованность MUST быть закреплена на уровне базы данных, а не только проверкой в приложении.

Страница, удалённая ранее и самостоятельно, при последующем удалении её предка MUST сохранять источник «удалена самостоятельно» и MUST сохранять свою прежнюю отметку времени удаления. Повторное удаление уже удалённой страницы MUST NOT изменять ни её источник, ни её отметку времени.

Источник MUST определять, где страница показывается в корзине и что происходит при восстановлении её предка: страница с источником «удалена самостоятельно» MUST быть корнем корзины и MUST NOT восстанавливаться заодно с предком. Адресовать операцию восстановления MUST быть можно любой удалённой странице независимо от источника — источник задаёт границы восстановления, а не право на него.

#### Scenario: Источник у самостоятельно удалённой страницы
- **WHEN** пользователь удаляет свою страницу
- **THEN** у неё проставляется отметка удаления и источник «удалена самостоятельно»

#### Scenario: Источник у каскадно удалённого потомка
- **GIVEN** страница с потомками на нескольких уровнях
- **WHEN** пользователь удаляет эту страницу
- **THEN** у каждого её живого потомка на любой глубине проставляется отметка удаления и источник «удалена вместе с родительской страницей»

#### Scenario: Ранее удалённое поддерево не перемечается
- **GIVEN** страница `A` с потомком `B`, причём `B` удалена самостоятельно раньше
- **WHEN** пользователь удаляет `A`
- **THEN** `B` сохраняет источник «удалена самостоятельно» и прежнюю отметку времени удаления
- **AND** потомки `B` сохраняют источник «удалена вместе с родительской страницей» и свои прежние отметки времени

#### Scenario: Согласованность отметки и источника закреплена базой
- **WHEN** предпринимается попытка сохранить страницу с отметкой удаления без источника либо с источником без отметки удаления, в обход прикладных проверок
- **THEN** база данных отклоняет запись нарушением constraint

### Requirement: Мягкое удаление страницы
API MUST публиковать защищённый `DELETE /api/v1/pages/{pageId}`, помечающий страницу удалённой. Удаление MUST быть мягким: запись MUST оставаться в хранилище, и её идентификатор, владелец, проект, родитель, заголовок и ранг MUST оставаться неизменными.

Удаление MUST каскадно помечать всё живое поддерево удаляемой страницы на любой глубине. Пометка страницы и пометка её поддерева MUST выполняться в одной транзакции: при отказе на любом шаге ни одна страница MUST NOT остаться помеченной.

Успешное удаление MUST отвечать `204` без тела. Удаление уже удалённой, чужой или несуществующей страницы MUST отвечать `404` в едином формате HTTP-ошибок.

#### Scenario: Удаление страницы без потомков
- **WHEN** пользователь отправляет `DELETE /api/v1/pages/{pageId}` со своей страницей без потомков
- **THEN** API отвечает `204`
- **AND** последующие `GET /api/v1/pages` и `GET /api/v1/pages/{pageId}` эту страницу не возвращают

#### Scenario: Каскадное удаление поддерева
- **GIVEN** страница с детьми и внуками
- **WHEN** пользователь удаляет эту страницу
- **THEN** API отвечает `204`, и ни она, ни один её потомок не возвращаются чтением дерева и чтением одной страницы

#### Scenario: Соседнее поддерево не затрагивается
- **WHEN** пользователь удаляет одну из двух своих root-страниц
- **THEN** вторая root-страница и все её потомки остаются в выдаче дерева, и их ранги не изменяются

#### Scenario: Повторное удаление
- **WHEN** пользователь удаляет страницу, уже помеченную удалённой
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при удалении несуществующей страницы

#### Scenario: Удаление чужой страницы
- **WHEN** пользователь удаляет страницу, принадлежащую другому пользователю
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, и страница другого пользователя остаётся неудалённой

#### Scenario: Удаление без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и не удаляет страницу

#### Scenario: Отказ в середине каскада
- **WHEN** удаление прерывается ошибкой после пометки части поддерева
- **THEN** ни одна страница не остаётся помеченной, и дерево возвращается чтением в прежнем виде

### Requirement: Восстановление страницы
API MUST публиковать защищённый `POST /api/v1/pages/{pageId}/restore`, снимающий отметку удаления со страницы. Восстановление MUST снимать отметку с самой страницы и со всех её потомков, удалённых не самостоятельно, на любой глубине — тем же правилом, которым чтение корзины подвешивает узел к родителю. Спуск MUST останавливаться на потомках, удалённых самостоятельно: поддерево, удалённое раньше и отдельно, восстановлением предка MUST NOT восстанавливаться. Как следствие, восстановление возвращает ровно то, что корзина показывала вложенным в восстанавливаемую страницу.

Восстановление MUST возвращать страницу на прежнее место, когда её родительская страница жива: владелец, проект, родитель и ранг MUST оставаться теми же, что до удаления.

Если родительская страница остаётся удалённой, восстанавливаемая страница MUST становиться root-страницей своего проекта и MUST получать новый ранг последней среди его root-страниц. Её потомки MUST сохранять своих родителей и свой относительный порядок: поддерево поднимается целиком. Владелец и проект MUST оставаться прежними в обоих случаях, и восстановление MUST NOT изменять заголовок и содержимое документа.

Восстановление MUST выполняться в одной транзакции: при отказе на любом шаге ни одна страница MUST NOT остаться восстановленной, и ни один ранг MUST NOT остаться изменённым.

Восстановлению MUST подлежать любая удалённая страница, независимо от источника её удаления: страница, удалённая вместе с родительской, MUST NOT отклоняться, а MUST восстанавливаться и подниматься в корень своего проекта — её прежний родитель остался в корзине, и вернуть её на место некуда.

Страница, чей проект остаётся в корзине, MUST отвечать `409`: восстановление MUST NOT создавать живую страницу в удалённом проекте, а подъём в корень тут не помогает — корень принадлежит тому же удалённому проекту. Отказ MUST называть свою причину в теле ответа и MUST называть способ продолжить: восстановить проект либо указать другой.

Запрос MUST принимать необязательный идентификатор проекта назначения. Он MUST приниматься только когда собственный проект страницы лежит в корзине; в остальных случаях запрос MUST отвечать `400`, потому что иначе восстановление стало бы обходным путём для переноса между проектами. Проект назначения MUST принадлежать текущему пользователю и MUST быть неудалённым; чужой, удалённый и несуществующий MUST отвечать одинаковым `404`.

При указанном проекте назначения восстановление MUST переносить в него всё физическое поддерево восстанавливаемой страницы — включая вложенные поддеревья, которые остаются удалёнными: страница не может лежать в одном проекте, а её родитель в другом, и оставить их позади MUST NOT быть возможно. Восстанавливаемая страница MUST становиться root-страницей проекта назначения и MUST получать новый ранг последней среди его root-страниц. Перенос и снятие отметки MUST выполняться в одной транзакции.

Успешное восстановление MUST отвечать `200` и возвращать восстановленную страницу. Восстановление неудалённой, чужой или несуществующей страницы MUST отвечать `404` в едином формате HTTP-ошибок.

#### Scenario: Восстановление поддерева целиком
- **GIVEN** страница с детьми и внуками, удалённая одной операцией
- **WHEN** пользователь отправляет `POST /api/v1/pages/{pageId}/restore`
- **THEN** API отвечает `200` и возвращает восстановленную страницу
- **AND** чтение дерева возвращает её и всех её потомков с прежними родителями и в прежнем относительном порядке

#### Scenario: Ранее удалённое поддерево не воскресает
- **GIVEN** страница `A` с потомком `B`, причём `B` удалена самостоятельно раньше, а затем удалена `A`
- **WHEN** пользователь восстанавливает `A`
- **THEN** API отвечает `200`, и `A` и её потомки, кроме `B`, возвращаются чтением дерева
- **AND** ни `B`, ни её потомки чтением дерева не возвращаются

#### Scenario: Восстановление каскадно удалённого потомка
- **GIVEN** страница `A` с потомком `C`, удалённая одной операцией
- **WHEN** пользователь восстанавливает `C`
- **THEN** API отвечает `200`, и `C` возвращается чтением дерева root-страницей своего проекта
- **AND** её собственное поддерево возвращается вместе с ней
- **AND** `A` остаётся в корзине

#### Scenario: Поднятая страница не трогается восстановлением прежнего предка
- **GIVEN** страница `C`, поднятая в корень восстановлением из-под удалённого предка `A`
- **WHEN** пользователь затем восстанавливает `A`
- **THEN** `C` остаётся root-страницей и не возвращается под `A`

#### Scenario: Восстановление под удалённым родителем поднимает страницу в корень
- **GIVEN** страница `B` с потомками, удалённая самостоятельно, чей родитель `A` затем удалён и не восстановлен
- **WHEN** пользователь восстанавливает `B`
- **THEN** API отвечает `200`, и `B` возвращается чтением дерева root-страницей своего проекта без родителя
- **AND** потомки `B` остаются её потомками в прежнем относительном порядке
- **AND** `A` остаётся удалённой

#### Scenario: Поднятая в корень страница встаёт последней
- **GIVEN** проект с несколькими root-страницами
- **WHEN** пользователь восстанавливает страницу, чей родитель остаётся удалённым
- **THEN** она появляется последней среди root-страниц этого проекта
- **AND** ранги остальных root-страниц не изменяются

#### Scenario: Восстановление в удалённом проекте без проекта назначения
- **WHEN** пользователь восстанавливает страницу, чей проект помечен удалённым, не указывая проект назначения
- **THEN** API отвечает `409` в едином формате HTTP-ошибок, называет причину и способ продолжить, и страница остаётся удалённой

#### Scenario: Восстановление из удалённого проекта в другой проект
- **GIVEN** удалённый проект, в корзине которого лежит страница `C` с вложенной веткой
- **WHEN** пользователь восстанавливает `C`, указав другой свой живой проект
- **THEN** API отвечает `200`, и `C` возвращается чтением дерева root-страницей указанного проекта последней среди его root-страниц
- **AND** ветка, которую корзина показывала вложенной в `C`, возвращается вместе с ней и лежит в том же проекте
- **AND** исходный проект остаётся в корзине

#### Scenario: Удалённое поддерево едет за переносимой страницей
- **GIVEN** страница `C` в удалённом проекте, внутри поддерева которой лежит удалённая раньше и самостоятельно страница `B`
- **WHEN** пользователь восстанавливает `C` в другой проект
- **THEN** `B` остаётся удалённой, но её проектом становится проект назначения
- **AND** последующее восстановление `B` возвращает её в проект назначения

#### Scenario: Проект назначения у страницы из живого проекта
- **WHEN** пользователь указывает проект назначения, восстанавливая страницу, чей собственный проект не удалён
- **THEN** API отвечает `400` в едином формате HTTP-ошибок и не восстанавливает страницу

#### Scenario: Недоступный проект назначения
- **WHEN** пользователь указывает проектом назначения чужой, удалённый либо несуществующий проект
- **THEN** API отвечает одинаковым `404` во всех трёх случаях и не восстанавливает страницу

#### Scenario: Восстановление неудалённой страницы
- **WHEN** пользователь восстанавливает страницу, не помеченную удалённой
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при восстановлении несуществующей страницы

#### Scenario: Восстановление чужой страницы
- **WHEN** пользователь восстанавливает удалённую страницу другого пользователя
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, и страница другого пользователя остаётся удалённой

#### Scenario: Удаление и восстановление обратимы
- **WHEN** пользователь удаляет страницу и сразу восстанавливает её
- **THEN** чтение дерева возвращает то же дерево, что и до удаления: те же родители, тот же порядок братьев и то же содержимое документов

### Requirement: Чтение корзины страниц
API MUST публиковать защищённый `GET /api/v1/pages/trash`, возвращающий удалённые страницы текущего пользователя и только его. Ответ MUST иметь ту же форму, что и обычное чтение дерева: у каждого узла MUST быть перечислены его дочерние узлы.

Выдача MUST содержать все удалённые страницы текущего пользователя, независимо от источника удаления, — включая страницы, удалённые вместе с проектом. Отдельного чтения удалённых страниц у проектов MUST NOT быть: корзина страниц — единственное место, где видно удалённые страницы.

Вложенность MUST задаваться одним правилом: страница MUST быть вложена в свою родительскую страницу тогда и только тогда, когда она удалена не самостоятельно и её родительская страница тоже удалена. Все остальные удалённые страницы MUST быть корнями выдачи. Как следствие, страница, удалённая самостоятельно, MUST быть корнем даже когда её родитель тоже удалён, а страницы удалённого проекта MUST сохранять свою вложенность, и корнями от них MUST становиться только root-страницы этого проекта.

Каждый узел MUST попадать в выдачу ровно один раз. Неудалённые страницы MUST NOT попадать в эту выдачу. Каждый узел MUST содержать отметку времени удаления и идентификатор своего проекта — по нему клиент сопоставляет узел со списком удалённых проектов и заранее понимает, что отдельное восстановление такой страницы отклоняется.

Порядок MUST быть детерминированным и задаваться разными правилами на разных уровнях. Корни выдачи MUST быть упорядочены по убыванию отметки времени удаления: недавно удалённое идёт первым. Корни не являются братьями — они приходят с разных уровней живого дерева, и их ранги друг с другом несравнимы, поэтому по рангу они MUST NOT упорядочиваться. Вложенные узлы на каждом уровне MUST быть упорядочены по возрастанию ранга: они настоящие братья и их ранги сравнимы.

Пользователь без удалённых страниц MUST получать пустой список, а не ошибку.

#### Scenario: Чтение непустой корзины
- **GIVEN** пользователь удалил страницу с детьми и внуками
- **WHEN** он запрашивает `GET /api/v1/pages/trash`
- **THEN** API отвечает `200` и возвращает удалённую страницу корнем выдачи с вложенными в неё потомками
- **AND** ответ не содержит ни одной неудалённой страницы и ни одной страницы другого пользователя

#### Scenario: Отдельно удалённое поддерево — отдельный корень
- **GIVEN** страница `A` с потомком `B`, причём `B` удалена самостоятельно раньше, а затем удалена `A`
- **WHEN** пользователь запрашивает корзину
- **THEN** `A` и `B` возвращаются двумя разными корнями выдачи
- **AND** `B` не вложена в `A`, хотя ссылка `B` на родителя по-прежнему указывает на `A`
- **AND** `A` идёт раньше `B`, потому что удалена позже

#### Scenario: Порядок корней не зависит от их рангов
- **GIVEN** два корня корзины, пришедшие с разных уровней живого дерева и имеющие одинаковый ранг
- **WHEN** пользователь запрашивает корзину
- **THEN** они возвращаются в порядке убывания отметки времени удаления
- **AND** два последовательных чтения без изменяющих операций возвращают одинаковую последовательность

#### Scenario: Страницы удалённого проекта видны деревом
- **GIVEN** проект с деревом страниц на нескольких уровнях
- **WHEN** пользователь удаляет проект и запрашивает `GET /api/v1/pages/trash`
- **THEN** ответ содержит все страницы этого проекта с сохранённой вложенностью
- **AND** корнями от них выступают только root-страницы этого проекта, а не каждая его страница по отдельности

#### Scenario: Чтение пустой корзины
- **WHEN** пользователь, не удаливший ни одной страницы, запрашивает корзину
- **THEN** API отвечает `200` и возвращает пустой список

#### Scenario: Чтение корзины без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок

### Requirement: Окончательное удаление страницы по запросу пользователя
API MUST публиковать защищённый `DELETE /api/v1/pages/trash/{pageId}`, безвозвратно удаляющий страницу из хранилища.

Окончательное удаление — и страницы, и проекта — MUST подчиняться одному правилу: если операция уничтожает записи, которые парное чтение корзины показывало **не** внутри удаляемого, она MUST отказать, пока вызывающий не подтвердит это явно.

Удаление MUST уносить документ страницы и всё её физическое поддерево на любой глубине, включая страницы, удалённые раньше и самостоятельно: вне своего родителя страница существовать не может, и сохранить её MUST NOT быть возможно.

Такие страницы корзина показывает отдельными корнями, а не содержимым удаляемой страницы, поэтому их уничтожение MUST требовать явного подтверждения. Запрос без подтверждения MUST отвечать `409` и MUST называть причину.

Отказ MUST перечислять обречённые страницы поимённо: тело ответа MUST содержать заголовки всех страниц, которые будут уничтожены сверх нарисованного, — их достаточно, чтобы показать пользователю, что именно он теряет. Перечень MUST передаваться в едином формате HTTP-ошибок и MUST NOT требовать от клиента разбора строки. Заголовки MUST отдаваться такими, как хранятся, включая пустые.

Повторный запрос с подтверждением MUST выполнять удаление целиком. Подтверждение MUST передаваться отдельным явным параметром запроса и MUST NOT подразумеваться по умолчанию.

Страница, внутри поддерева которой нет отдельно удалённых страниц, MUST удаляться без подтверждения: всё уничтожаемое корзина показывала вложенным в неё.

Операция MUST быть доступна для любой страницы, которую показывает чтение корзины страниц, — независимо от источника удаления и от того, корень это выдачи или вложенный в неё узел. Отказ по источнику удаления MUST NOT применяться: всё удалённое видно в корзине, и что видно, то MUST быть можно удалить навсегда.

Неудалённая, чужая или несуществующая страница MUST отвечать `404` в едином формате HTTP-ошибок — окончательное удаление MUST NOT быть способом убрать живую страницу в обход мягкого удаления.

Операция MUST быть необратимой: после неё страница MUST NOT возвращаться ни одним чтением, включая чтение корзины, и её восстановление MUST отвечать `404`.

Удаление MUST выполняться в одной транзакции: при отказе на любом шаге ни одна страница MUST NOT исчезнуть из хранилища.

#### Scenario: Окончательное удаление поддерева
- **GIVEN** удалённая страница с детьми и внуками
- **WHEN** пользователь отправляет `DELETE /api/v1/pages/trash/{pageId}`
- **THEN** API отвечает `204`
- **AND** ни страница, ни её потомки, ни их документы не возвращаются ни обычным чтением, ни чтением корзины
- **AND** последующее восстановление этой страницы отвечает `404`

#### Scenario: Отказ без подтверждения
- **GIVEN** удалённая страница `A`, внутри поддерева которой лежит удалённая раньше и самостоятельно страница `B` со своими потомками
- **WHEN** пользователь окончательно удаляет `A` без явного подтверждения
- **THEN** API отвечает `409` в едином формате HTTP-ошибок, называет причину и перечисляет заголовки страниц, которые будут уничтожены дополнительно
- **AND** перечень содержит заголовок `B`
- **AND** ни `A`, ни `B` не исчезают из хранилища

#### Scenario: Удаление с подтверждением
- **GIVEN** та же страница `A` и тот же отказ
- **WHEN** пользователь повторяет запрос с явным подтверждением
- **THEN** API отвечает `204`, и `A`, `B` и все их потомки исчезают из хранилища
- **AND** `B` перестаёт быть корнем корзины

#### Scenario: Поддерево без отдельно удалённых страниц не требует подтверждения
- **GIVEN** удалённая страница, всё поддерево которой было удалено вместе с ней
- **WHEN** пользователь окончательно удаляет её без подтверждения
- **THEN** API отвечает `204` и удаляет её вместе со всем поддеревом

#### Scenario: Окончательное удаление ветки внутри корзины
- **GIVEN** удалённая страница `A`, внутри которой чтение корзины показывает вложенную ветку `C` с потомками
- **WHEN** пользователь окончательно удаляет `C`
- **THEN** API отвечает `204`, и `C` с потомками исчезает из хранилища
- **AND** `A` и остальные её вложенные ветки остаются в корзине и по-прежнему подлежат восстановлению
- **AND** последующее восстановление `A` возвращает её без ветки `C`

#### Scenario: Окончательное удаление страницы удалённого проекта
- **GIVEN** удалённый проект, чьи страницы показываются в корзине страниц
- **WHEN** пользователь окончательно удаляет одну из них
- **THEN** API отвечает `204`, и эта страница с потомками исчезает из хранилища
- **AND** проект остаётся в корзине проектов и по-прежнему подлежит восстановлению
- **AND** восстановление проекта возвращает его оставшиеся страницы

#### Scenario: Окончательное удаление живой страницы
- **WHEN** пользователь адресует этой операцией страницу, не помеченную удалённой
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, и страница остаётся в дереве

#### Scenario: Окончательное удаление чужой страницы
- **WHEN** пользователь адресует этой операцией удалённую страницу другого пользователя
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при несуществующей странице, и страница другого пользователя остаётся в хранилище

#### Scenario: Окончательное удаление без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и ничего не удаляет

### Requirement: Очистка корзины страниц
API MUST публиковать защищённый `DELETE /api/v1/pages/trash`, безвозвратно удаляющий из хранилища всё, что возвращает чтение корзины страниц того же пользователя, вместе с поддеревьями и документами.

Очистка MUST затрагивать только записи текущего пользователя и MUST NOT затрагивать неудалённые страницы. Страницы удалённых проектов MUST удаляться наравне с остальными: корзина страниц показывает их, а очистка удаляет ровно то, что показывает парное ей чтение. Сами проекты при этом MUST оставаться в корзине проектов и MUST оставаться восстановимыми — восстановленный проект MUST возвращаться пустым, если все его страницы были очищены.

Очистка MUST быть идемпотентной: вызов на пустой корзине MUST отвечать успехом, а не ошибкой. Успешная очистка MUST отвечать `204` без тела.

#### Scenario: Очистка непустой корзины
- **GIVEN** пользователь удалил несколько страниц с потомками
- **WHEN** он отправляет `DELETE /api/v1/pages/trash`
- **THEN** API отвечает `204`, и последующее чтение корзины возвращает пустой список
- **AND** ни одна из этих страниц и ни один их документ не остаются в хранилище

#### Scenario: Очистка не трогает живое дерево
- **WHEN** пользователь очищает корзину страниц
- **THEN** чтение дерева возвращает то же дерево, что и до очистки

#### Scenario: Очистка уносит и страницы удалённого проекта
- **GIVEN** пользователь удалил проект со страницами
- **WHEN** он очищает корзину страниц
- **THEN** страницы этого проекта исчезают из хранилища
- **AND** сам проект остаётся в списке удалённых проектов, а его восстановление отвечает `200` и возвращает проект без страниц

#### Scenario: Очистка не трогает чужую корзину
- **WHEN** пользователь очищает свою корзину страниц
- **THEN** удалённые страницы других пользователей остаются в хранилище

#### Scenario: Очистка пустой корзины
- **WHEN** пользователь, не удаливший ни одной страницы, отправляет `DELETE /api/v1/pages/trash`
- **THEN** API отвечает `204` и ничего не изменяет

#### Scenario: Очистка корзины без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и ничего не удаляет

### Requirement: Изоляция дерева по владельцу
Ни одна операция над страницами MUST NOT раскрывать существование страницы или проекта другого пользователя. Для чужой и для несуществующей записи API MUST отвечать одинаковым HTTP status `404` и одинаковым телом ответа — это относится и к самой адресуемой странице, и к идентификаторам проекта, родителя и соседей внутри тела запроса.

Удалённая страница и удалённый проект MUST быть неотличимы от несуществующих во всех операциях, кроме чтения корзины и восстановления: создание, чтение, переименование и перемещение MUST отвечать на них тем же `404` и тем же телом, что и на несуществующие. Удалённая страница MUST NOT быть ни родителем создаваемой страницы, ни целью и ни соседом перемещения.

Ответ `403` на маршрутах страниц MUST NOT использоваться: он отличал бы существующую чужую страницу от несуществующей.

Ни одна операция MUST NOT изменять владельца существующей страницы. Передача владения MUST NOT быть доступна через маршруты страниц.

Проект страницы MUST NOT изменяться ничем, кроме восстановления страницы из удалённого проекта, и только в живой проект того же владельца. Создание, чтение, переименование, перемещение и удаление MUST оставлять проект неизменным; отдельной операции переноса между проектами MUST NOT быть.

#### Scenario: Чужая и несуществующая страница неразличимы
- **WHEN** пользователь адресует чужую страницу и затем идентификатор, которому не соответствует ни одна страница, одной и той же операцией
- **THEN** оба ответа имеют одинаковый статус `404` и одинаковое тело

#### Scenario: Удалённая и несуществующая страница неразличимы
- **WHEN** пользователь адресует свою удалённую страницу и затем идентификатор, которому не соответствует ни одна страница, операцией чтения, переименования или перемещения
- **THEN** оба ответа имеют одинаковый статус `404` и одинаковое тело

#### Scenario: Удалённая страница не принимается родителем или соседом
- **WHEN** пользователь указывает удалённую страницу родителем создаваемой страницы либо родителем или соседом при перемещении
- **THEN** API отвечает `404` в едином формате HTTP-ошибок и не изменяет дерево

#### Scenario: Отсутствие ответа о запрете
- **WHEN** аутентифицированный пользователь выполняет любую операцию над страницами с идентификатором из чужого дерева
- **THEN** API не отвечает статусом `403`

#### Scenario: Владелец не меняется существующими операциями
- **WHEN** пользователь выполняет создание, переименование, перемещение или удаление
- **THEN** идентификаторы владельца и проекта затронутых страниц остаются неизменными
- **AND** владелец не изменяется и восстановлением

### Requirement: Документирование операций страниц в OpenAPI
Опубликованный OpenAPI-документ MUST описывать каждую операцию над страницами со стабильным явным operation ID, schema тела запроса, schema успешного ответа и документированными ответами `400`, `401`, `404`, а для перемещения, восстановления и окончательного удаления одной страницы — дополнительно `409`. Операции мягкого удаления, окончательного удаления и очистки корзины MUST документировать ответ `204` без тела, а окончательное удаление — ещё и параметр подтверждения. Каждая операция MUST быть помечена bearer-схемой безопасности. Закоммиченный OpenAPI snapshot и сгенерированный из него frontend-код MUST соответствовать этим операциям.

#### Scenario: Операции страниц в OpenAPI-документе
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ содержит paths операций страниц с явными operation ID, schemas запросов и ответов и bearer-схемой безопасности

#### Scenario: Операции корзины в OpenAPI-документе
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ содержит операции мягкого удаления, восстановления, чтения корзины, окончательного удаления страницы и очистки корзины страниц с явными operation ID и документированными ответами

#### Scenario: Отсутствие contract drift
- **WHEN** выполняется обязательная проверка соответствия сгенерированных артефактов
- **THEN** закоммиченные `openapi.json` и сгенерированный web-код совпадают с текущей Nest metadata
