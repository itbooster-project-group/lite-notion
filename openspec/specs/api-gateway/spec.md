# api-gateway Specification

## Purpose

Определяет единую точку входа Lite Notion: как внешний трафик попадает в систему, как запросы аутентифицируются до попадания в сервисы, как личность пользователя передаётся вниз по стеку и почему внутренние маршруты недостижимы снаружи.

## Requirements

### Requirement: Шлюз является единственным публичным входом

Система MUST публиковать за пределы периметра развёртывания ровно один сетевой адрес — адрес шлюза. Порты web-приложения, API и collaboration runtime MUST NOT быть достижимы извне периметра ни прямо, ни через перенаправление.

Граница периметра задаётся окружением. В production ею MUST быть сеть развёртывания: сервисы не публикуют портов наружу. В development сервисы запускаются процессами на машине разработчика, и периметром MUST считаться сама эта машина: их порты остаются доступны локально, и это MUST NOT приниматься за нарушение требования.

Шлюз MUST маршрутизировать запросы по префиксу пути: корневой префикс — во frontend, префикс публичного API — в API, префикс collaboration — в collaboration runtime. Маршрутизация MUST определяться конфигурацией шлюза и MUST NOT зависеть от содержимого запроса.

Поскольку все три адресата доступны через один origin, cross-origin запросы между frontend и backend MUST перестать возникать, а конфигурация CORS и проверка `Origin` MUST NOT оставаться единственным средством разграничения.

#### Scenario: Запрос к frontend проходит через шлюз
- **WHEN** браузер запрашивает корневой путь у адреса шлюза
- **THEN** шлюз передаёт запрос web-приложению и возвращает его ответ

#### Scenario: Запрос к API проходит через шлюз
- **WHEN** клиент запрашивает путь публичного API у адреса шлюза
- **THEN** шлюз передаёт запрос API и возвращает его ответ

#### Scenario: Прямое обращение к сервису извне периметра невозможно
- **WHEN** клиент вне периметра развёртывания обращается к порту API или collaboration runtime напрямую
- **THEN** соединение не устанавливается

#### Scenario: Локальный запуск не публикует сервисы наружу
- **WHEN** окружение запущено в development, где сервисы работают процессами на машине разработчика
- **THEN** за пределы этой машины опубликован только порт шлюза

### Requirement: Граница аутентификации проходит по префиксу публичного API

Шлюз MUST применять аутентификацию только к запросам под префиксом публичного API. Запросы к frontend — документ приложения, его статические ресурсы и ресурсы сборщика — MUST проходить без проверки токена: это публично раздаваемая статика, не содержащая ни данных пользователя, ни секретов, и требовать для неё токен означало бы сделать недостижимой саму страницу входа.

Приватность экранов приложения MUST оставаться ответственностью frontend: шлюз MUST NOT разграничивать доступ к маршрутам SPA. Пользователь без токена MUST получать приложение, которое само приводит его к экрану входа.

Маршрут collaboration MUST быть вне границы аутентификации по отдельной причине, изложенной ниже: предъявить токен на этапе смены протокола невозможно.

#### Scenario: Страница приложения открывается без токена
- **WHEN** неаутентифицированный пользователь открывает адрес шлюза
- **THEN** шлюз отдаёт документ приложения, не требуя токен

#### Scenario: Статические ресурсы приложения доступны без токена
- **WHEN** браузер загружает скрипты, стили и ресурсы сборщика, на которые ссылается документ приложения
- **THEN** шлюз отдаёт их, не требуя токен

#### Scenario: Неаутентифицированный пользователь доходит до экрана входа
- **WHEN** пользователь без токена открывает адрес приватного экрана приложения
- **THEN** приложение загружается и приводит пользователя к экрану входа
- **AND** шлюз не отвечает `401` на запрос самого экрана

### Requirement: Шлюз аутентифицирует запросы к публичному API, делегируя проверку API

Шлюз MUST аутентифицировать каждый запрос к защищённому маршруту публичного API до передачи его адресату. Проверку access-токена шлюз MUST делегировать внутреннему эндпоинту API и MUST NOT выполнять её сам: единственная реализация верификации подписи MUST оставаться в API, а подписывающий секрет MUST существовать ровно в одном процессе.

Запрос с отсутствующим, malformed, истёкшим или неверно подписанным токеном MUST отклоняться шлюзом со статусом `401` и MUST NOT доходить до адресата.

Ответ внутреннего эндпоинта проверки MUST содержать идентификатор пользователя и идентификатор сессии при успехе и MUST NOT содержать сам токен.

#### Scenario: Запрос с действующим токеном проходит
- **WHEN** клиент отправляет запрос к защищённому маршруту публичного API с действующим access-токеном
- **THEN** шлюз получает подтверждение от API и передаёт запрос адресату

#### Scenario: Запрос без токена отклоняется шлюзом
- **WHEN** клиент отправляет запрос к защищённому маршруту публичного API без access-токена
- **THEN** шлюз отвечает `401`
- **AND** запрос не доходит до адресата

#### Scenario: Запрос с недействительным токеном отклоняется шлюзом
- **WHEN** клиент отправляет запрос с истёкшим, malformed или неверно подписанным токеном
- **THEN** шлюз отвечает `401`
- **AND** запрос не доходит до адресата

#### Scenario: Проверка подписи не дублируется
- **WHEN** запрос аутентифицируется шлюзом
- **THEN** проверку подписи выполняет код API
- **AND** конфигурация шлюза не содержит подписывающий секрет

### Requirement: Маршруты входа внутри публичного API проходят без аутентификации

Внутри префикса публичного API шлюз MUST пропускать без проверки токена маршруты, которые по своей природе вызываются неаутентифицированным клиентом: регистрация, вход, обновление пары токенов и health endpoint. Перечень MUST быть явным: маршрут публичного API, в него не попавший, MUST считаться защищённым.

Обновление пары токенов MUST оставаться доступным при истёкшем access-токене: оно предъявляет refresh-токен, а не access-токен, и требование действующего access-токена сделало бы обновление невозможным ровно тогда, когда оно нужно.

#### Scenario: Вход доступен без токена
- **WHEN** неаутентифицированный клиент вызывает маршрут входа
- **THEN** шлюз передаёт запрос API без проверки токена

#### Scenario: Обновление токенов доступно с истёкшим access-токеном
- **WHEN** клиент вызывает маршрут обновления пары токенов, имея истёкший access-токен
- **THEN** шлюз передаёт запрос API без проверки access-токена
- **AND** клиент получает новую пару токенов

#### Scenario: Маршрут публичного API вне перечня защищён по умолчанию
- **WHEN** клиент вызывает маршрут публичного API, не перечисленный как публичный, без токена
- **THEN** шлюз отвечает `401`

### Requirement: Шлюз передаёт личность заголовками и затирает клиентские копии

При успешной аутентификации шлюз MUST добавлять к запросу заголовки с идентификатором пользователя и идентификатором сессии. Адресаты MUST считать эти заголовки доверенным источником личности.

Шлюз MUST безусловно удалять или перезаписывать эти заголовки, полученные от клиента, на каждом маршруте — включая публичные, где аутентификация не выполняется. Клиент MUST NOT иметь возможности повлиять на значение личности, дошедшее до сервиса.

#### Scenario: Личность доходит до сервиса
- **WHEN** запрос с действующим токеном проходит аутентификацию
- **THEN** адресат получает заголовки с идентификатором пользователя и сессии, соответствующими предъявленному токену

#### Scenario: Клиентская подмена личности не проходит
- **WHEN** клиент сам отправляет заголовки с идентификатором пользователя и действующий токен другого пользователя
- **THEN** адресат получает личность из токена, а не из клиентских заголовков

#### Scenario: Клиентская личность не проходит и на публичном маршруте
- **WHEN** клиент отправляет заголовки с идентификатором пользователя на публичный маршрут без токена
- **THEN** адресат не получает эти заголовки

### Requirement: Шлюз пропускает WebSocket upgrade без аутентификации

Шлюз MUST пропускать HTTP-запрос смены протокола на маршруте collaboration, сохраняя заголовки согласования WebSocket, и MUST поддерживать установленное соединение открытым.

Шлюз MUST NOT пытаться аутентифицировать WebSocket-соединение: access-токен передаётся первым кадром внутри протокола и в запросе upgrade отсутствует. Ответственность за аутентификацию такого соединения MUST оставаться на collaboration runtime.

Таймаут простоя на этом маршруте MUST превышать интервал keepalive протокола, иначе шлюз разрывает исправные соединения. Буферизация ответа на этом маршруте MUST быть отключена.

#### Scenario: Соединение устанавливается через шлюз
- **WHEN** клиент открывает WebSocket-соединение к маршруту collaboration через шлюз
- **THEN** согласование протокола завершается успешно и соединение остаётся открытым

#### Scenario: Шлюз не отклоняет upgrade без токена
- **WHEN** запрос upgrade не содержит access-токен ни в одном заголовке
- **THEN** шлюз передаёт запрос collaboration runtime, а не отвечает `401`

#### Scenario: Простаивающее соединение не разрывается шлюзом
- **WHEN** по установленному соединению не передаются данные дольше одного интервала keepalive
- **THEN** соединение остаётся открытым

### Requirement: Внутренние маршруты недостижимы снаружи

Маршруты, предназначенные для обращений между сервисами — проверка токена для шлюза, проверка доступа к странице и операции над содержимым документа, — MUST NOT быть доступны через шлюз. Обращение к ним снаружи периметра MUST отклоняться шлюзом до передачи адресату.

Внутренние маршруты MUST NOT попадать в публикуемый OpenAPI-документ.

#### Scenario: Внутренний маршрут не проходит через шлюз
- **WHEN** внешний клиент обращается к внутреннему маршруту через адрес шлюза
- **THEN** шлюз отклоняет запрос и не передаёт его адресату

#### Scenario: Внутренние маршруты не документируются публично
- **WHEN** клиент читает опубликованный OpenAPI-документ
- **THEN** он не содержит описания внутренних маршрутов
