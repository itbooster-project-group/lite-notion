# page-documents Specification

## Purpose

Определяет наблюдаемый контракт содержимого страницы Lite Notion: как документ появляется вместе со страницей, как его содержимое читается и заменяется, и как он исчезает вместе со страницей. Содержимое хранится как Yjs state и передаётся клиенту без интерпретации на сервере.

## Requirements

### Requirement: Документ существует ровно у одной страницы
Каждая страница MUST иметь ровно один документ, создаваемый в той же транзакции, что и сама страница. Отдельная операция создания документа MUST NOT существовать: документ не может появиться без страницы и страница не может появиться без документа.

Создаваемый документ MUST инициализироваться пустым содержимым: пустым Yjs state и текущей версией Tiptap-схемы.

Документ MUST удаляться вместе со своей страницей и MUST NOT удаляться отдельной операцией.

#### Scenario: Документ создаётся вместе со страницей
- **WHEN** пользователь создаёт страницу
- **THEN** у созданной страницы существует документ с пустым содержимым и текущей версией Tiptap-схемы

#### Scenario: Отдельного создания документа нет
- **WHEN** клиент ищет операцию создания документа в опубликованном API
- **THEN** такой операции нет: единственный способ получить документ — создать страницу

#### Scenario: Документ исчезает вместе со страницей
- **WHEN** строка страницы удаляется из базы
- **THEN** её документ удаляется тем же действием и не остаётся сиротой

### Requirement: Чтение содержимого документа
API MUST публиковать защищённый `GET /api/v1/pages/{pageId}/document`, возвращающий содержимое документа страницы, к которой у текущего пользователя есть эффективный доступ: Yjs state и версию Tiptap-схемы. Роли `viewer` MUST хватать. Yjs state MUST передаваться в кодировке base64.

Документ никогда не записанной страницы MUST возвращаться как пустой, а не как ошибка.

#### Scenario: Чтение записанного документа
- **WHEN** пользователь запрашивает документ своей страницы, содержимое которой ранее было записано
- **THEN** API отвечает `200` и возвращает ровно тот Yjs state, который был записан последним, и его версию Tiptap-схемы

#### Scenario: Чтение пустого документа
- **WHEN** пользователь запрашивает документ только что созданной страницы
- **THEN** API отвечает `200` и возвращает пустой Yjs state, а не ошибку

#### Scenario: Чтение документа по прямому разрешению
- **GIVEN** пользователю выдан `viewer` на чужой странице
- **WHEN** он запрашивает документ этой страницы
- **THEN** API отвечает `200` и возвращает его содержимое

#### Scenario: Чтение документа по унаследованному разрешению
- **GIVEN** пользователю выдан `viewer` на чужой странице, а запрашиваемый документ принадлежит её потомку в режиме `inherit`
- **THEN** API отвечает `200` и возвращает содержимое документа этого потомка

#### Scenario: Чтение документа чужой страницы
- **WHEN** пользователь запрашивает документ страницы, на которую ему ничего не выдано
- **THEN** API отвечает `404` в едином формате HTTP-ошибок

#### Scenario: Чтение документа несуществующей страницы
- **WHEN** пользователь запрашивает документ по идентификатору, которому не соответствует ни одна страница
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при странице, на которую ничего не выдано

#### Scenario: Чтение документа без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок

### Requirement: Замена содержимого документа
API MUST публиковать защищённый `PUT /api/v1/pages/{pageId}/document`, принимающий Yjs state в кодировке base64 и версию Tiptap-схемы. Запись MUST заменять содержимое целиком.

Запись MUST требовать роли `editor` или выше. Роли `viewer` MUST NOT хватать: она даёт чтение и только его.

Сервер MUST NOT интерпретировать, разбирать и валидировать структуру Yjs state сверх проверки того, что это корректный base64 допустимого размера: содержимое непрозрачно для API.

Размер принимаемого содержимого MUST быть ограничен, и превышение предела MUST отклоняться, не приводя к частичной записи.

Успешная запись MUST отвечать `200` и возвращать сохранённое содержимое.

#### Scenario: Первая запись содержимого
- **WHEN** пользователь отправляет `PUT /api/v1/pages/{pageId}/document` с непустым Yjs state для своей страницы
- **THEN** API отвечает `200`, а последующее чтение возвращает ровно этот state

#### Scenario: Повторная запись заменяет содержимое
- **WHEN** пользователь записывает содержимое дважды подряд разными значениями
- **THEN** последующее чтение возвращает содержимое второй записи, а не объединение обеих

#### Scenario: Запись пустого содержимого
- **WHEN** пользователь записывает пустой Yjs state
- **THEN** API отвечает `200` и последующее чтение возвращает пустое содержимое

#### Scenario: Запись редактором
- **GIVEN** пользователю выдан `editor` на чужой странице
- **WHEN** он записывает содержимое её документа
- **THEN** API отвечает `200`, и владелец страницы читает записанное им содержимое

#### Scenario: Запись читателем
- **GIVEN** пользователю выдан `viewer` на чужой странице
- **WHEN** он пытается записать содержимое её документа
- **THEN** API отвечает `403` в едином формате HTTP-ошибок, и ранее сохранённое содержимое остаётся неизменным

#### Scenario: Запись содержимого сверх предела размера
- **WHEN** тело запроса превышает установленный предел размера содержимого
- **THEN** API отвечает ошибкой в едином формате HTTP-ошибок, и ранее сохранённое содержимое остаётся неизменным

#### Scenario: Запись некорректного содержимого
- **WHEN** запрос содержит Yjs state не в кодировке base64, не содержит версию Tiptap-схемы либо содержит лишнее поле
- **THEN** API отвечает `400` в едином формате HTTP-ошибок и не изменяет содержимое

#### Scenario: Запись в документ чужой страницы
- **WHEN** пользователь записывает содержимое документа страницы, на которую ему ничего не выдано
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при несуществующей странице, и не изменяет ни один документ

#### Scenario: Запись не затрагивает дерево
- **WHEN** пользователь записывает содержимое документа
- **THEN** заголовок, родитель, ранг, владелец, проект и режим наследования страницы остаются неизменными

### Requirement: Изоляция документов по доступу
Ни одна операция над документами MUST NOT раскрывать существование страницы, к которой у текущего пользователя нет доступа. Для документа недоступной и для документа несуществующей страницы API MUST отвечать одинаковым HTTP status `404` и одинаковым телом ответа.

Ответ `403` MUST использоваться в единственном случае: текущий пользователь вправе читать документ, но его роли не хватает для записи. Скрывать существование документа, который он и так читает, не от кого. Во всех остальных случаях `403` MUST NOT использоваться.

Доступ к документу MUST определяться той же моделью, что и доступ к его странице: отдельных разрешений у документа MUST NOT быть.

#### Scenario: Недоступный и несуществующий документ неразличимы
- **WHEN** пользователь адресует документ страницы, на которую ему ничего не выдано, и затем документ по идентификатору, которому не соответствует ни одна страница, одной и той же операцией
- **THEN** оба ответа имеют одинаковый статус `404` и одинаковое тело

#### Scenario: Читатель получает запрет на запись
- **GIVEN** пользователю выдан `viewer` на чужой странице
- **WHEN** он записывает содержимое её документа
- **THEN** API отвечает `403` в едином формате HTTP-ошибок
- **AND** чтение того же документа этим же пользователем по-прежнему отвечает `200`

#### Scenario: Отсутствие доступа не отвечает запретом
- **WHEN** аутентифицированный пользователь читает или записывает документ страницы, на которую ему ничего не выдано
- **THEN** API не отвечает статусом `403`

### Requirement: Документирование операций документа в OpenAPI
Опубликованный OpenAPI-документ MUST описывать чтение и запись документа со стабильным явным operation ID, schema тела запроса, schema успешного ответа и документированными ответами `400`, `401` и `404`, а запись — дополнительно `403`. Обе операции MUST быть помечены bearer-схемой безопасности. Yjs state MUST быть описан как строка в формате base64.

#### Scenario: Операции документа в OpenAPI-документе
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ содержит paths чтения и записи документа с явными operation ID, schemas запросов и ответов, форматом base64 у Yjs state и bearer-схемой безопасности

#### Scenario: Ответ о недостаточной роли у записи документа
- **WHEN** клиент читает описание записи документа
- **THEN** среди документированных ответов есть `403` в едином формате HTTP-ошибок

### Requirement: Document write ownership transitions to collaboration without dual writers
System MUST считать `PageDocument.yjsState` canonical binary Yjs state для page content. Existing authenticated REST `PUT /api/v1/pages/{pageId}/document` MUST remain available unchanged as a temporary compatibility path for legacy clients until a separate removal change.

После миграции web editor MUST NOT читать или записывать document content через REST, выполнять REST autosave или использовать REST PUT как fallback при ошибках WebSocket. Все штатные frontend document writes MUST идти через Yjs/Hocuspocus, а collaboration runtime MUST быть единственным writer-ом, используемым migrated web editor. Удаление backend REST writer оформляется отдельным change после проверки collaboration end-to-end.

#### Scenario: REST PUT remains a compatibility path
- **WHEN** legacy client вызывает authenticated `PUT /api/v1/pages/{pageId}/document`
- **THEN** API сохраняет существующий REST behavior и validation contract
- **AND** endpoint остаётся доступным до отдельного change по его удалению

#### Scenario: Migrated web editor does not use REST document content
- **WHEN** migrated web editor synchronizes or changes page content
- **THEN** он использует Yjs/Hocuspocus и не вызывает document GET, PUT или REST autosave
- **AND** metadata страниц продолжает работать через REST

#### Scenario: WebSocket failure does not fall back to REST
- **WHEN** collaboration WebSocket disconnected, reconnecting или завершился authentication failure
- **THEN** web editor не вызывает REST PUT для сохранения document content

#### Scenario: Collaboration is the migrated editor writer
- **WHEN** migrated editor changes `PageDocument.yjsState`
- **THEN** изменение сохраняется collaboration runtime
- **AND** backend REST writer не удаляется в этом change и будет рассмотрен отдельным migration change
