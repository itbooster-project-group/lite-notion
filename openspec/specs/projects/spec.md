# projects Specification

## Purpose

Определяет наблюдаемый контракт проектов Lite Notion: контейнеров верхнего уровня, которым принадлежат деревья страниц. Проект нужен странице обязательно, поэтому capability покрывает создание проекта, перечисление проектов владельца и изоляцию чужих проектов.

## Requirements

### Requirement: Проект как контейнер владельца
Проект MUST принадлежать ровно одному пользователю-владельцу и MUST иметь имя. Владельцем создаваемого проекта MUST становиться текущий пользователь; идентификатор владельца MUST NOT приниматься от клиента.

Проект MUST быть контейнером для страниц: страница MUST принадлежать ровно одному проекту, и владелец страницы и владелец её проекта MUST совпадать. Это совпадение MUST быть закреплено на уровне базы данных, а не только проверкой в приложении.

Проект MUST иметь отметку удаления. Все операции чтения проектов MUST исключать проекты с проставленной отметкой удаления; единственное исключение — чтение списка удалённых проектов, которое возвращает только их. Проект с отметкой удаления MUST NOT содержать ни одной страницы без отметки удаления.

#### Scenario: Владелец созданного проекта
- **GIVEN** аутентифицированный пользователь
- **WHEN** он создаёт проект
- **THEN** созданный проект принадлежит ему

#### Scenario: Разные владельцы у страницы и её проекта отвергаются базой
- **WHEN** предпринимается попытка сохранить страницу, чей идентификатор владельца не совпадает с идентификатором владельца её проекта, в обход прикладных проверок
- **THEN** база данных отклоняет запись нарушением constraint, и страница не появляется

#### Scenario: Удалённый проект не виден в чтениях
- **WHEN** у проекта проставлена отметка удаления
- **THEN** список проектов его не возвращает

#### Scenario: Созданный проект не удалён
- **WHEN** пользователь создаёт проект
- **THEN** отметка удаления у него не проставлена, и он возвращается списком проектов

### Requirement: Создание проекта
API MUST публиковать защищённый `POST /api/v1/projects`, принимающий имя проекта. Имя MUST быть непустым и не длиннее установленного предела. Успешное создание MUST отвечать `201` и возвращать проект с его идентификатором, владельцем и именем.

Одинаковые имена у разных проектов одного владельца MUST быть допустимы: имя не является идентификатором.

#### Scenario: Успешное создание проекта
- **WHEN** аутентифицированный пользователь отправляет `POST /api/v1/projects` с непустым именем
- **THEN** API отвечает `201` и возвращает проект, принадлежащий этому пользователю

#### Scenario: Создание проекта с занятым именем
- **WHEN** пользователь создаёт второй проект с именем уже существующего своего проекта
- **THEN** API отвечает `201` и создаёт второй проект

#### Scenario: Создание проекта с недопустимым именем
- **WHEN** запрос содержит пустое имя, имя длиннее допустимого либо лишнее поле
- **THEN** API отвечает `400` в едином формате HTTP-ошибок с перечнем validation messages и не создаёт проект

#### Scenario: Создание проекта без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и не создаёт проект

### Requirement: Список проектов владельца
API MUST публиковать защищённый `GET /api/v1/projects`, возвращающий неудалённые проекты текущего пользователя и только их. Порядок MUST быть детерминированным: два последовательных чтения без изменяющих операций MUST возвращать одинаковую последовательность.

Пользователь без проектов MUST получать пустой список, а не ошибку.

#### Scenario: Чтение непустого списка проектов
- **WHEN** пользователь с несколькими проектами запрашивает `GET /api/v1/projects`
- **THEN** API отвечает `200` и возвращает его проекты
- **AND** ответ не содержит ни одного проекта другого пользователя

#### Scenario: Чтение пустого списка проектов
- **WHEN** пользователь, не создавший ни одного проекта, запрашивает `GET /api/v1/projects`
- **THEN** API отвечает `200` и возвращает пустой список

#### Scenario: Детерминированный порядок проектов
- **WHEN** пользователь дважды подряд запрашивает список, не выполняя между запросами изменяющих операций
- **THEN** порядок проектов в обоих ответах совпадает

#### Scenario: Удалённый проект в списке отсутствует
- **WHEN** пользователь удаляет один из своих проектов и запрашивает `GET /api/v1/projects`
- **THEN** ответ содержит его остальные проекты и не содержит удалённый

### Requirement: Мягкое удаление проекта
API MUST публиковать защищённый `DELETE /api/v1/projects/{projectId}`, помечающий проект удалённым. Удаление MUST быть мягким: запись MUST оставаться в хранилище, и её идентификатор, владелец и имя MUST оставаться неизменными.

Удаление проекта MUST каскадно помечать удалёнными все его живые страницы на любой глубине с источником «удалена вместе с проектом». Страницы, уже помеченные удалёнными, MUST сохранять свой источник и свою прежнюю отметку времени удаления.

Пометка проекта и пометка его страниц MUST выполняться в одной транзакции: при отказе на любом шаге ни проект, ни одна страница MUST NOT остаться помеченными.

Успешное удаление MUST отвечать `204` без тела. Удаление уже удалённого, чужого или несуществующего проекта MUST отвечать `404` в едином формате HTTP-ошибок.

#### Scenario: Удаление проекта со страницами
- **GIVEN** проект с деревом страниц на нескольких уровнях
- **WHEN** пользователь отправляет `DELETE /api/v1/projects/{projectId}`
- **THEN** API отвечает `204`
- **AND** последующие `GET /api/v1/projects` и `GET /api/v1/pages` не возвращают ни этот проект, ни одну его страницу

#### Scenario: Удаление пустого проекта
- **WHEN** пользователь удаляет проект без страниц
- **THEN** API отвечает `204`, и проект перестаёт возвращаться списком проектов

#### Scenario: Соседний проект не затрагивается
- **WHEN** пользователь удаляет один из двух своих проектов
- **THEN** второй проект и все его страницы остаются в обычных выдачах

#### Scenario: Ранее удалённая страница не перемечается
- **GIVEN** проект, в котором страница `B` удалена самостоятельно раньше
- **WHEN** пользователь удаляет этот проект
- **THEN** `B` сохраняет источник «удалена самостоятельно» и прежнюю отметку времени удаления

#### Scenario: Повторное удаление проекта
- **WHEN** пользователь удаляет проект, уже помеченный удалённым
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при удалении несуществующего проекта

#### Scenario: Удаление чужого проекта
- **WHEN** пользователь удаляет проект другого пользователя
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, и ни проект, ни его страницы не помечаются удалёнными

#### Scenario: Удаление проекта без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и не удаляет проект

#### Scenario: Отказ в середине каскада
- **WHEN** удаление прерывается ошибкой после пометки проекта, но до пометки всех его страниц
- **THEN** ни проект, ни одна страница не остаются помеченными

### Requirement: Восстановление проекта
API MUST публиковать защищённый `POST /api/v1/projects/{projectId}/restore`, снимающий отметку удаления с проекта. Восстановление MUST снимать отметку ровно с тех страниц проекта, чей источник — «удалена вместе с проектом». Страницы, удалённые раньше и самостоятельно, и их каскадные потомки MUST оставаться удалёнными.

Восстановление MUST возвращать дерево проекта в состояние, предшествовавшее удалению проекта: родители, ранги и содержимое документов MUST оставаться прежними.

Восстановление MUST выполняться в одной транзакции: при отказе на любом шаге ни проект, ни одна страница MUST NOT остаться восстановленными.

Успешное восстановление MUST отвечать `200` и возвращать восстановленный проект. Восстановление неудалённого, чужого или несуществующего проекта MUST отвечать `404` в едином формате HTTP-ошибок.

#### Scenario: Восстановление проекта с деревом
- **GIVEN** удалённый проект с деревом страниц
- **WHEN** пользователь отправляет `POST /api/v1/projects/{projectId}/restore`
- **THEN** API отвечает `200` и возвращает восстановленный проект
- **AND** чтение дерева страниц возвращает то же дерево, что и до удаления проекта

#### Scenario: Ранее удалённая страница не воскресает
- **GIVEN** проект, в котором страница `B` удалена самостоятельно раньше, а затем удалён сам проект
- **WHEN** пользователь восстанавливает проект
- **THEN** API отвечает `200`, и все страницы проекта, кроме `B` и её потомков, возвращаются чтением дерева
- **AND** `B` остаётся в корзине страниц отдельным корнем

#### Scenario: Восстановление неудалённого проекта
- **WHEN** пользователь восстанавливает проект, не помеченный удалённым
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при восстановлении несуществующего проекта

#### Scenario: Восстановление чужого проекта
- **WHEN** пользователь восстанавливает удалённый проект другого пользователя
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, и проект другого пользователя остаётся удалённым

#### Scenario: Восстановление проекта без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и не восстанавливает проект

### Requirement: Чтение списка удалённых проектов
API MUST публиковать защищённый `GET /api/v1/projects/trash`, возвращающий удалённые проекты текущего пользователя и только их. Неудалённые проекты MUST NOT попадать в эту выдачу.

Выдача MUST быть плоским списком самих проектов и MUST NOT содержать их страниц: удалённые страницы, включая удалённые вместе с проектом, целиком видны через корзину страниц. Второго места, где показывается удалённая страница, MUST NOT существовать.

Каждый элемент MUST содержать идентификатор, владельца, имя и отметку времени удаления. Проекты MUST быть упорядочены по убыванию отметки времени удаления: недавно удалённое идёт первым — тем же правилом, что и корни корзины страниц. Порядок MUST быть детерминированным: два последовательных чтения без изменяющих операций MUST возвращать одинаковую последовательность.

Пользователь без удалённых проектов MUST получать пустой список, а не ошибку.

#### Scenario: Чтение непустого списка удалённых проектов
- **GIVEN** пользователь удалил проект со страницами
- **WHEN** он запрашивает `GET /api/v1/projects/trash`
- **THEN** API отвечает `200` и возвращает этот проект с отметкой времени удаления
- **AND** ответ не содержит ни одной страницы
- **AND** ответ не содержит ни одного неудалённого проекта и ни одного проекта другого пользователя

#### Scenario: Чтение пустого списка удалённых проектов
- **WHEN** пользователь, не удаливший ни одного проекта, запрашивает `GET /api/v1/projects/trash`
- **THEN** API отвечает `200` и возвращает пустой список

#### Scenario: Детерминированный порядок удалённых проектов
- **WHEN** пользователь дважды подряд запрашивает список удалённых проектов, не выполняя между запросами изменяющих операций
- **THEN** порядок проектов в обоих ответах совпадает

#### Scenario: Недавно удалённый проект идёт первым
- **GIVEN** пользователь удалил два проекта в разное время
- **WHEN** он запрашивает список удалённых проектов
- **THEN** удалённый позже возвращается раньше удалённого раньше

#### Scenario: Чтение списка удалённых проектов без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок

### Requirement: Окончательное удаление проекта по запросу пользователя
API MUST публиковать защищённый `DELETE /api/v1/projects/trash/{projectId}`, безвозвратно удаляющий проект из хранилища вместе со всеми его страницами и их документами — независимо от того, каким источником удаления помечена каждая страница.

Операция MUST быть доступна только для удалённого проекта. Неудалённый, чужой или несуществующий проект MUST отвечать `404` в едином формате HTTP-ошибок: окончательное удаление MUST NOT быть способом убрать живой проект в обход мягкого удаления.

Операция MUST подчиняться тому же правилу подтверждения, что и окончательное удаление страницы. Страницы проекта, удалённые самостоятельно, корзина страниц показывает отдельными корнями, а не содержимым удаляемого проекта, поэтому их уничтожение MUST требовать явного подтверждения: запрос без него MUST отвечать `409`, MUST называть причину и MUST перечислять заголовки всех таких страниц тем же способом, что и окончательное удаление страницы, а повторный запрос с подтверждением MUST выполнять удаление целиком.

Подтверждение MUST передаваться тем же явным параметром запроса, что и у окончательного удаления страницы, и MUST NOT подразумеваться по умолчанию. Сохранить такие страницы MUST NOT быть возможно: вне проекта страница существовать не может.

Проект, все страницы которого удалены вместе с ним, MUST удаляться без подтверждения: отдельных корней корзины в нём нет.

Операция MUST быть необратимой: после неё ни проект, ни его страницы MUST NOT возвращаться ни одним чтением, включая чтения корзины, и их восстановление MUST отвечать `404`.

Удаление MUST выполняться в одной транзакции: при отказе на любом шаге ни проект, ни одна страница MUST NOT исчезнуть из хранилища.

#### Scenario: Окончательное удаление проекта с деревом
- **GIVEN** удалённый проект с деревом страниц
- **WHEN** пользователь отправляет `DELETE /api/v1/projects/trash/{projectId}`
- **THEN** API отвечает `204`
- **AND** ни проект, ни его страницы, ни их документы не возвращаются ни обычными чтениями, ни чтениями корзины
- **AND** последующее восстановление этого проекта отвечает `404`

#### Scenario: Отказ без подтверждения
- **GIVEN** удалённый проект, в котором страница `B` была удалена самостоятельно раньше и потому осталась отдельным корнем корзины страниц
- **WHEN** пользователь окончательно удаляет проект без явного подтверждения
- **THEN** API отвечает `409` в едином формате HTTP-ошибок, называет причину и перечисляет заголовки страниц, которые будут уничтожены дополнительно
- **AND** перечень содержит заголовок `B`
- **AND** ни проект, ни `B` не исчезают из хранилища

#### Scenario: Удаление с подтверждением
- **GIVEN** тот же удалённый проект и тот же отказ
- **WHEN** пользователь повторяет запрос с явным подтверждением
- **THEN** API отвечает `204`, и проект вместе с `B` и всеми остальными его страницами исчезает из хранилища

#### Scenario: Проект без отдельно удалённых страниц не требует подтверждения
- **GIVEN** удалённый проект, все страницы которого удалены вместе с ним
- **WHEN** пользователь окончательно удаляет проект без подтверждения
- **THEN** API отвечает `204` и удаляет проект со всеми его страницами

#### Scenario: Страницы других проектов не затрагиваются
- **GIVEN** пользователь удалил два проекта и окончательно удаляет один из них
- **WHEN** запрос выполнен
- **THEN** страницы второго проекта остаются в хранилище и по-прежнему возвращаются чтением корзины страниц

#### Scenario: Окончательное удаление живого проекта
- **WHEN** пользователь адресует этой операцией проект, не помеченный удалённым
- **THEN** API отвечает `404` в едином формате HTTP-ошибок, и проект со своими страницами остаётся в хранилище

#### Scenario: Окончательное удаление чужого проекта
- **WHEN** пользователь адресует этой операцией удалённый проект другого пользователя
- **THEN** API отвечает `404` с тем же статусом и тем же телом, что и при несуществующем проекте, и проект другого пользователя остаётся в хранилище

#### Scenario: Окончательное удаление проекта без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и ничего не удаляет

### Requirement: Очистка корзины проектов
API MUST публиковать защищённый `DELETE /api/v1/projects/trash`, безвозвратно удаляющий из хранилища все удалённые проекты текущего пользователя вместе со всеми их страницами и документами.

Очистка MUST затрагивать только записи текущего пользователя и MUST NOT затрагивать неудалённые проекты. Очистка MUST быть идемпотентной: вызов на пустой корзине MUST отвечать успехом, а не ошибкой. Успешная очистка MUST отвечать `204` без тела.

Очистка MUST подчиняться тому же правилу подтверждения, что и удаление одного проекта: если хотя бы в одном из очищаемых проектов есть страницы, удалённые самостоятельно, запрос без подтверждения MUST отвечать `409` с причиной и заголовками всех таких страниц по всем очищаемым проектам, а запрос с подтверждением MUST выполнять очистку целиком.

#### Scenario: Очистка непустой корзины проектов
- **GIVEN** пользователь удалил несколько проектов со страницами
- **WHEN** он отправляет `DELETE /api/v1/projects/trash`
- **THEN** API отвечает `204`, и последующее чтение списка удалённых проектов возвращает пустой список
- **AND** ни один из этих проектов, ни одна их страница и ни один документ не остаются в хранилище

#### Scenario: Очистка не трогает живые проекты
- **WHEN** пользователь очищает корзину проектов
- **THEN** список проектов и дерево страниц возвращают то же, что и до очистки

#### Scenario: Очистка не трогает чужую корзину проектов
- **WHEN** пользователь очищает свою корзину проектов
- **THEN** удалённые проекты других пользователей остаются в хранилище

#### Scenario: Очистка корзины проектов без подтверждения
- **GIVEN** среди удалённых проектов есть проект с самостоятельно удалённой страницей
- **WHEN** пользователь отправляет `DELETE /api/v1/projects/trash` без явного подтверждения
- **THEN** API отвечает `409` с причиной и заголовками таких страниц и ничего не удаляет

#### Scenario: Очистка пустой корзины проектов
- **WHEN** пользователь, не удаливший ни одного проекта, отправляет `DELETE /api/v1/projects/trash`
- **THEN** API отвечает `204` и ничего не изменяет

#### Scenario: Очистка корзины проектов без аутентификации
- **WHEN** запрос не содержит действующий access-токен
- **THEN** API отвечает `401` в едином формате HTTP-ошибок и ничего не удаляет

### Requirement: Изоляция проектов по владельцу
Ни одна операция MUST NOT раскрывать существование проекта другого пользователя. Для чужого и для несуществующего проекта API MUST отвечать одинаковым HTTP status `404` и одинаковым телом ответа. Ответ `403` MUST NOT использоваться.

Удалённый проект MUST быть неотличим от несуществующего во всех операциях, кроме чтения списка удалённых проектов и восстановления: любая операция, принимающая идентификатор проекта, включая создание страницы, MUST отвечать на удалённый проект тем же `404` и тем же телом, что и на несуществующий.

Ни одна операция MUST NOT изменять владельца существующего проекта — включая удаление и восстановление.

#### Scenario: Использование чужого проекта
- **WHEN** пользователь адресует проект другого пользователя в любой операции, принимающей идентификатор проекта
- **THEN** API отвечает `404` в едином формате HTTP-ошибок

#### Scenario: Чужой и несуществующий проект неразличимы
- **WHEN** пользователь адресует чужой проект и затем идентификатор, которому не соответствует ни один проект
- **THEN** оба ответа имеют одинаковый статус `404` и одинаковое тело

#### Scenario: Удалённый и несуществующий проект неразличимы
- **WHEN** пользователь адресует свой удалённый проект и затем идентификатор, которому не соответствует ни один проект
- **THEN** оба ответа имеют одинаковый статус `404` и одинаковое тело

#### Scenario: Создание страницы в удалённом проекте
- **WHEN** пользователь создаёт страницу, указывая идентификатор своего удалённого проекта
- **THEN** API отвечает `404` в едином формате HTTP-ошибок и не создаёт страницу

### Requirement: Документирование операций проектов в OpenAPI
Опубликованный OpenAPI-документ MUST описывать каждую операцию над проектами со стабильным явным operation ID, schema тела запроса, schema успешного ответа и документированными ответами `400` и `401`, а для операций, адресующих конкретный проект, — дополнительно `404`. Операции мягкого удаления, окончательного удаления и очистки корзины MUST документировать ответ `204` без тела, а операции окончательного удаления и очистки корзины — ещё и ответ `409` вместе с параметром подтверждения. Каждая операция MUST быть помечена bearer-схемой безопасности.

#### Scenario: Операции проектов в OpenAPI-документе
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ содержит paths операций проектов с явными operation ID, schemas запросов и ответов и bearer-схемой безопасности

#### Scenario: Операции корзины проектов в OpenAPI-документе
- **WHEN** клиент читает опубликованный OpenAPI JSON
- **THEN** документ содержит операции мягкого удаления, восстановления, чтения списка удалённых проектов, окончательного удаления проекта и очистки корзины проектов с явными operation ID и документированными ответами
