# user-authentication Specification

## Purpose

Определяет наблюдаемый контракт учётных записей Lite Notion: регистрацию по email, вход с выдачей токенов, серверные сессии в базе данных, обновление и отзыв доступа, а также правило, по которому маршрут считается защищённым.

## Requirements

### Requirement: Регистрация по email
API MUST публиковать публичный `POST /api/v1/auth/register`, принимающий `email`, `name` и `password`. Email MUST быть синтаксически корректным и нормализоваться к нижнему регистру перед сохранением и сравнением. Email MUST быть уникален среди учётных записей. Пароль MUST иметь длину не менее 8 символов и не более 72 байт в кодировке UTF-8 и MUST сохраняться исключительно в виде bcrypt-хеша. Верхняя граница MUST измеряться в байтах, а не в символах: bcrypt обрезает вход ровно на 72 байтах, поэтому проверка по символам принимала бы пароли, от которых до хеша доходит только часть. Подтверждение email MUST NOT требоваться: созданная учётная запись сразу пригодна для входа.

Успешная регистрация MUST создавать учётную запись, открывать сессию и возвращать ту же пару токенов, что и вход. Ответ MUST NOT содержать хеш пароля или сам пароль ни в каком виде.

#### Scenario: Успешная регистрация
- **WHEN** клиент отправляет `POST /api/v1/auth/register` с неиспользованным email, непустым именем и паролем допустимой длины
- **THEN** API отвечает `201`, создаёт учётную запись с bcrypt-хешем пароля, открывает сессию и возвращает access-токен в теле вместе с профилем пользователя
- **AND** тело ответа не содержит ни пароль, ни его хеш

#### Scenario: Повторная регистрация с занятым email
- **WHEN** клиент отправляет `POST /api/v1/auth/register` с email, который уже принадлежит учётной записи
- **THEN** API отвечает `409` в едином формате HTTP-ошибок и не создаёт вторую учётную запись

#### Scenario: Регистрация с email в другом регистре
- **WHEN** клиент регистрируется с email, отличающимся от существующего только регистром символов
- **THEN** API отвечает `409` и трактует адрес как уже занятый

#### Scenario: Регистрация с недопустимыми данными
- **WHEN** запрос содержит некорректный email, пустое имя, пароль короче 8 символов либо лишнее поле
- **THEN** API отвечает `400` в едином формате HTTP-ошибок с перечнем validation messages и не создаёт учётную запись

#### Scenario: Регистрация с не-ASCII паролем длиннее 72 байт
- **WHEN** клиент отправляет пароль, укладывающийся в 72 символа, но занимающий более 72 байт UTF-8 — например 40 символов кириллицы или 36 emoji
- **THEN** API отвечает `400` и не создаёт учётную запись

#### Scenario: Регистрация с не-ASCII паролем ровно в 72 байта
- **WHEN** клиент отправляет пароль, занимающий ровно 72 байта UTF-8 — например 36 символов кириллицы
- **THEN** API отвечает `201`, и этот же пароль позволяет последующий вход

### Requirement: Вход по email и паролю
API MUST публиковать публичный `POST /api/v1/auth/login`, принимающий `email` и `password`. При совпадении учётных данных API MUST открывать новую сессию и выдавать пару токенов.

Ответ на неверные учётные данные MUST быть неотличим для несуществующего email и для неверного пароля: одинаковый HTTP status `401` и одинаковое сообщение. Сравнение пароля MUST выполняться и в случае отсутствия учётной записи, чтобы время ответа не раскрывало существование email.

Вход MUST отклонять пароль длиннее 72 байт UTF-8 как невалидный ввод. Такой пароль MUST NOT считаться совпавшим ни с одной учётной записью: сравнение по усечённому до 72 байт значению открывало бы доступ по любому префиксу нужной длины.

#### Scenario: Вход с верными учётными данными
- **WHEN** клиент отправляет `POST /api/v1/auth/login` с email и паролем существующей учётной записи
- **THEN** API отвечает `200`, создаёт запись сессии и возвращает access-токен в теле и refresh-токен в cookie

#### Scenario: Вход с неверным паролем
- **WHEN** клиент отправляет корректный email существующей учётной записи и неверный пароль
- **THEN** API отвечает `401` в едином формате ошибок с сообщением, не раскрывающим существование учётной записи, и не создаёт сессию

#### Scenario: Вход с несуществующим email
- **WHEN** клиент отправляет email, которому не соответствует ни одна учётная запись
- **THEN** API отвечает `401` с тем же статусом и тем же сообщением, что и при неверном пароле

#### Scenario: Вход с паролем длиннее 72 байт
- **WHEN** клиент отправляет пароль, занимающий более 72 байт UTF-8
- **THEN** API отвечает `400` и не выдаёт токены

#### Scenario: Вход по префиксу пароля длиной 72 байта
- **WHEN** клиент отправляет пароль, первые 72 байта которого совпадают с паролем существующей учётной записи
- **THEN** API не считает учётные данные верными и не выдаёт токены

### Requirement: Пара токенов и их транспорт
Успешные вход, регистрация и обновление MUST возвращать короткоживущий access-токен в теле ответа и долгоживущий refresh-токен в `Set-Cookie`.

Access-токен MUST быть подписанным JWT, содержать идентификатор пользователя и идентификатор сессии, иметь настроенный ограниченный срок жизни и проверяться без обращения к базе данных. Refresh-токен MUST быть непредсказуемой случайной строкой, MUST NOT нести полезную нагрузку и MUST устанавливаться cookie с флагами `HttpOnly` и `SameSite`, а вне development — дополнительно с флагом `Secure`. Cookie MUST быть ограничена путём эндпоинтов аутентификации.

Refresh-токен MUST NOT возвращаться в теле ответа и MUST NOT быть доступен клиентскому JavaScript.

#### Scenario: Состав успешного ответа аутентификации
- **WHEN** запрос регистрации, входа или обновления завершается успешно
- **THEN** тело ответа содержит access-токен и его срок жизни, а заголовок `Set-Cookie` содержит refresh-токен с флагами `HttpOnly` и `SameSite`
- **AND** тело ответа не содержит refresh-токен

#### Scenario: Использование access-токена
- **WHEN** клиент обращается к защищённому маршруту с действительным непросроченным access-токеном в заголовке `Authorization`
- **THEN** API выполняет запрос, определяя пользователя и сессию из полезной нагрузки токена, и сама проверка токена не обращается к базе данных

### Requirement: Хранение сессий в базе данных
Каждая выданная пара токенов MUST соответствовать строке сессии в базе данных. Сессия MUST хранить владельца, срок истечения, отметку отзыва и идентификатор цепочки ротаций. Refresh-токен MUST храниться только как криптографический хеш: компрометация содержимого базы MUST NOT позволять предъявить refresh-токен.

Удаление учётной записи MUST удалять все её сессии.

#### Scenario: Сессия создаётся при выдаче токенов
- **WHEN** API выдаёт пару токенов
- **THEN** в базе появляется строка сессии, связанная с владельцем, с сроком истечения по настроенному refresh TTL и с хешем refresh-токена вместо самого токена

#### Scenario: Предъявление токена, отсутствующего в базе
- **WHEN** клиент предъявляет refresh-токен, которому не соответствует ни одна строка сессии
- **THEN** API отвечает `401` и не выдаёт новую пару токенов

### Requirement: Обновление токенов с ротацией
API MUST публиковать публичный `POST /api/v1/auth/refresh`, принимающий refresh-токен из cookie. При действительной сессии API MUST выдавать новую пару токенов, помечать предъявленную сессию отозванной и связывать её с заменившей сессией в той же цепочке.

Просроченная либо ранее отозванная за пределами grace-периода сессия MUST NOT продлевать доступ. Обновление MUST NOT продлевать общий срок жизни цепочки сверх настроенного refresh TTL, отсчитываемого от последней ротации.

#### Scenario: Успешное обновление
- **WHEN** клиент отправляет `POST /api/v1/auth/refresh` с действительным неотозванным refresh-токеном
- **THEN** API отвечает `200`, выдаёт новую пару токенов, помечает предъявленную сессию отозванной и связывает её с новой

#### Scenario: Обновление без cookie
- **WHEN** клиент отправляет `POST /api/v1/auth/refresh` без refresh cookie
- **THEN** API отвечает `401` в едином формате ошибок

#### Scenario: Обновление по истёкшему токену
- **WHEN** клиент предъявляет refresh-токен, срок действия которого истёк
- **THEN** API отвечает `401`, не выдаёт новую пару токенов и очищает refresh cookie

### Requirement: Grace-период повторного обновления
Отозванная ротацией сессия MUST оставаться пригодной для обновления в течение grace-периода в 30 секунд после момента отзыва. Обновление внутри grace-периода MUST выдавать новую действующую пару токенов в той же цепочке ротаций и MUST NOT трактоваться как повторное использование токена.

В каждой цепочке ротаций MUST существовать не более одной неотозванной сессии: обновление внутри grace-периода MUST отзывать текущую действующую сессию цепочки, а не создавать параллельную ветвь.

Предъявление сессии, отозванной более 30 секунд назад, MUST трактоваться как повторное использование токена.

#### Scenario: Параллельное обновление с одинаковым токеном
- **WHEN** клиент отправляет два запроса обновления с одним и тем же refresh-токеном с интервалом менее 30 секунд
- **THEN** оба запроса отвечают `200` и возвращают действующие refresh-токены одной цепочки, пользователь остаётся аутентифицированным и может обновиться по последнему полученному токену

#### Scenario: Повтор запроса после потерянного ответа
- **WHEN** клиент не получил ответ на обновление и повторяет запрос тем же refresh-токеном в пределах 30 секунд
- **THEN** API отвечает `200` и выдаёт действующую пару токенов, не отзывая цепочку

#### Scenario: Единственная действующая сессия в цепочке
- **WHEN** внутри grace-периода выполнено несколько последовательных обновлений одной цепочки
- **THEN** в цепочке остаётся не более одной неотозванной сессии

#### Scenario: Повторное обновление после истечения grace-периода
- **WHEN** клиент предъявляет refresh-токен, отозванный более 30 секунд назад
- **THEN** API отвечает `401` и трактует запрос как повторное использование токена

### Requirement: Обнаружение повторного использования refresh-токена
Предъявление отозванной сессии за пределами grace-периода MUST отзывать все сессии её цепочки ротаций, включая текущую действующую. После этого владелец MUST быть вынужден войти заново, а ранее выданные refresh-токены цепочки MUST перестать действовать.

Отзыв цепочки MUST NOT затрагивать сессии того же пользователя, открытые другими входами.

#### Scenario: Использование украденного refresh-токена
- **WHEN** refresh-токен предъявлен повторно позже grace-периода, а цепочка уже была ротирована
- **THEN** API отвечает `401`, отзывает все сессии этой цепочки и очищает refresh cookie

#### Scenario: Действующая сессия после отзыва цепочки
- **WHEN** цепочка отозвана из-за обнаруженного повторного использования и клиент предъявляет самый свежий refresh-токен этой цепочки
- **THEN** API отвечает `401` и не выдаёт новую пару токенов

#### Scenario: Изоляция других устройств
- **WHEN** цепочка одного устройства отозвана из-за обнаруженного повторного использования
- **THEN** сессии того же пользователя, открытые другими входами, продолжают действовать

### Requirement: Выход
API MUST публиковать защищённый `POST /api/v1/auth/logout`, который делает недействительной всю цепочку ротаций текущего запроса и очищает refresh cookie. Областью выхода MUST быть цепочка целиком, а не отдельная сессия: выход MUST прекращать доступ и в случае, когда цепочку успели ротировать после выдачи предъявленного access-токена. API MUST также публиковать защищённый выход со всех устройств, делающий недействительными все сессии пользователя.

Выход MUST действовать немедленно: grace-период повторного обновления MUST NOT продлевать жизнь завершённой цепочки. Выход MUST NOT затрагивать другие цепочки того же пользователя.

Выход MUST быть идемпотентным: повторный выход MUST NOT возвращать серверную ошибку.

#### Scenario: Выход с текущего устройства
- **WHEN** аутентифицированный клиент отправляет `POST /api/v1/auth/logout`
- **THEN** API отвечает `204`, делает цепочку недействительной и возвращает `Set-Cookie`, очищающий refresh cookie

#### Scenario: Обновление после выхода
- **WHEN** клиент после выхода предъявляет refresh-токен завершённой цепочки
- **THEN** API отвечает `401` и не выдаёт новую пару токенов, независимо от того, сколько времени прошло с момента выхода

#### Scenario: Выход после опередившей ротации
- **WHEN** цепочка была ротирована после выдачи предъявленного при выходе access-токена
- **THEN** API отвечает `204`, и самый свежий refresh-токен цепочки перестаёт позволять обновление

#### Scenario: Выход не затрагивает другие устройства
- **WHEN** аутентифицированный клиент выходит на одном устройстве
- **THEN** сессии того же пользователя, открытые другими входами, продолжают действовать

#### Scenario: Выход со всех устройств
- **WHEN** аутентифицированный клиент запрашивает выход со всех устройств
- **THEN** API отвечает `204`, и ни один ранее выданный refresh-токен этого пользователя не позволяет обновление

### Requirement: Профиль текущего пользователя
API MUST публиковать защищённый `GET /api/v1/auth/me`, возвращающий идентификатор, email, имя и момент создания учётной записи владельца access-токена. Ответ MUST NOT содержать хеш пароля, сам пароль, refresh-токен или его хеш.

#### Scenario: Запрос профиля с действительным токеном
- **WHEN** клиент запрашивает `GET /api/v1/auth/me` с действительным access-токеном
- **THEN** API отвечает `200` и возвращает идентификатор, email, имя и момент создания учётной записи

#### Scenario: Запрос профиля без токена
- **WHEN** клиент запрашивает `GET /api/v1/auth/me` без заголовка `Authorization`
- **THEN** API отвечает `401` в едином формате ошибок

### Requirement: Защита маршрутов по умолчанию
Каждый прикладной HTTP-маршрут API MUST требовать действительный access-токен, если он не помечен явно как публичный. Отсутствующий, синтаксически некорректный, просроченный либо подписанный другим ключом токен MUST приводить к ответу `401` в едином формате HTTP-ошибок. Ответ `401` MUST NOT раскрывать причину отклонения токена.

`GET /api/v1/health` MUST оставаться публичным и сохранять существующий контракт ответов.

#### Scenario: Приватный маршрут без токена
- **WHEN** клиент обращается к маршруту, не помеченному публичным, без заголовка `Authorization`
- **THEN** API отвечает `401` в едином формате ошибок и не выполняет обработчик маршрута

#### Scenario: Приватный маршрут с просроченным токеном
- **WHEN** клиент обращается к приватному маршруту с access-токеном, срок действия которого истёк
- **THEN** API отвечает `401` и не выполняет обработчик маршрута

#### Scenario: Приватный маршрут с подделанной подписью
- **WHEN** клиент обращается к приватному маршруту с токеном, подписанным другим ключом либо с изменённой полезной нагрузкой
- **THEN** API отвечает `401` и не выполняет обработчик маршрута

#### Scenario: Публичный маршрут без токена
- **WHEN** клиент обращается к `GET /api/v1/health` без токена
- **THEN** API обрабатывает запрос по существующему контракту health-проверки

### Requirement: Плановая очистка устаревших сессий
API MUST периодически по расписанию удалять из базы данных сессии, срок действия которых истёк, а также сессии, отозванные ранее настроенного порога хранения. Очистка MUST NOT удалять действующие сессии и MUST NOT прерывать обработку HTTP-запросов. Ошибка отдельного запуска очистки MUST логироваться и MUST NOT останавливать процесс API или последующие запуски.

#### Scenario: Плановый запуск очистки
- **WHEN** наступает момент планового запуска очистки
- **THEN** истёкшие и давно отозванные сессии удаляются, а действующие сессии остаются в базе

#### Scenario: Аутентификация после очистки
- **WHEN** очистка удалила истёкшие сессии и клиент с действующей сессией отправляет запрос обновления
- **THEN** API отвечает `200` и выдаёт новую пару токенов

#### Scenario: Ошибка запуска очистки
- **WHEN** плановый запуск очистки завершается ошибкой базы данных
- **THEN** API записывает ошибку в серверный лог, продолжает обслуживать запросы и выполняет следующий плановый запуск
